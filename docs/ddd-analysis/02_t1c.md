### ungear-core + ungear-plugin

- **Status:** CURRENT
- Audit date: 2026-03-20
- Declared tier: T1 · 1c · The Mechanics
- Pair: `ungear-core` / `ungear-plugin` (same tier: YES)
- Internal deps (`ungear-core`): `unspatial-core` (T0), `untypes-core` (T0), `unghost-core` (T1·1b)
- Internal deps (`ungear-plugin`): `ungear-core` (T1·1c), `unspatial-core` (T0), `untypes-core` (T0), `untags-core`
  (T0), `unboard-core` (T1·1a), `unplayer-core` (T1·1b), `unmetrics-core` (T0), `untruck-core` (T1·1c), `unrender-std`
  (T4·4a)
- Highest tier imported (`ungear-core`): **T1** — `unghost-core` (T1·1b, same tier, compliant)
- Highest tier imported (`ungear-plugin`): **T4** — `unrender-std`
- Tier compliance (`ungear-core`): **PASS**
- Tier compliance (`ungear-plugin`): **FAIL** — declared T1, imports T4

**Notes — `ungear-core`:**

The crate is architecturally sound for a framework layer. It defines the gear slot model (`PlayerGear`, `HeldObject`,
`EquipmentPosition`), base component traits (`Handheld`, `Battery`, `Electronic`, `EvidenceSensor`, `GearSprite`), the
`GearSpawnerRegistry` (a component factory registry), the `LookingGear` resource, and the `DifficultyGearExt` extension
trait that maps `Difficulty` → starting gear loadout.

The only coupling concern:

`unghost-core` (T1·1b) is imported because `GearDetails::RepellentFlask` carries `liquid_content: Option<GhostType>`.
Gear needs to reference ghost types for the crafting mechanic. This is a same-tier (T1) downward import within the
sub-tier ordering (1c → 1b) and is formally compliant. However, it couples the gear framework to the ghost domain at the
framework level: every crate that imports `ungear-core` transitively depends on `unghost-core`. The cleaner fix would be
to promote `GhostType` to `untypes-core` (T0), where it would be available to all domains without cross-domain coupling.

**Notes — `ungear-plugin`:**

The plugin handles two concerns: visual presentation of deployed gear (sprite updates) and UI state (the gear slot
images in the HUD + status text). Both are squarely T4 concerns. The gear slot images rendered in the HUD — mapping hand
slots to sprite atlas indices — are pure presentation logic.

**Additional structural issue — two plugins in one file:**

Like `unnpc-plugin`, the `plugin.rs` file defines both `UnhaunterGearCorePlugin` and `UnhaunterGearPlugin`. The "core
plugin" initializes `GameConfig` (a camera-follow resource from `unplayer-core`) and `GearSpawnerRegistry`. Initializing
a camera-follow config from the gear plugin is a separation-of-concerns violation regardless of tier: `GameConfig`
should be initialized by `unplayer-plugin` or by the application layer, not by the gear plugin.

**Violations (`ungear-plugin`):**

1. `unrender-std` (T4·4a) — `update_deployed_gear_sprites` inserts `GameSprite`, `SpriteLayer`, `MapColor`, `Sprite`
   (with `TextureAtlas`) onto gear entities. `GearAssets` and `SpriteRegistry` are also T4 rendering resources.
   Deployed-gear sprite management is entirely a T4 rendering concern and belongs in `unrender-plugin` or a T4
   gear-rendering crate, not in the T1 mechanics plugin.

### ungearitems-core + ungearitems-plugin

- **Status:** CURRENT
- Audit date: 2026-03-20
- Declared tier: T1 · 1c · The Mechanics
- Pair: `ungearitems-core` / `ungearitems-plugin` (same tier: YES)
- Internal deps (`ungearitems-core`): `unfoundation-core` (T0), `unghost-core` (T1·1b), `ungear-core` (T1·1c)
- Internal deps (`ungearitems-plugin`): `unspatial-core` (T0), `unfoundation-core` (T0), `untypes-core` (T0),
  `untags-core` (T0), `unmetrics-core` (T0), `unboard-core` (T1·1a), `unlight-core` (T1·1a), `unfog-core` (T1·1a),
  `unsoundfield-core` (T1·1a), `unthermal-core` (T1·1a), `unghost-core` (T1·1b), `unplayer-core` (T1·1b), `ungear-core`
  (T1·1c), `ungearitems-core` (T1·1c), `uninteraction-core` (T1·1c), `undifficulty-core` (T1·1c), `unbehavior-core`
  (T1·1a), `unprofile-core` (T3·3b), `unreplicon-core` (T2), `unaudiospatial-core` (T0), `unmission-core` (T2),
  `unrender-std` (T4·4a)
- Highest tier imported (`ungearitems-core`): **T1** — `unghost-core` (T1·1b), `ungear-core` (T1·1c); all same tier or
  below, compliant.
- Highest tier imported (`ungearitems-plugin`): **T4** — `unrender-std` (T4·4a)
- Tier compliance (`ungearitems-core`): **PASS**
- Tier compliance (`ungearitems-plugin`): **FAIL** — declared T1, imports T2, T3, and T4

**Notes — `ungearitems-core`:**

A clean separation layer for concrete gear state: one file per gear item, each holding data components specific to that
item (`Thermometer`, `SpiritBox`, `Flashlight`, `SageBundleData`, etc.). Also contains `GearDetails`, the compact
network-serializable gear state enum used in `PlayerInput`. The `unghost-core` dep is for
`GearDetails::RepellentFlask::liquid_content: Option<GhostType>` — same coupling note as in `ungear-core`.

The module layout is correct: 20 item-specific component files under `src/components/`, matching the 20 systems under
`ungearitems-plugin/src/components/`. The split is clean and symmetric.

**Notes — `ungearitems-plugin`:**

The plugin is large by necessity: 20 gear items, each with a dedicated update system, all assembled in `plugin.rs`. This
breadth is unavoidable given the item count. The structural quality is high — systems are isolated per item, most bugs
are contained. This is not a god crate in the organisational sense.

**Additional structural issue — two plugins in one file:**

`UnhaunterGearItemsCorePlugin` and `UnhaunterGearItemsPlugin` are both defined in `plugin.rs`. The "core plugin" runs
`system_apply_gear_intent_from_input`, which replicates remote player gear state — a replication concern, not a domain
mechanic. It should live in a T2 or `unreplicon-plugin` handler.

**Violations (`ungearitems-plugin`):**

1. `unbehavior` (T3·3a) — `registration.rs` inserts `Collision` and `InteractableByGhost` from `unbehavior::components`
   onto every registered gear item. The systemic Tiled ACL bleed: domain component registration depends on T3 collision
   marker types that originate from the map pipeline.

2. `unprofile-core` (T3·3b) — `thermometer.rs` and `spiritbox.rs` read `Persistent<PlayerProfileData>` to check
   `times_evidence_acknowledged_on_gear` for the blinking hint UI. A player profile persistence type is being read
   inside a T1 gear simulation system to control a UI hint. This mixes T3 persistence, T4 UI behavior, and T1 domain
   simulation in a single query.

3. `unreplicon-core` (T2) — `plugin.rs` uses `LocalPlayerRole` and `AuthorityRole`; `systems.rs` uses `LocalPlayerRole`
   for conditional execution; `registration.rs` reads `AuthorityRole` to gate which visual-only components are inserted
   (`if !is_authority { cmd.insert(ThermometerVisuals) }`). Replication role-awareness hardcoded into item registration
   means every item knows whether it is on a server or client and installs components accordingly. This is T2
   orchestration embedded in T1 item setup.

4. `unsummary-core` (declared T4·4c, actually misplaced) — same systemic mislabeling documented in prior entries.
   `unsummary-core` is not a T4 presentation type; it is mission-outcome data that is written to in T1 systems.

**Design observation — authority-gated component insertion:**

The `is_authority` flag check in `registration.rs` (e.g. `if !is_authority { cmd.insert(Thermometer::default()) }`)
means that visual and client-side-simulation components are only installed on clients. This is a legitimate network
concern, but it embeds T2 topology knowledge directly into T1 item setup closures. A cleaner design would have the T1
registration insert all components unconditionally, and let a T2 observer despawn or disable presentation components on
the authority node based on role.

**Cross-pair observation — the gear framework split:**

The `ungear-core` / `ungear-plugin` pair defines the item framework and slot model. The `ungearitems-core` /
`ungearitems-plugin` pair provides the concrete implementations. This split is semantically correct: the framework
should not depend on any specific item, and the items should implement the framework's contracts. The current code
honours this: `ungear-core` has no dep on `ungearitems-core`, and `ungear-plugin` has no dep on `ungearitems-plugin`.
The boundary is clean at the core level; the violations are in the plugins, not the framework.

### uninteraction-core + uninteraction-plugin

- **Status:** CURRENT
- Audit date: 2026-03-20
- Declared tier: T1 · 1c · The Mechanics
- Pair: `uninteraction-core` / `uninteraction-plugin` (same tier: YES)
- Internal deps (`uninteraction-core`): `unspatial-core` (T0)
- Internal deps (`uninteraction-plugin`): `uninteraction-core` (T1), `unspatial-core` (T0), `untypes-core` (T0),
  `unboard-core` (T1·1a), `unbehavior-core` (T1·1a), `unrender-std` (T4·4a), `unaudiospatial-core` (T0)
- Highest tier imported (`uninteraction-core`): T0
- Highest tier imported (`uninteraction-plugin`): **T4** (`unrender-std`)
- Tier compliance (`uninteraction-core`): **PASS**
- Tier compliance (`uninteraction-plugin`): **FAIL** — declared T1, imports T4

**Notes — `uninteraction-core`:**

Clean and minimal. The crate defines:

| Module / type               | Content                                                                                          | Verdict |
| --------------------------- | ------------------------------------------------------------------------------------------------ | ------- |
| `InteractionExecutionType`  | Enum: `ChangeState` / `ReadRoomState` (deprecated)                                               | ✅ T1   |
| `RoomChangedEvent`          | Signals a room-level transition; `open_van: bool` flag for van UI                                | ✅ T1   |
| `RoomStateSyncEvent`        | Requests all interactable entities to re-sync their state with `RoomStateMap`                    | ✅ T1   |
| `ExecuteInteractionEvent`   | Triggers an interaction on a specific entity; carries `ietype` and `force_tuid` for network sync | ✅ T1   |
| `Toggleable`                | Component: `is_on: bool` — Bevy-reflected, serializable                                          | ✅ T1   |
| `Triggered`                 | Marker component for activated-this-frame state                                                  | ✅ T1   |
| `Target` / `PositionTarget` | Generic wrapper components for entity/position targeting                                         | ✅ T1   |
| `Authority`                 | Enum: `Host` / `Client` — authority level for interaction execution                              | ✅ T1   |

The event protocol established here is genuinely well-designed: `ExecuteInteractionEvent` is the canonical domain verb
("interact with entity X"), and the event-driven decoupling means multiple dispatchers (player, ghost, environment) can
all trigger interactions without knowing about the handler. No content misplacement and no T3/T4 spillage. A rare clean
`-core`.

**Violations (`uninteraction-plugin`):**

`uninteraction-plugin` is the **handler** side of the interaction domain. It contains three systems and the
`InteractiveStuff` `SystemParam`:

| System / function              | Responsibility                                                                                                                |
| ------------------------------ | ----------------------------------------------------------------------------------------------------------------------------- |
| `interaction_event_handler`    | Receives `ExecuteInteractionEvent`, calls `InteractiveStuff::execute_interaction` — authority-only                            |
| `room_state_sync_system`       | Receives `RoomStateSyncEvent`, iterates all interactive entities and calls `InteractiveStuff::synchronize_entity` — auth-only |
| `trigger_grid_rebuild_on_sync` | Watches for `Changed<Behavior>`, emits `BoardTopologyToRebuild` — runs on all nodes                                           |

`InteractiveStuff` is a `SystemParam` that carries the state machine implementation: it looks up sprite tile variants
from `SpriteDB`, mutates `RoomStateMap`, and plays sounds via `AudioEmitter`. This is where the T3/T4 coupling lives.

1. `unbehavior` (T3·3a) — **RESOLVED (2026-03-22)**: `Behavior`, `Interactive`, `RoomStateDelta` now live in
   `unbehavior-core` (T1·1a) after the split. `uninteraction-plugin` now imports these types from `unbehavior-core`
   instead of `unbehavior`. The structural concern remains: `Interactive` should eventually migrate to
   `uninteraction-core` with a thin Tiled bridge in `unbehavior`, but the tier violation is resolved.

2. `unrender-std` (T4·4a) — `SpriteDB` from `unrender-std` is used in `apply_behavior_update` and `synchronize_entity`
   to resolve tile variant lookups (e.g., "same object, open state" vs "same object, closed state"). The state machine's
   valid states are indexed in the sprite database, indexed by tile CVO key. Sprite variant lookup at interaction time
   is a rendering artifact bleeding into domain logic.

**Domain completeness — the user's main concern:**

The extraction is confirmed **partial**. The crate gives the interaction domain its _event protocol_ and _response
handler_, but leaves substantial interaction complexity distributed across other domains:

| Responsibility                                       | Where it should live              | Where it actually lives                                             |
| ---------------------------------------------------- | --------------------------------- | ------------------------------------------------------------------- |
| Event protocol and domain types                      | `uninteraction-core` ✅           | `uninteraction-core` ✅                                             |
| Nearest-interactable selection + player dispatch     | `uninteraction-plugin`            | `unlocomotion-plugin` (`dispatch_interact_intent`) ❌               |
| Response handler (state machine execution)           | `uninteraction-plugin` ✅         | `uninteraction-plugin` ✅                                           |
| Ghost interaction selection + object manipulation    | `uninteraction-plugin` or event   | `unghost-plugin/systems/gis/` (own parallel path) ❌                |
| Environmental / autonomous interaction dispatch      | `uninteraction-plugin` or T2      | `unclassic-mode-gameplay-plugin/environmental_mechanics.rs` (T2) ⚠️ |
| Room-changed application (van UI, state transitions) | T2 observer on `RoomChangedEvent` | `unclassic-mode-gameplay-plugin/roomchanged.rs` (T2 — correct) ✅   |
| `Interactive` entity type definition                 | `uninteraction-core`              | `unbehavior::behavior` (T3) ❌                                      |
| `InteractableByGhost` marker                         | `uninteraction-core`              | `unbehavior::components` (T3) ❌                                    |
| Network re-firing on server                          | T2 / `unreplicon-plugin`          | `unreplicon-plugin/systems/players.rs` (T2 — correct) ✅            |

**The most telling gap** is `dispatch_interact_intent` in `unlocomotion-plugin`. It queries for `Interactive` entities
within range, applies spatial proximity math, and emits `ExecuteInteractionEvent`. This is squarely an interaction
domain responsibility — finding the interaction target is not locomotion, it is the first step of an interaction. The
extraction stopped at the event boundary: the event definition and response moved, but the dispatch initiation stayed in
locomotion because that was the existing call site.

**Ghost interaction is a parallel path.** The ghost's GIS (`unghost-plugin/systems/gis/`) does not go through
`uninteraction-plugin`. It emits `RoomChangedEvent` directly from its own interaction execution and handles object
manipulation (`gis/execution.rs`) without calling `ExecuteInteractionEvent`. This means there are effectively two
interaction state machines: one in `uninteraction-plugin` (for player interactions), one buried in ghost AI (for ghost
interactions). They share some events (`RoomChangedEvent`) but are otherwise independent code paths. Any future change
to how state machines work (e.g., adding lighting effects when a light is toggled) must be made in both places.

**`Interactive` in `unbehavior` is the root coupling.** Because the canonical type that makes an entity "interactive"
(its sound effects, its state machine contract) is defined in T3, both the dispatch and handler sides must import T3 to
do anything meaningful. Moving `Interactive` to `uninteraction-core` (and leaving only a thin `unbehavior` bridge to
translate Tiled properties into it) would break the upward dependency and allow the plugin to operate on T1 types only.

**The `trigger_grid_rebuild_on_sync` system** is an interesting special case: it watches for `Changed<Behavior>` (a T3
component) and emits `BoardTopologyToRebuild`. This is a reactive coupling — the interaction system tells the board to
rebuild whenever any game object's state changes. Placement here is reasonable because interaction state changes are the
primary cause of `Behavior` mutations at runtime. However, this system is also what makes the plugin technically unable
to avoid importing `unbehavior` even if all other coupling were fixed.

### uninventory-plugin

- **Status:** CURRENT
- Audit date: 2026-03-20
- Declared tier: T1 · 1c · The Mechanics
- Pair: `uninventory-plugin` only — **no `-core` counterpart**
- Internal deps: `unplayer-core` (T1·1b), `untypes-core` (T0), `ungear-core` (T1·1c), `unspatial-core` (T0),
  `unboard-core` (T1·1a), `unreplicon-core` (T2), `unaudiospatial-core` (T0), `unbehavior-core` (T1·1a), `unrender-std`
  (T4·4a), `unvitals-core` (T1·1c), `unlocomotion-core` (T1·1b), `uninput-core` (T1·1b)
- Highest tier imported: **T4** (`unrender-std`)
- Tier compliance: **FAIL** — declared T1, imports T2 and T4

**Violations:**

1. `unreplicon-core` (T2) — `RequestGrab`, `RequestDrop`, `LocallyOwned`, `PlayerDiedEvent` are all replication message
   types. Every slot mutation (pickup, drop, death cleanup) goes through T2 network messages or filters by T2 ownership
   markers. The inventory plugin cannot perform any persistent slot change without routing through the replication
   layer. Replication routing belongs in T2, not inside the domain plugin.

2. `unbehavior` (T3·3a) — **RESOLVED (2026-03-22)**: `Behavior` and `FloorItemCollidable` now come from
   `unbehavior-core` (T1·1a) after the split. The domain plugin no longer needs a T3 import for these types.

3. `unrender-std` (T4·4a) — `strip_visuals_from_grabbed_gear` removes `GameSprite`, `SpriteLayer`, `MapColor`, `Sprite`,
   `Transform`, `Visibility` from gear entities when they are picked up. Visual stripping is a T4 rendering concern: the
   renderer should react to the entity losing its `DeployedGear` component and clean up itself, rather than the
   inventory plugin executing sprite removal directly.

**Domain completeness — no `-core`, borrowed domain types:**

The user's concern is confirmed and extends further than missing a `-core` crate. The inventory domain's primary data
structures are split across **two foreign crates**:

| Type                | What it is                                                                                  | Where it lives          | Where it should live         |
| ------------------- | ------------------------------------------------------------------------------------------- | ----------------------- | ---------------------------- |
| `PlayerGear`        | Component: `left_hand`, `right_hand`, `inventory`, `held_item`                              | `ungear-core` (T1·1c)   | `uninventory-core` (missing) |
| `HeldObject`        | Component: wrapped `Entity` for a held furniture item                                       | `ungear-core` (T1·1c)   | `uninventory-core` (missing) |
| `PlayerGearKind`    | The loadout type: `left_hand: GearKind`, `right_hand: GearKind`, `inventory: Vec<GearKind>` | `ungear-core` (T1·1c)   | `uninventory-core` (missing) |
| `EquipmentPosition` | Enum: `Hand(Left/Right)` / `Stowed` — slot identity component on gear entities              | `ungear-core` (T1·1c)   | `uninventory-core` (missing) |
| `Inventory`         | UI marker component: `hand: Hand` — tags HUD slot image nodes                               | `unplayer-core` (T1·1b) | `uninventory-core` (missing) |
| `InventoryNext`     | UI marker: `idx: Option<usize>` — tags backpack slot slot nodes                             | `unplayer-core` (T1·1b) | `uninventory-core` (missing) |
| `InventoryStats`    | UI marker: `hand: Hand` — tags ammo/stat image nodes                                        | `unplayer-core` (T1·1b) | `uninventory-core` (missing) |

- `PlayerGear`, `HeldObject`, `EquipmentPosition`, and `PlayerGearKind` live in `ungear-core` because inventory was
  never extracted from the gear framework — the extraction created a plugin but left the data where it was. The gear
  framework crate (`ungear-core`) now acts as the `-core` for two bounded contexts: gear framework and inventory state.
  Any crate that needs to know which items a player is holding must import `ungear-core`, not any inventory crate.

- `Inventory`, `InventoryNext`, `InventoryStats` live in `unplayer-core`, further scattering the domain. These three are
  UI marker components used by the gear HUD system (`ungear-plugin`, `unclassic-mode-ui-plugin`, `untruck-plugin`).
  Their placement in the player actor core is incorrect: they are inventory-domain components that escaped into the
  closest available crate at the time of writing.

**What `uninventory-plugin` actually does (correctly):**

Despite the missing core and the imports, the systems inside the plugin represent genuine inventory domain logic:

| System                                | Responsibility                                  | Domain correctness                   |
| ------------------------------------- | ----------------------------------------------- | ------------------------------------ |
| `sync_inventory_position_to_holder`   | Gear entities follow player position            | ✅ T1 kinematics concern             |
| `sync_held_object_position_to_holder` | Held furniture follows player                   | ✅ T1 kinematics concern             |
| `queue_pickup_request`                | Proximity search → emit `RequestGrab`           | ✅ inventory verb                    |
| `queue_drop_request`                  | Drop item at player's feet → emit `RequestDrop` | ✅ inventory verb                    |
| `assign_received_item_to_slot`        | Assign newly-owned entity to a slot             | ✅ slot management                   |
| `strip_visuals_from_grabbed_gear`     | Remove render components when item is picked up | ❌ T4 (should be reactive rendering) |
| `cycle_inventory`                     | Rotate right_hand ↔ inventory queue             | ✅ slot management                   |
| `swap_hand_equipment`                 | Swap left and right hand items                  | ✅ slot management                   |
| `despawn_gear_on_player_death`        | Despawn all gear on player death                | ✅ inventory lifecycle               |

Seven of nine systems are correctly placed as domain inventory mechanics. The boundary violation is in the _how_ (T2
routing, T3 type inspection, T4 visual stripping, T4 sounds) rather than in the _what_.

**The correct target shape:**

1. Create `uninventory-core` (T1·1c) and migrate `PlayerGear`, `HeldObject`, `EquipmentPosition`, `PlayerGearKind` there
   from `ungear-core`. Move `Inventory`, `InventoryNext`, `InventoryStats` there from `unplayer-core`.

2. `ungear-core` retains the gear framework types (`Handheld`, `Battery`, `GearSpawnerRegistry`, etc.) without the slot
   model. It may import `uninventory-core` for `EquipmentPosition` if needed by gear framework types.

3. `uninventory-plugin` imports `uninventory-core` (T1) only. Replication routing (grab/drop requests) becomes T2
   observers on top of inventory events, not embedded in pickup/drop systems. `strip_visuals_from_grabbed_gear` moves to
   a T4 rendering observer. Sounds move to a T4 audio observer reacting to inventory events.

4. The `Inventory` / `InventoryNext` / `InventoryStats` UI markers stay in `uninventory-core` since they are domain
   markers consumed by T4 UI crates — a downward dependency, which is correct.

**Notes — domain scope: player vitals only**

The user raised whether "vitals" should cover all actor types, given that the ghost also has a form of health
(`get_health()` on `GhostSprite`, derived from `repellent_hits`).

The answer from ECS domain modeling is **no**. Vitals — health, sanity, stamina — are human biological and psychological
state, shaped by environmental stressors: light levels, temperature, ambient sound, proximity to supernatural entities.
They form a coherent bounded context.

Ghost resilience is a fundamentally different simulation: a combat mechanic (`1.0 - repellent_hits as f32 / 1000.0`)
computed on demand with no separate simulation loop. If ghost resilience ever needs its own driven simulation (e.g.,
multi-stage weakening, environmental modulation), that belongs in a bounded context extension of the ghost domain — not
in this crate. Mixing them would force `unvitals-plugin` to import both `unplayer-core` and `unghost-core` as actor
owners, coupling two separate actor domains. The current `apply_ghost_proximity_damage` import of `unghost-core` is
correct because the _player's_ health is being modulated by observable ghost state — the ownership direction is right.

**Vitals = human biological state. Keep the scope as it is.**

**Notes — data layer created 2026-03-22**

`unvitals-core` (T1·1c) was created as recommended. `PlayerVitals` and `Stamina` were migrated from `unplayer-core` into
`unvitals-core`. All consumers now import `unvitals-core` instead of `unplayer-core` for these types. One structural
issue was introduced: `unvitals-core` imports `unreplicon-core` (T2), making it the first T1 `-core` crate with a T2
dependency — a new violation that must be resolved (see violations above).

The original migration table below is now historical context; the migration has been completed.

| Type           | What it is                                                                             | Previous location | Current location   |
| -------------- | -------------------------------------------------------------------------------------- | ----------------- | ------------------ |
| `PlayerVitals` | Component: `crazyness`, `sanity`, `mean_sound`, `health`                               | `unplayer-core`   | `unvitals-core` ✅ |
| `Stamina`      | Component: `current`, `max`, `running`, `exhausted`, `depletion_rate`, `recovery_rate` | `unplayer-core`   | `unvitals-core` ✅ |

As long as these components remain in `unplayer-core`, every crate that needs to read a player's health or sanity must
import `unplayer-core` — a large actor-domain crate carrying much more than just vitals. Moving them to `unvitals-core`
would not break any consumer (just an import path change), but would make the vitals bounded context visible and would
allow `unplayer-core` to shed two large component definitions.

`PlayerVitals` is currently read by at least eight crates: `unvitals-plugin`, `unghost-plugin`, `unplayer-plugin`,
`ungearitems-plugin`, `unlocomotion-plugin`, `unreplicon-plugin`, and the classic-mode crates. All of them would update
their import to `unvitals-core` with no logical change.

**The correct target shape:**

1. Create `unvitals-core` (T1·1c). Migrate `PlayerVitals` and `Stamina` from `unplayer-core` into it. `unplayer-core`
   may import `unvitals-core` if its component bundle needs to reference vitals at construction time.

2. Move `PlayerDiedEvent` from `unreplicon-core` to `unvitals-core`. The replication layer in `unreplicon-plugin` would
   observe the domain event and broadcast it over the network — the correct direction (T2 reads T1 events, not the other
   way around).

3. Extract three foreign systems from the plugin:
   - `update_damage_vignette_color` → T4 UI plugin polling `PlayerVitals` component.
   - `record_death_to_profile` → T3 observer reacting to `PlayerDiedEvent`.
   - `sync_client_reported_sanity` → T2 replication system in `unreplicon-plugin`.

**Notes — `undifficulty-core`:**

Both crates pass tier compliance cleanly. The pattern is correct: `DifficultySettings` is a trait implemented for the
`Difficulty` enum that gives every domain a single call-site for its difficulty-scaled parameters. Every consuming
plugin queries `Res<CurrentDifficulty>` and calls one method (`ghost_speed()`, `sanity_drain_rate()`,
`ambient_temperature()`, etc.). No consumer needs to know the numeric tables; they live here and here alone.

The old stale audit recommended: "The giant DifficultyStruct probably should be removed eventually, and replaced with
traits." **That refactor has already been completed.** The trait-based approach is entirely in place.

**Content misplacement (does not affect dep-compliance):**

1. **The `Difficulty` enum lives in `untypes-core`, not here.** `difficulty_impl.rs` implements
   `DifficultySettings for Difficulty`, but the enum itself is defined in `untypes-core::difficulty`. The canonical home
   for the enum is this crate. Every crate that wants just the enum type imports `untypes-core`; every crate that wants
   the settings API imports `undifficulty-core`. These should be one import. This was already flagged in the
   `untypes-core` audit as the most egregious misplacement in that crate: "already owned by `undifficulty-core`" and "❌
   belongs in T1·1c."

2. **`DifficultySelectionState` is application state, not domain data.** `difficulty_state.rs` defines a `Resource` with
   `selected_difficulty: Difficulty`, `selected_map_idx: usize`, and `state_entered_at: Instant`. This tracks which
   difficulty and map the player is looking at on the pre-mission selection screen, and how long they have been there.
   That is selection-screen navigation state — it belongs in T2 (selection screen orchestration) or the T4 crate
   managing that screen. It landed in `-core` because `Difficulty` types are here, making it the path of least
   resistance. Note that `undifficulty-plugin` does **not** register `DifficultySelectionState` — that resource must be
   initialized elsewhere; its definition should follow it there.

**Notes — `undifficulty-plugin`:**

The plugin is minimal by design: it calls `app.init_resource::<CurrentDifficulty>()` and nothing else. This is not a
structural weakness. The domain's value is entirely in the `-core` (the trait, its implementation, and the resource
wrapper); the plugin's job is simply to bring that resource into the ECS world. A one-liner plugin is acceptable when
the bounded context is well-scoped.

**Domain completeness:**

Yes — this is a complete, functional domain that is actively reducing complexity across the workspace.

The `DifficultySettings` trait covers ~25 gameplay parameters across six concern categories: ghost behavior (speed, hunt
duration, cooldown, aggression, provocation radius, anger rates), environment (ambient temperature, spread speed,
lighting gamma), player vitals (max recoverable sanity, drain rates, health recovery, movement speed), equipment
(evidence visibility, sensitivity, repellent crafting limit), and UI/scoring (van auto-open, score multiplier, display
strings). Without this domain, every one of those values would be scattered as magic numbers or duplicated constants at
each call site. Instead, each consuming domain (`unthermal-plugin`, `unlight-plugin`, `unghost-plugin`,
`unvitals-plugin`, `ungearitems-plugin`, `unlocomotion-plugin`) reads a single resource and makes one trait call.

The one outstanding structural gap is the `Difficulty` enum's location. Moving it from `untypes-core` into
`undifficulty-core` would complete the domain and collapse two imports into one for all consumers.

**What the domain is not doing — and correctly so:**

There is no runtime difficulty mutation mechanism. `CurrentDifficulty` is set once at mission start and read throughout
the mission. If the game later needs adaptive difficulty, time-based escalation, or per-player handicaps, the domain has
a clear extension surface here. The current design is not blocking that evolution.

#### 3. Information Hiding

1. **`TruckUIButton` color methods in `-core`.** `border_color()`, `background_color()`, and `text_color()` compute
   `Color` from `Interaction` state and button disability. This is T4 presentation logic embedded in a T1 data
   component. The component's state fields (`status`, `class`, `hold_timer`, etc.) are legitimate domain data; the
   color-computation methods are not. The correct fix is to move the three methods into the plugin system that reads
   `TruckUIButton` and updates `BorderColor`/`BackgroundColor` components directly — systems that already exist in
   `journal.rs`'s `button_system`.

2. **`TruckTab` presentation methods in the plugin.** `text_color()`, `bg_color()`, and `font_size()` are presentation
   decisions on a component that lives inside the plugin. This is acceptable — it is not leaking into a `-core`. No fix
   required.

3. **`JOURNAL_HINT_THRESHOLD = 3` and `HIGH_CLARITY_THRESHOLD = 0.75` constants.** These are baked into
   `journal_blinking_system.rs` and `journal.rs`. The threshold of acknowledging an evidence hint 3 times before the
   blink stops is a pedagogical/cognitive rule that belongs conceptually in the walkie or profile domain — whichever
   domain owns "how many times has the player been exposed to this hint". Duplicated in two places: defined in
   `journal_blinking_system.rs` as `pub(crate) const`, then redefined inline in `button_system` as a local `const`.

4. **Audio file paths hardcoded in domain logic systems.** `hold_button_system` spawns
   `"sounds/fadein-progress-1000ms.ogg"` and `truckui_event_handle` spawns `"sounds/effects-dingdingding.ogg"`.
   Embedding asset paths in a T1 domain handler couples the domain logic to T4 audio assets.

5. **`update_journal_ghost_blinking_system` encodes cheat-assist logic.** The system reads `GhostSprite.class` (the
   actual ghost type) to verify that the player's guess matches the real answer, then only blinks when the evidence
   uniquely identifies the correct ghost. This gameplay hint policy — "blink when you've correctly narrowed it to one" —
   belongs in the ghost or walkie domain as a pushed signal, not computed inline by querying the ghost entity's private
   type.

6. **`update_sanity` hardcodes "Player 1".** The format string `"Player 1:\n  {:.0}% Sanity"` is fixed. In any
   multiplayer scenario with multiple local players, this is incorrect.

7. **State-mutation methods in `-core`: `TruckUIButton::pressed()` and `toggle_discard()`.** These methods mutate the
   button's `status` field and return a `TruckUIEvent`. A `-core` component should hold data; state transitions and
   event generation are Bevy system responsibilities. `pressed()` encodes the toggle cycle (`Off → Pressed → Off`,
   `Pressed → Off`) and returns the domain event — this is game logic embedded in a struct method. The same applies to
   `RepellentCraftTracker::craft()`, which enforces the limit and mutates `crafted_count`. These belong in plugin
   systems, not in component `impl` blocks.

8. **Ghost deduction math encoded inline in `button_system`.** The system computes `possible_ghosts` by iterating all
   ghost types and applying `ghost_ev.is_superset(&gg.evidences_found) && ghost_ev.is_disjoint(&gg.evidences_missing)`
   inline. This set-arithmetic is the core deduction algorithm of the ghost domain — it determines which ghosts are
   still compatible with the evidence. `GhostGuess` (owned by `unghost`) should maintain a
   `valid_ghosts: Vec<GhostType>` derived field that is updated by a ghost-domain system. The truck UI should read that
   pre-computed list to en/disable buttons, not re-derive it.

#### 5. Marker-Gated Write Rule

Entity-class markers in this codebase: `MainPlayer`, `GhostSprite`, `MapTileMarker`, etc.

**Violations found:**

1. **`on_enter_truck`** — `Query<Entity, (With<MainPlayer>, Without<InTruck>)>` → inserts
   `Hiding { hiding_spot: None }`. `Hiding` is a player-domain component (`unplayer_core::components::Hiding`).
   Inserting it on entities filtered by `With<MainPlayer>` is a write through a foreign entity-class marker. The truck
   domain should emit a domain event (or trigger an observer) signalling that the player entered the truck; the player
   domain should respond by managing `Hiding`.

2. **`on_exit_truck`** — `Query<Entity, (With<MainPlayer>, With<InTruck>)>` → removes `Hiding`. Same violation; removing
   a player-domain component from player entities belongs in the player domain.

3. **`truckui_event_handle`** — `Query<(&PlayerSprite, &mut PlayerGear), With<MainPlayer>>` — writes `PlayerGear` (a
   player-domain component) on entities filtered by `With<MainPlayer>`. The CraftRepellent branch also assigns
   `NetworkId` and `Replicated` to gear entities. Modifying `PlayerGear` and managing replication identity on player
   entities from the truck plugin is a direct write through a foreign entity-class marker. The correct pattern: the
   truck emits a `CraftRepellentConfirmed { ghost_type }` domain event; the gear/player domain consumes it and mutates
   `PlayerGear`.

4. **`button_clicked` in `loadoutui.rs`** — obtains `Query<(&PlayerSprite, &mut PlayerGear, Has<MainPlayer>), ...>` and
   directly mutates `p_gear.left_hand`, `p_gear.right_hand`, and `p_gear.inventory`. On the `Van` branch (equipment
   pickup), it also spawns a gear entity and inserts `NetworkId`, `Replicated`, `Owner`, and `LocallyOwned` directly via
   `commands`. This combines a marker-gated write on a player entity with illegal gear entity spawning from inside the
   truck domain. The `Van` branch in particular mirrors the same pattern as `craft_repellent.rs`: full gear lifecycle
   management performed outside the gear domain.

**Read-only foreign marker use (not violations):**

- `update_sanity`: `Query<&PlayerVitals, With<MainPlayer>>` — reads only. ✅
- `update_evidence_ui`: `Query<(&PlayerSprite, &PlayerGear), With<MainPlayer>>` — reads only. ✅
- `keyboard_evidence`: `Query<(&PlayerInputMapping, &PlayerGear), With<MainPlayer>>` — reads only (but the system has an
  authority-gated `GhostGuess` write; that is a TDA/membership violation, not a marker-gated write violation).
- `update_journal_ghost_blinking_system`: `Query<&GhostSprite>` — reads only. ✅

#### 8. Defensive Logging

Per the defensive logging rule: every code path that "should not happen" must log. Silent fallthrough on entity lookups
that are expected to succeed is forbidden.

1. **`craft_repellent.rs` — silent `return false` on a guaranteed component.** After locating a specific entity by
   `GearKind::RepellentFlask`, the function calls `q_repellent.get_mut(entity)` to access its `RepellentFlask`
   component. If that lookup fails, it falls through to `return false` with no log entry. At that point the player has
   already interacted with the button and the animation has played, but nothing was crafted. Because the entity was
   confirmed to be a flask by its `GearKind`, missing the `RepellentFlask` component means the entity is structurally
   broken. This must be `error!` — the game state is known inconsistent: the crafting was accepted but cannot complete.

2. **`journal_blinking_system.rs` — `ghost_sprite_query.single().ok()` swallows spawn failures.** This runs inside
   `GameState::Truck` (an active mission). There must be exactly one `GhostSprite`. The `.single().ok()` call silently
   returns `None` for both "zero ghosts" (spawn failure) and "two ghosts" (replication or map bug), causing all ghost
   button hints to silently stop working. Should match on `QuerySingleError` and emit `error!` for either failure case,
   since the mission is running without a valid ghost entity.

3. **`truck_ui_systems.rs` — `update_craft_button_text` child search with no fallback log.** The system searches button
   children for the first `Text` node to update the remaining-crafts display:

   ```rust
   for &child in children {
       if let Ok(mut text) = q_text.get_mut(child) {
           // update text
           break;
       }
   }
   ```

   If no `Text` child is found (e.g. after a UI hierarchy change during refactoring), the button silently shows stale
   text with no diagnostic. Should emit `warn!` if the loop completes without finding the text node, since the UI tree
   invariant is violated.

4. **`loadoutui.rs` — `.ok().unwrap_or(GearKind::None)` on inventory entities.** Multiple sites use:
   ```rust
   entity.and_then(|e| q_gearkind.get(e).ok()).cloned().unwrap_or(GearKind::None)
   ```
   on entities taken directly from `p_gear.left_hand`, `p_gear.right_hand`, and `p_gear.inventory`. Every gear entity in
   those slots must have a `GearKind` component — it is the entity's class identity. If it is missing, the slot renders
   as blank and the player cannot interact with it; meanwhile no diagnostic is emitted. This should be `warn!` on a
   `None` result for any `Some(entity)` that lacks `GearKind`, since it indicates the gear spawner produced a
   structurally incomplete entity.

#### Summary

**Domain completeness** is the primary structural failure. The ghost domain's principal resource (`GhostGuess`) is
registered and lifecycle-managed by the truck plugin. The walkie domain's state (`WalkiePlay`) is mutated by systems in
the truck plugin. These cross-domain ownership leaks are the root cause of the deletable-silo cascades.

**TDA violations** are the second tier of failures. The journal blinking systems pull data from three foreign domains to
compute presentation signals those domains should be pushing. The button system and keyboard handler are direct writers
into the ghost domain's resource. The craft repellent handler is a direct writer into the player domain's gear state.

**Marker-gated write violations** (`on_enter_truck`, `on_exit_truck`, `truckui_event_handle`, `button_clicked`) expose
where the truck domain is managing the lifecycle of player-domain components and gear entities. Each should be replaced
with an emitted truck-domain event consumed by the respective owning domain.

**Defensive logging** has four confirmed violations. The most dangerous is in `craft_repellent.rs`: a crafting operation
that the player has already triggered silently fails and returns `false` with no log, masking potential entity
corruption. The `single().ok()` pattern in the ghost blinking system masks broken mission state. Both must be `error!`
paths.

**The overall pattern:** `untruck-plugin` is a vertical monolith covering T1 mechanics, T2 application flow, T3
persistence, and T4 UI presentation in a single plugin. The correct split is:

1. `untruck-core` retains: `InTruck`, `TruckGear`, `RepellentCraftTracker`, `ForceDiscardEvidenceEvent`. UI types move
   to the T4 UI plugin.
2. `untruck-plugin` retains only: `InTruck` lifecycle (minus `Hiding` writes), van gear spawning, repellent tracker
   init/reset, and a `CraftRepellentConfirmed` event emission. It imports T0 + T1 only and becomes a true thin T1
   mechanics plugin.
3. A new `untruck-ui-plugin` (T4·4c) receives: all UI layout/rendering, journal button interaction, hold-button
   mechanic, evidence UI, sanity display, sensors, tab system.
4. Journal network routing (`RequestJournalEvidenceToggle`, `RequestJournalGhostToggle`) moves to `unreplicon-plugin` or
   a dedicated T2 observer.
5. `GhostGuess` registration and reset moves to `unghost-plugin` (ghost domain).
6. `WalkiePlay.clear_evidence_hint()` call moves to `unwalkie-plugin` observing a truck-domain event.
7. `Hiding` insertion/removal on player entities moves to `unplayer-plugin`, triggered by a truck-domain event.
8. `hydration_van_entry_system` moves to a behavior/map-setup system (belongs in `unbehavior` or equivalent).

Until that restructuring, `unclassic-mode-ui-plugin` (T4) is the least-wrong home for the truck's UI systems.

**Content observations in `unwalkie-core` (no tier violations):**

1. **`WalkiePlay::set()` embeds the scheduling algorithm.** The method contains the full priority gating, timing
   constraints, cross-mission repeat suppression, and dice-roll logic. Per project convention, complex behavior belongs
   in plugin systems, not in resource methods. The resource should be a passive data holder; the scheduler logic should
   be a system in the plugin. This is a convention violation, not a tier violation.

2. **`generated/` is static content compiled into the binary.** Voice lines are Rust arrays of `VoiceLineData` structs.
   Content changes require a recompile. The `VoiceLineData` struct is already `Serialize`/`Deserialize` and the on-disk
   OGG files already have a JSON manifest alongside them — loading the manifest at runtime would decouple voice line
   authoring from compilation without changing the rest of the domain. No tier violation, but a content-over-code
   observation.

3. **`PotentialIDTimer` (from `unghost-core`) is initialized by `UnhaunterWalkieCorePlugin`.** A ghost-domain resource
   is registered by the walkie plugin. The expected pattern is each domain's plugin initializes its own resources.
   `PotentialIDTimer` initialization should move to `unghost-plugin`; `unwalkie-plugin` should only read it.

4. **`WalkieEvent` carries domain types as payload.** `WalkieEvent::GearExplanation(GearKind)`,
   `WalkieEvent::ChapterIntro(Difficulty)`, and `WalkieEvent::IncorrectRepellentHint(Evidence)` embed gear, difficulty,
   and ghost-domain types in the event enum. These are tier-compliant (all T0–T1), but they couple the event vocabulary
   to three other domains at compile time.

**Notes — `unwalkie-plugin`:**

`plugin.rs` defines both `UnhaunterWalkieCorePlugin` (headless: registers event, initializes `WalkiePlay`,

implementations in `plugin.rs` violates the project convention of one `Plugin` per file. The headless/client split is
the correct pattern; the co-location in one file is not.

**Domain completeness — the user's main concern:**

This is **not a dumping ground.** The walkie-talkie coaching system is a genuine bounded context with a clear
responsibility: observe player behavior across all gameplay domains, apply priority/timing scheduling, deliver
contextually appropriate voice coaching, and track cross-mission history so advice does not become repetitive.

The domain owns a coherent end-to-end pipeline:

```
Game state observations (16 trigger modules)
    → WalkiePlay scheduler (priority / timing / repeat suppression)
        → Voice line selection (generated/ catalog via ConceptTrait)
            → Audio playback + subtitle display (presentation side)
                → Cross-mission history (profile persistence)
```

The trigger system is broad because the walkie coach legitimately observes all gameplay domains — that breadth is the
feature. The wide dep profile of `unwalkie-plugin` reflects genuinely wide observation scope, not a design smell.

The structural gap is **tier layering**: the pipeline spans T1 (coaching AI, scheduling) through T3 (persistence) to T4
(audio, UI, rendering), and these are currently collapsed into one plugin. The domain is coherent; the plugin's tier
boundary is wrong.

**The correct target shape:**

- `unwalkie-core` retains: `WalkieEvent`, `WalkiePlay`, `WalkieTalkingEvent`, `generated/` content, `ConceptTrait`. Move
  the scheduling algorithm out of `WalkiePlay::set()` into a dedicated system.

- `unwalkie-plugin` retains: all 16 trigger modules + `state_tracking`. Imports only T0–T1. Contains one `Plugin` struct
  per project convention (split across two files if needed for headless/client separation).

- A new `unwalkie-audio-plugin` (T4·4b or T4·4c) receives: `walkie_talk` (audio playback, subtitle update, hint
  dispatch), `focus_ring_showcase_system`, `update_focus_rings`. Reacts to `WalkieTalkingEvent`.

- Cross-mission persistence (`walkie_stats`, `walkie_level_stats`) moves to a T3 observer in `unprofile-plugin` or a
  dedicated module at T3.

- `PotentialIDTimer` initialization moves to `unghost-plugin`.
