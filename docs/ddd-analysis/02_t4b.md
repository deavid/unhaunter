## Tier 4 · Presentation (Client-Side Only)

Rendering, audio, UI. May import everything below. Must never be imported by T0–T3.

### 4b · Audio

Crates: `unaudiobg-core`, `unaudiobg-plugin`, `unaudiospatial-core`, `unaudiospatial-plugin`

---

### `unaudiobg-core`

**Audit date:** 2026-03-20 **Assigned tier:** T4·4b (Audio) **Declared role:** Ambient and background music data

#### Dependencies

No internal game crate dependencies. External: `bevy` only.

#### Contents

Four source files under `src/`: `components.rs`, `events.rs`, `mute.rs`, `smooth.rs`.

**`components.rs`** — `SoundType` enum (`BackgroundHouse`, `BackgroundStreet`, `HeartBeat`, `Insane`); `GameSound`
component (`class: SoundType`) marking entities that play a looping background audio track.

**`events.rs`** — `AmbientSoundMuteEvent` (`Message`-derived): carries `fade_out_duration`, `mute_duration`,
`fade_in_duration`, and `reduction_factor` (f32, where 3.0 means 1/3 volume). Default values are 3500 ms / 2500 ms / 15
s / 3.0.

**`mute.rs`** — `ActiveMute` (plain struct): wraps a `AmbientSoundMuteEvent` config plus elapsed `Duration`, with a
`current_multiplier()` method that interpolates fade-out → mute → fade-in phases. `AmbientMuteController` (Resource):
holds `Vec<ActiveMute>`, combines multipliers multiplicatively via `current_multiplier()`.

**`smooth.rs`** — `smooth_volume_db()` free function: converts current and target linear volumes to dB, advances by up
to `db_per_second * dt_secs`, returns the new linear value. A pure math utility with no Bevy dependencies beyond the
type system.

#### Tier Assessment

The crate carries only `bevy` as an external dependency and defines no game logic — it is pure data types and a math
helper. This placement at T4·4b is structurally correct for its downstream coupling (it defines the component that marks
Bevy audio entities).

However, **`AmbientSoundMuteEvent`** is pure configuration data (four floats / durations) with no coupling to the audio
engine itself. Domain code that wants to suppress ambient audio during key events (e.g., ghost hunts) must import this
T4 crate to send that event, which creates a T1→T4 dependency. See Violations.

**Reverse consumers:**

- `unaudiobg-plugin` (T4·4b) — legitimate
- `unghost-plugin` (T1·1b) — **T1→T4 violation** (see below)

#### Violations

**🔴 T1→T4 (×1): `unghost-plugin` imports `unaudiobg-core`**

`unghost-plugin` imports `unaudiobg-core` to send `AmbientSoundMuteEvent` (to reduce ambient audio during ghost hunting
phases). Domain code must not depend on presentation crates. `AmbientSoundMuteEvent` contains only `Duration` and `f32`
fields — it has no coupling to Bevy's audio engine and could be moved to T0 or T1.

#### Recommendation

Extract `AmbientSoundMuteEvent` into a dedicated T0 event type (e.g., as part of a `unmission-core` lifecycle event, or
its own thin crate). `GameSound`, `SoundType`, `ActiveMute`, and `AmbientMuteController` are audio-infrastructure types
and should remain in `unaudiobg-core` (T4). `smooth_volume_db` is a pure math function and could also live at T0, but
its impact is low since only `unaudiobg-plugin` uses it.

### `unaudiobg-plugin`

**Audit date:** 2026-03-20 **Assigned tier:** T4·4b (Audio) **Declared role:** Ambient and background music plugin

#### Dependencies

Internal: `unaudiobg-core` (T4·4b), `unsettings-core` (T3·3b), `unplayer-core` (T1·1b), `unboard-core` (T1·1a),
`unspatial-core` (T0), `untypes-core` (T0). External: `bevy`, `bevy-persistent`, `ndarray`.

All internal dependencies are T0, T1, T3, or T4 peer — correct downward direction for a T4 plugin.

#### Contents

Systems split across `systems/spawn.rs`, `systems/volume.rs`, `systems/mute.rs`, `systems/menu_music.rs`.

**`spawn.rs`** — `spawn_background_tracks`: spawns four looping `AudioPlayer` entities at startup (house ambient, street
ambient, heartbeat, insanity track), all at essentially zero volume. `silence_background_tracks`: sets all `GameSound`
audio sinks to volume zero on `OnExit(AppState::InGame)`.

**`volume.rs`** — `update_ambient_sound_volumes`: the core volume-driving system. Samples a 64×64 window of
`VisibilityData::visibility_field` (ndarray) around the player's board position, weighted by indoor/outdoor tile
topology, to derive `house_volume` and `street_volume`. Derives `heartbeat_volume` from `PlayerVitals.health` (below 50%
→ analog curve) and `insane_volume` from `PlayerVitals.sanity` (below 70% → analog curve). Applies master / ambient
volume settings, global volume, and the `AmbientMuteController` multiplier, then uses `smooth_volume_db` at 10 dB/s to
drive each `AudioSink`.

**`mute.rs`** — `process_ambient_mute_events`: reads incoming `AmbientSoundMuteEvent` messages, pushes them as
`ActiveMute` entries into `AmbientMuteController`, advances all elapsed timers, and removes expired entries.

**`menu_music.rs`** — `manage_title_song` + `despawn_sound`: manages a looping `MenuSound` entity for the title screen.
Spawns when not in `AppState::InGame`, sets `despawn = true` when entering the game; `despawn_sound` does a dB-smooth
fade-out then `despawn()`.

#### Tier Assessment

Correctly placed at T4·4b. All systems deal directly with Bevy audio entities (`AudioPlayer`, `AudioSink`,
`PlaybackSettings`). Imports are limited to T0–T4 with no upward violations. No domain logic beyond reading health and
sanity ratios to drive volume curves.

#### Violations

None.

### `unaudiospatial-core`

**Audit date:** 2026-03-20 **Assigned tier:** T4·4b (Audio) **Declared role:** Positional SFX data

#### Dependencies

Internal: `unspatial-core` (T0). External: `bevy`.

#### Contents

Two source files: `events.rs`, `emitter.rs`.

**`events.rs`** — `SoundEvent` (`Message + Event`, `Debug`, `Clone`): carries `sound_file: String`, `volume: f32`,
`position: Option<Position>`, and `broadcast: bool` (multiplayer flag). This is the sole inter-crate bus for all
one-shot positional sound effects in the game.

**`emitter.rs`** — `AudioEmitter` (`SystemParam`): a convenience bundle of `AssetServer`, `Time`, and
`MessageWriter<SoundEvent>`. Four public methods cover the common dispatch patterns:

- `play_audio` — positioned, broadcast
- `play_audio_nopos` — no position, broadcast
- `play_audio_local` — positioned, no broadcast
- `play_audio_nopos_local` — no position, no broadcast

All four delegate to a private `play_audio_ex` which guards against empty file paths.

#### Tier Assessment

The crate's only internal dependency is `unspatial-core` (T0) for the `Position` type. `SoundEvent` itself is pure data
— it contains no Bevy audio engine types, only a file-path string, a float volume, an optional position, and a bool
flag.

By placing `SoundEvent` and `AudioEmitter` in T4, every domain plugin that needs to emit a sound effect must import a T4
crate. This is the most impactful tier boundary issue in the audio subsystem: six T1 crates have an upward dependency on
`unaudiospatial-core`.

**Reverse consumers:**

- `unaudiospatial-plugin` (T4·4b) — legitimate
- `unlocomotion-plugin` (T1·1b) — **T1→T4 violation**
- `uninventory-plugin` (T1·1c) — **T1→T4 violation**
- `uninteraction-plugin` (T1·1c) — **T1→T4 violation**
- `unplayer-plugin` (T1·1b) — **T1→T4 violation**
- `unghost-plugin` (T1·1b) — **T1→T4 violation**
- `ungearitems-plugin` (T1·1c) — **T1→T4 violation**

#### Violations

**🔴 T1→T4 (×6): Six T1 domain plugins import `unaudiospatial-core`**

All six T1 crates import `unaudiospatial-core` to use `AudioEmitter` or to write `SoundEvent` directly. This is
structurally the same problem as with `unrender-std`: the event bus for audio side-effects was placed in a presentation
crate, forcing every gameplay plugin that triggers a sound to carry an upward dependency.

The root cause is that `SoundEvent`'s data has no audio-engine coupling — it is transferable to T0 (it only needs
`unspatial-core::position::Position`, which is already T0). If `SoundEvent` and `AudioEmitter` were extracted to a
dedicated T0 crate, all six T1 violations would be eliminated.

#### Recommendation

Extract `SoundEvent` and `AudioEmitter` into a new T0 crate (e.g., `unaudiospatial-types` or by adding an `audio` module
to an existing T0 signals/events crate). The module only needs `unspatial-core` (T0) and `bevy::prelude`— both already
available at T0. `unaudiospatial-core` would then re-export or simply be retired. `unaudiospatial-plugin` would import
from the T0 types crate instead.

### `unaudiospatial-plugin`

**Audit date:** 2026-03-20 **Assigned tier:** T4·4b (Audio) **Declared role:** Positional SFX plugin

#### Dependencies

Internal: `unaudiospatial-core` (T4·4b), `unspatial-core` (T0), `unsettings-core` (T3·3b), `untags-core` (T0),
`unmetrics-core` (T0), `untypes-core` (T0). External: `bevy`, `bevy-persistent`.

All internal deps are T0, T3, or T4 peer — correct for a T4 plugin.

#### Contents

Single system file `systems.rs`; a `metrics.rs` helper; `plugin.rs` registering both.

**`systems.rs`** — `spatial_audio_playback`: reads all `SoundEvent` messages per frame. For each event, resolves the
local player's `Position`, computes Euclidean distance to the sound origin, adjusts volume inversely (and additionally
reduces for `SoundOutput::Mono`), then spawns an `AudioPlayer<AudioSource>` entity with `PlaybackMode::Despawn`. If the
sound has a position and the output is not mono, enables Bevy's spatial audio (`spatial: true`,
`SpatialScale::new(0.005)`) and inserts a `Transform` driven by `perspective::to_screen_coord`. Includes a rate-limited
error log for non-finite player positions.

**`metrics.rs`** — Registers a `unaudiospatial/sound_playback` Bevy diagnostic (milliseconds) using
`unmetrics_core::metrics::SendMetric` for frame-time profiling of the playback system.

#### Tier Assessment

Correctly placed at T4·4b. All systems directly spawn and configure Bevy audio entities. Dependency direction is
strictly downward. No violations.

#### Violations

None.
