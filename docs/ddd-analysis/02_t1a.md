### unboard-core + unboard-plugin

- **Status:** CURRENT
- Audit date: 2026-03-20
- Declared tier: T1 · 1a · The Stage
- Pair: `unboard-core` / `unboard-plugin` (same tier: YES)
- Internal deps (`unboard-core`): `unspatial-core` (T0)
- Internal deps (`unboard-plugin`): `unboard-core` (T1), `unspatial-core` (T0), `untypes-core` (T0), `unbehavior`
  (T3·3a), `unrender-std` (T4·4a)
- Highest tier imported (`unboard-core`): T0
- Highest tier imported (`unboard-plugin`): **T4** (`unrender-std`)
- Tier compliance (`unboard-core`): PASS
- Tier compliance (`unboard-plugin`): **FAIL** — declared T1, imports T3 and T4

**Violations (`unboard-plugin`):**

1. Imports `unbehavior` (T3·3a). Used in `boardfield_update.rs` to query `&Behavior` on board entities when rebuilding
   collision data. `Behavior` is a Tiled map pipeline type — a T3 concern — and should not be visible from T1. The
   collision rebuild belongs either in a T3 crate that bridges Tiled behavior into domain types, or `Behavior` must be
   moved to a lower tier.

2. Imports `unrender-std` (T4·4a). Used as `unrender_std::utils::collision::rebuild_collision_data`. A collision rebuild
   function living inside a _rendering_ crate is a placement error: collision geometry is a domain concern (T1), not a
   rendering concern (T4). The function should live in `unboard-core` or `unboard-plugin` itself, removing the T4
   dependency entirely.

**On the T0 question — what could be extracted:**

The user asked whether part of `unboard-core` could be T0, on the grounds that the grid structure itself ("space") is
more fundamental than the things in it (collision, room state, entity tracking). This is conceptually correct, and there
is a small, clean extractable subset.

Content analysis by module:

| Module                                                                                     | External `un*` deps             | "Space" or "stuff in space"?              | T0 viable? |
| ------------------------------------------------------------------------------------------ | ------------------------------- | ----------------------------------------- | ---------- |
| `types/floor.rs` — `FloorLevelMapping`                                                     | none                            | ✅ Space — maps floor numbers to z-coords | ✅ Yes     |
| `components/chunk.rs` — `ChunkIterator`, `CellIterator`                                    | `unspatial-core::BoardPosition` | ✅ Space — pure grid partitioning math    | T0→T0 dep  |
| `types/fielddata.rs` — `CollisionFieldData`                                                | `unspatial-core::Orientation`   | ❌ Stuff (collision)                      | No (T1)    |
| `components/spawning.rs` — spawn point markers                                             | none                            | ❌ Stuff (game domain)                    | No (T1)    |
| `components/mapcolor.rs` — `MapColor`                                                      | none                            | ❌ Stuff (presentation)                   | No (T4)    |
| `components/physics.rs` — `ThermalEmitter`, `FluidEmitter`                                 | none                            | ❌ Stuff (simulation actors)              | No (T1)    |
| `resources/board_topology.rs` — `BoardTopology`, `BoardCollisionField`, `BoardEntityField` | `unspatial-core`                | ❌ Stuff (game state)                     | No (T1)    |
| `resources/roomdb.rs` — `RoomTopology`, `RoomStateMap`                                     | `unspatial-core`                | ❌ Stuff (runtime state)                  | No (T1)    |
| `resources/visibility_data.rs` — `VisibilityData`                                          | none                            | ❌ Stuff (runtime state)                  | No (T1)    |

The extractable surface is exactly: `FloorLevelMapping` (zero `un*` deps) and `ChunkIterator`/`CellIterator` (only dep
is `unspatial-core::BoardPosition`, which is already T0). Both are pure spatial coordinate math — they define how the
grid is structured, not what lives in it.

**The right home is `unspatial-core`, not a new crate.** `unspatial-core` is already the coordinate math library. Floor
numbering and chunk grid iteration are coordinate math. Absorbing them there requires no new crate, no rule change, and
no new `un*` import. Everything else stays in `unboard-core` at T1 where it belongs.

The T1 status of `unboard-core` is correct: `BoardTopology`, `RoomTopology`, `RoomStateMap` etc. are living game-world
state, not pure spatial primitives. `unboard-core` is the _base_ of T1·1a; being widely depended upon by other Stage
crates is expected and correct.

**Correct cleanup path:**

- Migrate `FloorLevelMapping`, `ChunkIterator`, and `CellIterator` (with chunk constants) from `unboard-core` into
  `unspatial-core`. This tightens the T0 boundary and makes the spatial toolkit self-contained.
- Move `rebuild_collision_data` from `unrender-std` into `unboard-plugin` (or `unboard-core` if it is pure data logic).
  Remove the `unrender-std` dep from `unboard-plugin`.
- Factor out what `unboard-plugin` needs from `Behavior`. Either: (a) move the collision-relevant subset of `Behavior`
  to a T1 crate (if it is genuinely domain data), or (b) move the rebuild responsibility to a T3 system that translates
  `Behavior` updates into domain events that `unboard-plugin` already understands.

### unthermal-core + unthermal-plugin

- **Status:** CURRENT
- Audit date: 2026-03-20
- Declared tier: T1 · 1a · The Stage
- Pair: `unthermal-core` / `unthermal-plugin` (same tier: YES)
- Internal deps (`unthermal-core`): none
- Internal deps (`unthermal-plugin`): `unthermal-core` (T1), `unboard-core` (T1), `unspatial-core` (T0),
  `unfoundation-core` (T0), `unmetrics-core` (T0), `untypes-core` (T0), `undifficulty-core` (T1), `unmapload-core`
  (T3·3a), `unbehavior` (T3·3a), `unsettings-core` (T3·3b)
- Highest tier imported (`unthermal-core`): T0 (external only: bevy, ndarray)
- Highest tier imported (`unthermal-plugin`): **T3** (`unmapload-core`, `unbehavior`, `unsettings-core`)
- Tier compliance (`unthermal-core`): PASS
- Tier compliance (`unthermal-plugin`): **FAIL** — declared T1, imports T3

**Notes — `unthermal-core`:**

Clean field data crate. `ThermalGrid` is a 3D array Resource holding temperature, activity, and connectivity scores per
tile plus a `TemperatureDiffusionConfig`. No `un*` dependencies. No content misplacement. Textbook T1·1a field data.

**Violations (`unthermal-plugin`):**

1. `unmapload-core` (T3·3a) — uses `MapGeometryInitializedEvent` and `LevelReadyEvent` to initialize and populate the
   thermal grid when a map loads. This is the same systemic T3 import seen in `unboard-plugin`. See systemic note below.

2. `unbehavior` (T3·3a) — queries `(&Position, &Behavior)` with `With<HeatEmitter>` to inject heat from Tiled-defined
   heat-emitting tiles. `HeatEmitter` is a Tiled behavior component. The simulation should only read domain components
   (`ThermalEmitter` already exists in `unboard-core`); the T3 layer should translate `Behavior` into `ThermalEmitter`
   values.

3. `unsettings-core` (T3·3b) — reads `VideoSettings.quality` for a performance budget (`quality_factor3`). This is a
   presentation/platform concern living in a domain simulation system. Quality-dependent budgets should be passed in as
   a domain resource or derived in a T2/T4 system.

- Audit date: 2026-03-20
- Declared tier: T1 · 1a · The Stage
- Pair: `unfog-core` / `unfog-plugin` (same tier: YES)
- Internal deps (`unfog-core`): `unspatial-core` (T0)
- Internal deps (`unfog-plugin`): `unfog-core` (T1), `unspatial-core` (T0), `unfoundation-core` (T0), `unboard-core`
  (T1), `unmetrics-core` (T0), `untypes-core` (T0), `unnoise-core` (T0), `unghost-core` (T1·1b), `unplayer-core`
  (T1·1b), `unmapload-core` (T3·3a), `unbehavior` (T3·3a), `unrender-std` (T4·4a), `unsettings-core` (T3·3b)

**Notes — `unfog-core`:**

Clean. `MiasmaGrid` (pressure + velocity field as `Array3`, plus per-room modifiers), `MiasmaConfig` (pure simulation
parameters), `MiasmaSprite` (particle component for visual representation). No violations. Well-structured T1·1a.

Note: `MiasmaSprite` is a presentation-adjacent component (it drives a sprite's circular motion, radius, phase, etc.).
It could arguably belong in a T4 rendering crate, but it contains no rendering types (no `Bevy` asset handles or
`Sprite` components), so it straddles the line. Keeping it here is acceptable for now.

**Violations (`unfog-plugin`):**

1. `unmapload-core` (T3·3a) — same systemic map-loading event issue.

2. `unbehavior` (T3·3a) — used in `initialize_miasma` when rebuilding collision data; queries `&Behavior` on map
   entities, same pattern as `unboard-plugin`.

3. `unrender-std` (T4·4a) — used for: `GameSprite`, `SpriteLayer`, `LightSensitive` (rendering components), and
   `rebuild_collision_data` (same function as seen in `unboard-plugin`). The miasma simulation spawns `MiasmaSprite`
   entities that carry rendering components. The particle spawning and rendering setup should live in a T4 crate; the
   simulation (field diffusion) should stay in `unfog-plugin`.

4. `unsettings-core` (T3·3b) — reads `VideoSettings` for quality budget, same issue as `unthermal-plugin`.

The T1·1b cross-deps (`unghost-core`, `unplayer-core`) are fine — the fog simulation is affected by the ghost's position
and player proximity, which are domain-level interactions within the same tier.

### unlight-core + unlight-plugin

- **Status:** CURRENT
- Audit date: 2026-03-20
- Declared tier: T1 · 1a · The Stage
- Pair: `unlight-core` / `unlight-plugin` (same tier: YES)
- Internal deps (`unlight-core`): `unspatial-core` (T0), `unbehavior` (T3·3a)
- Internal deps (`unlight-plugin`): `unlight-core` (T1), `unspatial-core` (T0), `unfoundation-core` (T0), `unboard-core`
  (T1), `unfog-core` (T1), `undifficulty-core` (T1), `unmetrics-core` (T0), `untypes-core` (T0), `ungear-core` (T1·1c),
  `unplayer-core` (T1·1b), `uninteraction-core` (T1·1c), `unbehavior` (T3·3a), `unmapload-core` (T3·3a), `unrender-std`
  (T4·4a), `unreplicon-core` (T2), `unui-core` (T4·4c), `unsettings-core` (T3·3b)
- Highest tier imported (`unlight-core`): **T3** (`unbehavior`)
- Highest tier imported (`unlight-plugin`): **T4** (`unrender-std`, `unui-core`)
- Tier compliance (`unlight-core`): **FAIL** — declared T1, a `-core` crate imports T3
- Tier compliance (`unlight-plugin`): **FAIL** — declared T1, imports T2, T3, and T4

**Notes — `unlight-core`:**

The field data types themselves are clean: `LightFieldData` (lux + rgb color + transmissivity + spectral bands),
`LightData` (visible/red/IR/UV intensities), `LightType`, `ExposureModel`, `PrebakedLightingData`, `LightGrid`.
`tonemapping.rs` is pure math (artistic tone-mapping, gamma calculation, color tint).

The violation is in `light_grid.rs`: `LightGrid` contains a method `has_power()` that queries `Query<&Behavior>` (T3·3a)
to check whether electrical breakers are on. A field data resource in a `-core` crate must not import T3 types. The fix
is to extract this method into the plugin, replacing it with a simpler domain component or a pre-computed flag (e.g.,
`LightGrid.power_on: bool`) that the plugin keeps updated.

**Violations (`unlight-plugin`) — ordered by severity:**

1. **T4 mixing** — `unrender-std` (T4·4a) and `unui-core` (T4·4c): The plugin is doing two different jobs. The lighting
   _simulation_ (computing `LightGrid` values via BFS wave propagation) is T1. The _application of lighting to sprites_
   (`apply_lighting_to_tiles_system`, `power_visuals`) is T4 — it reads `LightGrid` and writes to
   `MeshMaterial2d<CustomMaterial1>`, `Visibility`, sprite color, etc. These two responsibilities must be separated:
   simulation stays in `unlight-plugin`, sprite application moves to a T4 rendering crate (e.g., `unrender-plugin` or a
   new `unlight-render-plugin`).

2. **T3 deps** — `unmapload-core`, `unbehavior`, `unsettings-core`: same systemic issues as other Stage plugins.

3. **T2 dep** — `unreplicon-core`: uses `LocallyOwned` (an ownership/replication component) to restrict which entities
   receive lighting updates. Replication ownership is an application-layer concern (T2). The T1 simulation should apply
   to all entities; filtering by ownership belongs in T2 or in the T4 rendering side.

4. **Cross-field dep** — `unfog-core` (T1·1a): `unlight-plugin` reads miasma pressure to modulate alpha/visibility of
   sprites. This is a T1→T1 dependency and is tier-compliant. However it means the lighting plugin carries knowledge
   about fog, coupling two fields. As fields multiply and interact, a dedicated field-interaction layer (still T1 or T2)
   may be worth introducing rather than having every field plugin import every other field.

### Systemic note — T3 map-loading events in all Stage plugins

Every Stage plugin (`unthermal-plugin`, `unsoundfield-plugin`, `unfog-plugin`, `unlight-plugin`, `unboard-plugin`)
imports `unmapload-core` (T3·3a) for `MapGeometryInitializedEvent` and/or `LevelReadyEvent`. These events are domain
signals — "the map geometry is ready", "the level is ready to play" — but they live in the map-loading pipeline (T3)
because that is where they are emitted.

This creates a universal T1→T3 upward dependency across the entire Stage group. The correct fix is to move these two
events into a lower-tier crate — most naturally `unboard-core` (T1) or a new thin `unmission-events-core` (T1). The T3
map-loading pipeline would emit them; every Stage plugin would consume them from the lower-tier crate with no upward
dependency.

This is the highest-leverage single refactor available at T1.

### unnavigation-core

- **Status:** CURRENT
- Audit date: 2026-03-20
- Declared tier: T1 · 1a · The Stage
- Pair: `unnavigation-core` only — **no `-plugin` counterpart**
- Internal deps: `unspatial-core` (T0), `unboard-core` (T1)
- Highest tier imported: T1
- Tier compliance: PASS

**Who uses this crate:**

| Consumer          | Tier   | What it takes                                                                                |
| ----------------- | ------ | -------------------------------------------------------------------------------------------- |
| `unplayer-plugin` | T1·1b  | `Waypoint`, `WaypointQueue`, `WaypointOwner`, `WaypointType`, `Pathfinder`                   |
| `uninput-plugin`  | **T2** | `MoveToTarget`, `Waypoint`, `WaypointOwner`, `WaypointQueue` (clears them on keyboard input) |

**Notes — tier compliance:**

Dependency compliance is PASS: the crate only imports T0 and T1.

**Notes — structural problems:**

The crate passes the tier check but fails as a domain design on several axes.

**1. Algorithm in a `-core`.** `pathfinding.rs` contains a full hand-rolled A\* implementation, path smoothing, and
visibility checks. `collision_handler.rs` contains collision-response delta math. Both are exposed as Bevy `SystemParam`
structs (`Pathfinder`, `CollisionHandler`). `SystemParam` is Bevy infrastructure for systems — not for data. Logic and
system parameters must never live in a `-core`; they belong in a `-plugin`. The convention is violated here.

**2. No `-plugin` counterpart — the bounded context is split across foreign crates.** The pair rule requires a domain to
own both its data (`-core`) and its systems (`-plugin`). Navigation currently has no plugin; its systems are distributed
across other crates. Waypoint creation (mouse click → A\* path → spawn `Waypoint` entities) lives in `unplayer-plugin`.
Waypoint following (`Waypoint` → `PlayerInput.movement`) lives in `unplayer-plugin`. Waypoint clearing (keyboard
override) lives in `uninput-plugin` (T2).

Navigation as a service is not owned by navigation. It is a guest in the player and input domains.

**3. Visibility constraint ties the algorithm to one agent.** The A\* implementation gates walkability on
`VisibilityData` — tiles invisible to the _player_ are impassable. This is a game design decision baked directly into
the search loop. It means the same pathfinder cannot be used for ghost or NPC navigation without giving them a
`VisibilityData` component that follows the same semantics. The algorithm is effectively player-only.

**This is not a complete domain — it needs a deep revisit.**

`unnavigation-core` as it stands is a half-finished scaffolding for what should be a `locomotion planning` bounded
context. Locomotion planning is the service that answers: "given a desired destination (or interaction target) and an
agent's current state, produce a sequence of intermediate positions the movement system can execute." This spans:

- The pathfinding algorithm (currently in this crate, incorrectly as a `SystemParam`)
- The waypoint queue data model (currently here — correct placement)
- The request origination (mouse click → goal, currently in `unplayer-plugin`)
- The waypoint following loop (currently in `unplayer-plugin`)
- The cancellation on keyboard override (currently in `uninput-plugin`)
- The stair traversal logic (currently in `unplayer-plugin/systems/pathfinding.rs`)

All six responsibilities belong to one bounded context. Right now they are split across three crates in two different
tiers.

**The natural target shape** is `unnavigation-plugin` (T1·1a) that owns the full cycle end-to-end, exposed as a service
to consumers via ECS components/events: any entity with a `MoveToTarget` component gets a `WaypointQueue` computed and
maintained automatically, without `unplayer-plugin` knowing anything about pathfinding. The player plugin would only set
`MoveToTarget`; the navigation plugin would do the rest. Ghost and NPC movement could later use the same mechanism with
their own visibility or without it.

Until this revisit happens, the current split is the pragmatic status quo. No action that makes it _worse_ should be
taken; document findings and keep the path forward in mind.
