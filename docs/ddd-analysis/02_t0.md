# Crate Audit — T0 · Domain Kernel

> Part of the Unhaunter DDD audit. Index: [02_crate_audit.md](02_crate_audit.md)

---

## Tier 0 · Domain Kernel

Pure primitives: types, math, markers. Must have **zero internal game dependencies**. Any `un*` import in a T0 crate is
a violation by definition.

---

### untypes-core

- **Status:** CURRENT
- Audit date: 2026-03-20
- Declared tier: T0 · Domain Kernel
- Pair: `untypes-core` only — no `-plugin` counterpart (correct for T0)
- Internal deps: none
- Highest tier imported: T0 (external only: bevy, serde, strum, enum-iterator)
- Tier compliance: PASS

**Notes — Content misplacement (does not affect dep-compliance, but affects DDD health):**

`untypes-core` passes dependency compliance: it has no `un*` imports. However, several modules contain content that
semantically belongs in higher tiers. The crate is being used as a "shared types" escape hatch, letting higher-tier
concepts be accessed from anywhere without going through their proper domain owner.

| Module                                                        | Content                                                              | Verdict                                   |
| ------------------------------------------------------------- | -------------------------------------------------------------------- | ----------------------------------------- |
| `states.rs` — AppState, BootState, GameState, SimulationState | State machine signals used by every tier                             | ✅ T0 · keep                              |
| `states.rs` — MapHubState, LobbyScreen                        | Feature-specific screen states                                       | ❌ belongs in T2 / T4·4c                  |
| `difficulty.rs`                                               | `Difficulty` enum — already owned by `undifficulty-core`             | ❌ belongs in T1·1c                       |
| `roles.rs`                                                    | AuthorityRole, LocalPlayerRole, LobbyPresenceRole, DisconnectRequest | ❌ belongs in T2                          |
| `cli.rs`                                                      | CliOptions, CliNetMode resources + Bevy system functions             | ❌ belongs in T2 (Resource) + a `-plugin` |
| `platform.rs`                                                 | UI_SCALE, FONT_SCALE, ASPECT_RATIO, IS_WASM constants                | ❌ belongs in T4                          |
| `hydration.rs`                                                | HydrationStage marker for the map loading pipeline                   | ❌ belongs in T3·3a (`unmapload-core`)    |
| `utils.rs`                                                    | `find_assets_directory()` — filesystem I/O                           | ❌ belongs in T3                          |

`difficulty.rs` is the most egregious: `undifficulty-core` already exists as the canonical home, yet the enum lives here
too. Every crate that imports `Difficulty` from `untypes-core` instead of `undifficulty-core` bypasses the domain
boundary without the dependency graph catching it.

`cli.rs` contains Bevy system functions (`pub fn is_authority(cli: Res<CliOptions>) -> bool`). System functions must
never live in `-core` crates (only in plugins), let alone in a T0 kernel crate.

The four core state enums in `states.rs` are genuine T0 content and should stay. Everything else should be migrated to
its proper home when that code is next touched.

**Notes:**

`unspatial-core` is the cleanest T0 crate in the workspace. Every module is legitimate kernel-level spatial math.

| Module             | Content                                                                                        | Verdict |
| ------------------ | ---------------------------------------------------------------------------------------------- | ------- |
| `boardposition.rs` | `BoardPosition` (Component), `MapEntityFieldBPos`, `NeighborsIterator` — integer 3D grid types | ✅ T0   |
| `constants.rs`     | `EPSILON: f32`                                                                                 | ✅ T0   |
| `direction.rs`     | `Direction` (Component) with vector math ops                                                   | ✅ T0   |
| `lerp_position.rs` | `LerpPosition` (Component) for visual interpolation                                            | ✅ T0   |
| `orientation.rs`   | `Orientation` enum (XAxis/YAxis/Both/None)                                                     | ✅ T0   |
| `perspective.rs`   | `to_screen_coord`, `direction_to_screen_coord`, `screen_to_world` — isometric projection math  | ✅ T0   |

`perspective.rs` uses `Camera` and `GlobalTransform` as function parameters for `screen_to_world`, but this does not
make it a T4 concern. These are Bevy primitives available at all tiers, and the code itself is pure coordinate
transformation math that defines the game's spatial model. The rendering layer consumes it; it is not part of it.

No action needed. This crate is a textbook T0 domain kernel.

### untags-core

- **Status:** CURRENT
- Audit date: 2026-03-20
- Declared tier: T0 · Domain Kernel
- Pair: `untags-core` only — no `-plugin` counterpart (correct for T0)
- Internal deps: none
- Highest tier imported: T0 (external only: bevy, serde)
- Tier compliance: PASS

**Notes:**

| Module    | Content                                                         | Verdict       |
| --------- | --------------------------------------------------------------- | ------------- |
| `tags.rs` | PlayerTag, GhostTag, InteractableTag, GearTag, NpcTag, TruckTag | ✅ T0         |
| `game.rs` | GCameraArena, MCamera                                           | ⚠️ borderline |

`tags.rs` is the correct use of T0: shared marker components that let domains observe each other's entities without
importing each other's crates. This is exactly the ECS decoupling pattern this tier exists for.

`game.rs` contains two camera marker components (`GCameraArena`, `MCamera`). Originally each screen owned a camera
entity, tagged it, and destroyed it on exit. At some point both markers ended up here as a shared escape hatch.

**GCameraArena** is used by the following crates:

| Crate                                            | Tier   | Usage                                                                       |
| ------------------------------------------------ | ------ | --------------------------------------------------------------------------- |
| `unclassic-mode-render-plugin` / `ungame-plugin` | T4 / ? | Spawns and despawns the camera entity; inserts the marker                   |
| `unclassic-mode-gameplay-plugin`                 | T2     | Moves camera `Transform` to follow the player                               |
| `uninput-plugin`                                 | T2     | Queries `(&Camera, &GlobalTransform)` for screen-to-world projection        |
| `unplayer-plugin`                                | **T1** | Queries `(&Camera, &GlobalTransform)` for mouse-aim and waypoint projection |

The T1 usage (`unplayer-plugin`) is decisive: moving `GCameraArena` to T4 would create an upward dependency from T1. The
marker staying at T0 is therefore **architecturally correct** — it is the ECS cross-tier communication pattern working
as designed. A T4 entity carries a T0 marker; T1 can find it without importing T4.

However, two things are suspicious:

1. **T2 moves the camera.** `unclassic-mode-gameplay-plugin` mutates the camera's `Transform` to follow the player.
   Camera movement is a rendering/presentation concern and should live in a T4 crate, not a T2 gameplay crate.
2. **Code duplication.** Spawn/despawn logic is duplicated across `unclassic-mode-render-plugin` and `ungame-plugin`.
   The game camera behavior is complex enough (follows player, has its own `Direction` component) that it warrants a
   proper domain pair — something like `ungamecamera-core` / `ungamecamera-plugin` at T4.

**MCamera** is used only by `unmenu-plugin` (T4·4c) and `unhub-plugin` (T3·3c) — both just spawn and despawn it. This is
a pure lifecycle marker. Its placement at T0 is wider than needed (T3 would suffice), but harmless.

### unmetrics-core + unmetrics-plugin

- **Status:** CURRENT
- Audit date: 2026-03-20
- Declared tier: T0 · Domain Kernel (both)
- Pair: `unmetrics-core` / `unmetrics-plugin` (same declared tier: T0)
- Internal deps (`unmetrics-core`): none
- Internal deps (`unmetrics-plugin`): `unmetrics-core` (T0), `untypes-core` (T0), `unreplicon-core` (T2)
- Highest tier imported (`unmetrics-core`): T0 (external only: bevy, bevy_platform)
- Highest tier imported (`unmetrics-plugin`): **T2** (`unreplicon-core`)
- Tier compliance (`unmetrics-core`): PASS
- Tier compliance (`unmetrics-plugin`): **FAIL** — declared T0, imports T2

**Violations:**

1. `unmetrics-plugin` imports `unreplicon-core` (T2). A T0 crate must never import T2. The declared placement in
   `Cargo.toml` and `[workspace.members]` is wrong. The plugin belongs at **T2** based on its actual dependencies. use
   unreplicon_core::components::{LobbyInfo, ServerGamePhase}; It imports unreplicon-core because it wants to print
   debugs on lobby information and server game phase - that is correct but probably those concepts are to be extracted
   from unreplicon-core to another domain.

2. The pair is tier-split: `unmetrics-core` is genuine T0, `unmetrics-plugin` is effectively T2. This violates the rule
   that a `-core`/`-plugin` pair is one bounded context and must always share a tier.

3. `unmetrics-core/src/metrics.rs` contains the `receive_data` system function — a Bevy system that takes
   `ResMut<DiagnosticsStore>` and `Local<...>`. System functions must never live in `-core` crates; they belong in
   `-plugin` crates only. This should be moved to `unmetrics-plugin`.

4. `performance_report.rs` mutates game state (`game_next_state.set(GameState::Running)`) as a side effect of metrics
   collection. State correction logic is an application-layer concern (T2), not a diagnostic concern. It should either
   be removed from the plugin or acknowledged as the reason the pair belongs at T2.
   - [deavid]: This is the plugin doing two functions and this should be removed. It was for trying to repair an
     inconsistent state and also log it. However I have not observed that log ever, so we can just remove the mutation
     part and leave the log for now. This also means that we might want some kind of domain or thing to do state
     validation: to confirm every now and then (not every frame) that the current database is consistent with some
     rules.

**Correct placement:** move both to **T2** in `Cargo.toml` and `[workspace.members]`. Move `receive_data` out of
`unmetrics-core` and into the plugin.

[deavid]: Disagree. This is T0, and it needs to be enforced to be T0.
