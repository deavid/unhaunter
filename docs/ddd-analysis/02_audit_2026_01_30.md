# DDD Audit Report: January 30, 2026

**Auditor:** Gemini
**Date:** 2026-01-30
**Scope:** `unplayer-core`, `unmapload-plugin`, `ungear-core`, `ungearitems-plugin`

## 1. Executive Summary

The codebase shows strong adherence to the `*-core` (Data) vs `*-plugin` (Systems) split. However, significant "Semantic Leakage" remains, particularly where Core domains are aware of specific input devices, visual implementation details, and global game rules.

The most critical architectural debt is the **Map Loading Factory**, which acts as a "God Object" knowing every entity type in the game, preventing true modularity.

## 2. Domain Analysis

### A. The Player Domain (`unplayer-core`)

**Bounded Context:** The representation of the player character's state and statistics.

**Issues:**
1.  **Infrastructure Leakage:** `PlayerSprite` contains `pub controls: ControlKeys`. The concept of a "Player" is coupled to a specific keyboard mapping struct from `unsettings-core`.
    *   *Violation:* Domain entities should not know about input hardware.
    *   *Fix:* Move controls to a separate `PlayerInputMapping` component or system resource.
2.  **Logic in Data:** `PlayerSprite` contains methods like `sanity()` and `required_crazyness()` that embed game balance formulas (magic numbers `30.0`, `100.0`).
    *   *Violation:* Core data crates should be dumb. Logic belongs in systems.
    *   *Fix:* Move these calculations to `unplayer-plugin::systems::sanity`.

### B. The Map Loading Domain (`unmapload-plugin`)

**Bounded Context:** Parsing map files and spawning the initial game state.

**Issues:**
1.  **The "God Factory" Pattern:** `src/factory.rs` contains a massive `if/else` chain that checks for every possible entity type (`is_npc`, `is_switch`, `is_door`, etc.) and manually attaches components.
    *   *Violation:* Open-Closed Principle. To add a new entity, you must modify this central file.
    *   *Impact:* Modules like `unnpc` or `unghost` are not truly self-contained; they rely on `unmapload` knowing about them.
    *   *Fix:* Implement a **Registry Pattern**. Plugins should register a "Spawner" for a given Tiled Class string. `unmapload` should just look up the spawner and execute it.

### C. The Gear Domain (`ungear-core` & `ungearitems-plugin`)

**Bounded Context:** The inventory system and specific tools.

**Positives:**
*   `ungearitems-plugin` is well-structured, with each item having its own component file.

**Issues:**
1.  **The "God Enum":** `GearKind` in `ungear-core` lists every single item in the game.
    *   *Violation:* Centralized dependency. `ungear-core` must be recompiled whenever a new item is added.
2.  **Hardcoded Meaning:** `TryFrom<&GearKind> for Evidence` hardcodes the relationship between a tool (Thermometer) and a game rule (Freezing Temps).
    *   *Violation:* Domain coupling. A physical object's purpose is context-dependent. In a different game mode, a Thermometer might be a weapon.
3.  **Visual Leakage:** `ungear-core` contains references to `sprite_idx` and `gear_spritesheetA_48x48.png`.
    *   *Violation:* Data layer knows about rendering implementation.
    *   *Fix:* `ungear-core` should only define the *Identity* of the gear. `unrender-plugin` should map that Identity to a Sprite Index.

## 3. Recommendations

### Priority 1: The Input Decoupling
Refactor `PlayerSprite` to remove `ControlKeys`. Create a system that maps `ControlKeys` (Resource) -> `PlayerInput` (Component).

### Priority 2: The Map Registry
Convert `unmapload-plugin` to use a Registry pattern. This is a prerequisite for a true "Engine vs Game" split, as it allows the Game Mode to define what entities exist.

### Priority 3: Visual Purification
Remove `sprite_idx` and asset paths from `ungear-core`. Create a `GearVisuals` resource or system in `unrender-plugin` that maps `GearKind` -> `TextureAtlasIndex`.
