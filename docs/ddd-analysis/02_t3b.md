#### What `unsettings-core` actually contains

Six modules of pure configuration-value types:

| Module        | Contents                                                                                                                            |
| ------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| `audio.rs`    | `AudioSettings`, `AudioLevel` (0%–100% with quadratic `as_f32()`), `SoundOutput`, `AudioPositioning`, `FeedbackDelay`, `FeedbackEQ` |
| `video.rs`    | `VideoSettings`, `VideoQuality` (with `to_quality_factor*()` methods), `UpscaleFactorChoice`, `WindowSize`, `AspectRatio`, `Scale`  |
| `controls.rs` | `ControlKeys` — keyboard mapping struct with `WASD`, `ARROWS`, `IJKL`, `NONE` presets; fields are `KeyCode` (Bevy primitive)        |
| `game.rs`     | `GameplaySettings`, `MovementStyle`, `CameraControls`, `CharacterControls`                                                          |
| `profile.rs`  | `ProfileSettings` (display name + color), `ProfileColor`                                                                            |

None of these types import any internal game crates. Every field is either a primitive, a Bevy type (`KeyCode`,
`Resource`, `Reflect`), or a type defined in the same crate. The methods present (`as_f32()`, `to_ear_offset()`,
`to_quality_factor1/2/3()`, `factor()`) are pure math — no side effects, no external coupling.

---

#### Why T0 is the correct tier

**Zero internal game dependencies.** This is the defining T0 criterion. `unsettings-core` has no `un*` imports — it
depends only on external crates (`bevy`, `serde`, `strum`, `enum-iterator`). It qualifies structurally as T0.

**The types are consumed at T1, T2, and T4.** `MovementStyle` affects how the locomotion system (T1b) resolves player
input. `ControlKeys` maps keyboard events in `uninput-plugin` (T2). `AudioLevel.as_f32()` sets gain in the audio plugins
(T4b). `VideoQuality.to_quality_factor*()` informs the render pipeline (T4a). When types are consumed across all tiers,
they must be placed at the lowest tier — T0.

**The persistence mechanism is already separated.** `unsettings-plugin` (T3b) correctly handles reading and writing
these types to disk. The types themselves have no I/O logic: they are plain data structures decorated with `Serialize` /
`Deserialize` to make them serializable — exactly what T0 primitives look like.

**`ControlKeys` stores `KeyCode`.** `bevy::input::keyboard::KeyCode` is a Bevy primitive with no game logic dependency.
Storing it in a settings struct does not elevate the tier; it simply means the settings are expressed in Bevy's input
vocabulary, which T0 types are allowed to use.

---

#### Fix (completed 2026-03-21)

Reclassified `unsettings-core` from `# ── 3b: Persistence` to `# ── T0: Domain Kernel` in both `[workspace.members]` and
`[workspace.dependencies]` in `Cargo.toml`. No code changes required. After reclassification, all six T1 crates that
import it are importing a T0 crate — exactly what T1 crates are supposed to do. The T3b bucket is correct for
`unsettings-plugin` (which does the actual I/O).

### unsettings-plugin

- **Status:** CURRENT
- Audit date: 2026-03-20 (updated 2026-03-21)
- Declared tier: T3·3b · Persistence
- Pair: `unsettings-core` (T0) / `unsettings-plugin` (T3·3b) — intentional tier split; core is pure data (T0), plugin
  does I/O (T3)
- Internal deps: `unsettings-core` (now T0)
- External deps of note: `bevy-persistent`, `dirs`, `serde`
- Highest tier imported: T0
- Tier compliance: **PASS**

**What it does:**

`unsettings-plugin` registers five `Persistent<T>` resources at app startup — one for each settings struct defined in
`unsettings-core`:

```
gameplay_settings.ron  → GameplaySettings
video_settings.ron     → VideoSettings
audio_settings.ron     → AudioSettings
profile_settings.ron   → ProfileSettings
control_settings.ron   → ControlKeys
```

`bevy-persistent` handles the load-on-startup / save-on-change lifecycle. Files are placed under
`dirs::config_dir()/unhaunter-game/config/` (platform-native config directory, with `local/config/` as fallback). The
RON format used is `RonPrettyWithStructNames`, which gives human-readable, forward-compatible files. The plugin sets
`revertible(true)` and `revert_to_default_on_deserialization_errors(true)`, so corrupted settings files silently reset
to defaults rather than crashing.

**No violations.** The plugin imports only `unsettings-core` (now correctly T0) and external infrastructure crates. It
adds no game logic — pure persistence wiring.

#### What `unprofile-core` actually contains

```
ProgressionData      — bank balance, insurance deposit, XP points, player level
                       includes: calculate_player_level(), update_level(), get_level_progress(), update_deposit()
AchievementData      — expelled_first_ghost: bool
StatisticsData       — total_missions_completed, total_deaths, total_play_time_seconds
MapStatisticsData    — per-map stats with best_grade: Grade, best_score: i64
WalkieEventStats     — play_count, last_played_at_time
PlayerProfileData    — (Resource) aggregates all the above; also:
                       - installation_id: Uuid (device identity)
                       - map_statistics: HashMap<String, HashMap<Difficulty, MapStatisticsData>>
                       - walkie_event_stats: HashMap<String, WalkieEventStats>
                       - times_evidence_acknowledged_on_gear: HashMap<Evidence, u32>
                       - times_evidence_acknowledged_in_journal: HashMap<Evidence, u32>
                       - nickname_letter, nickname_attempt
RuntimeInstallationId — (Resource) wraps Uuid, populated at startup
```

`calculate_player_level()` implements the XP → level formula using a power curve:

```
(player_xp / 250 + 1)^(1/1.5)
```

This is domain game logic — a design decision about how quickly players level up. It lives in what is currently a
persistence-tier crate.

`update_deposit()` implements the insurance deposit mechanic: checks whether the bank balance is sufficient to cover a
deposit, moves money between bank and deposit slot, and returns an error string if the player cannot afford it. This is
financial game logic, not a persistence schema field.

The `times_evidence_acknowledged_*` maps use `Evidence` from `unghost-core` as keys — this is the ghost-investigation
domain intrinsic to the profile. The profile tracks how familiar a player is with each piece of ghost evidence.

---

#### Tier classification recommendation

`unprofile-core` contains two logically distinct concerns:

**Concern A — Cross-session player state (domain):** XP, progression level, bank balance, insurance deposit, evidence
acknowledgment cadence, walkie event exposure. These are gameplay state that persists across sessions. T1/T2 systems
query and mutate them during a mission. They are domain data, and the five T1 crates that import this crate are
importing it for this reason.

**Concern B — Persistence schema:** `installation_id`, `nickname_letter`, `nickname_attempt`, the serialization
annotations (`#[serde(deny_unknown_fields)]`, `#[serde(default)]`), `PlayerProfileData` as the serialisation root. These
are the save-file envelope — they carry the schema identity and deserialization safety concerns that properly belong at
T3.

The practical recommendation is to move `unprofile-core` to **T1·1c** (Mechanics — player progression and financial
state are gameplay verbs). The types it holds are used by gameplay systems, not only by persistence infrastructure.
`unprofile-plugin` (T3b) continues to handle the actual file I/O without importing anything higher than T1. This mirrors
exactly how `unsettings-core` is being reclassified to T0 while `unsettings-plugin` stays at T3b.

An alternative — a clean split — would define a thin `unprofile-schema` at T3b (the serialisation envelope only) and
promote `PlayerProfileData`'s gameplay fields into a new or existing T1 resource. That is more work for a similar
architectural benefit.

### unprofile-plugin

- **Status:** CURRENT
- Audit date: 2026-03-20
- Declared tier: T3·3b · Persistence
- Pair: `unprofile-core` / `unprofile-plugin` (same declared tier: YES)
- Internal deps: `unprofile-core` (T3b → recommendation: T1·1c), `untypes-core` (T0)
- External deps of note: `bevy-persistent`, `dirs`, `ron`, `uuid`
- Highest tier imported: T3b as declared (will become T1 after reclassification of `unprofile-core`)
- Tier compliance: **PASS** (as T3b, imports only T0 and same-tier `-core`)

**What it does:**

`unprofile-plugin` registers `Persistent<PlayerProfileData>` at app startup (RON format, platform config dir) and adds
two `Startup` systems:

1. **`initialize_installation_id`** — reads `CliOptions.installation_id_file` for an override UUID (used in CI /
   dedicated-server deployments), or generates a new `Uuid::new_v4()` if the stored installation ID is nil. Inserts
   `RuntimeInstallationId` as a resource.

2. **`recover_stuck_insurance_deposit`** — on startup, if `progression.insurance_deposit > 0`, returns the held deposit
   to the bank balance and persists. This handles the case where a previous session ended mid-transaction (e.g., crash
   after deducting deposit but before completing the mission cycle).

**On `recover_stuck_insurance_deposit`:** This system embeds financial game logic (the deposit recovery rule) inside a
persistence plugin. The rule expresses a game design decision: "a deposit that is still recorded at session start was
never completed — refund it unconditionally." In a strict hexagonal model this decision belongs in the T1/T2 domain,
triggered by a startup event, with the T3 plugin only providing the persisted data. In practice, the mechanic is so
tightly coupled to the startup/load lifecycle (it is meaningless outside the context of "we just loaded a saves file and
found an incomplete transaction") that keeping it in the persistence plugin is tolerable. Flag for review — not a hard
violation.

**`dev_tools.rs`** (debug + Linux only): writes a versioned `.ron` snapshot of `PlayerProfileData` to a fixtures
directory, then validates all existing snapshots against the current struct definition. This is a schema evolution guard
— it will fail at startup (in debug builds on Linux) if a previously written snapshot cannot be deserialized by the
current struct, catching accidental breaking changes to the save-file format. Excellent practice; no tier concern.

**No tier violations.** The plugin imports only `unprofile-core` (its own pair) and `untypes-core` (T0) from internal
crates. After `unprofile-core` is reclassified to T1·1c the plugin will be T3 importing T1 — correct direction.
