### `unrender-core`

**Audit date:** 2026-03-20 **Assigned tier:** T4·4a (Rendering) **Declared role:** Low-level mesh/material foundations
(not in workspace members)

#### Dependencies

No internal game crate dependencies. External: `bevy` only.

**Note:** This crate is declared in `[workspace.dependencies]` but is **absent from `[workspace.members]`**. It is built
only as a path dependency pulled in by dependents, not as a standalone workspace target. This means `cargo clippy` and
`cargo check` will not cover it unless a consumer is also built — it cannot be linted or tested in isolation. Its
absence from workspace members is annotated in `Cargo.toml` with the note "not in workspace members".

#### Contents

Single source file: `src/materials.rs`. Exports only `pub mod materials`.

**`materials.rs`** defines:

- `CustomMaterial1Data` — a `ShaderType`-derived struct (implemented with `AsBindGroup`) holding all uniform data for
  the isometric tile shader: per-corner color values (tl, tr, bl, br), ambient color, gamma, per-corner gamma weights,
  sprite-sheet layout (rows, cols, idx), sprite dimensions (width, height, padding, margin), y-anchor, and upscale
  factor. Has a `delta()` method for change-detection comparisons.
- `CustomMaterial1` — a Bevy `Material2d` (GPU material asset) wrapping `CustomMaterial1Data` plus a texture handle.
  Sets up WGSL fragment shader (`shaders/custom_material1.wgsl`), alpha blending, and disables depth writes. This is the
  core sprite material shared across all map tiles and actors.
- Both types implement `Default`, `Debug`, `Clone`, `Component`, `Asset`.

#### Tier Assessment

Correctly placed at T4·4a. Contains only GPU-coupled presentation types (`Material2d`, `AsBindGroup`, `ShaderType`). No
game logic. No domain knowledge.

The "not in workspace members" status is a structural maintenance concern but not a tier violation.

**Reverse consumers (from workspace):**

- `unrender-std` (T4·4a) — re-exports `CustomMaterial1` and `CustomMaterial1Data`
- `untiled-core` (T3·3a) — flagged as violation below

#### Violations

**🔴 T3→T4 upward dependency: `untiled-core` imports `unrender-core`**

`untiled-core` is T3·3a (Map Pipeline ACL). It imports a T4 GPU material crate. This means Tiled map format parsing code
has a compile-time dependency on a Bevy rendering pipeline asset — a GPU-coupled type with shader bindings.
Infrastructure must never import presentation. The exact usage in `untiled-core` should be checked; if it needs the
material type only to store handle references, the handles could instead be typed as `Handle<M>` generics or wrapped in
a newtype defined at a lower tier.

### `unrender-std`

**Audit date:** 2026-03-20 **Assigned tier:** T4·4a (Rendering) **Declared role:** Standalone mesh / material helpers

**Status update (2026-03-22):**

- `CharacterAnimationDirection`, `CharacterAnimationState`, and `AnimationTimer` moved out of `unrender-std` into
  `unlocomotion-core`.
- This removes one major T1→T4 coupling path for locomotion animation state.
- Remaining extraction candidates still in `unrender-std`: `SpriteLayer`, `GameSprite`, and visual-attribute
  components in `components/visuals.rs`.

**Status update (2026-03-23):**

- `unlocomotion-plugin` no longer imports `unrender-std` — T1→T4 violation resolved.
- `unclassic-mode-orchestrator-plugin` no longer imports `unrender-std` — T2→T4 violation resolved.
- `unrender-std` itself now imports `unbehavior-core` (T1·1a) rather than `unbehavior` (T3·3a) — internal T3 dep resolved.
- `unnavigation-plugin` (new T1·1b crate, extracted from `unplayer-plugin`) imports `unrender-std` — new T1→T4 violation.
- Net change: −1 T1 violation (unlocomotion out, unnavigation in, count stays 13), −1 T2 violation (orchestrator out).
- Total active violations: 13 T1→T4, 2 T2→T4, 2 T3→T4 = **17 total**.

#### Dependencies

Internal (T0/T1/T3/T4): `unspatial-core` (T0), `unrender-core` (T4·4a), `unbehavior-core` (T1·1a), `unboard-core`
(T1·1a), `ungear-core` (T1·1c), `unlight-core` (T1·1a). External: `bevy`, `bevy_asset_loader`, `serde`, `enum-iterator`,
`bevy_platform`.

All internal deps are T0, T1, or T4 — correct downward imports for a T4 crate.

#### Contents

Modules: `assets`, `board`, `components`, `materials`, `resources`, `utils`.

**`assets.rs`** — `GearAssets` (AssetCollection/Resource): paths to the gear sprite sheet, texture atlas layout.

**`materials.rs`** — Re-exports `CustomMaterial1` and `CustomMaterial1Data` from `unrender-core`. Also defines
`CustomMaterial2` (additive-blending material for ghost effects) and `UIPanelMaterial` (UI panel with shader).

**`components/`** — Eight source files defining ECS components and enums:

- `sprite_layer.rs` — `SpriteLayer(f32)`: Z-offset component for draw-order fine-tuning
- `sprite_type.rs` — `SpriteType` enum: Ghost, GhostOrb, Breach, Player, Miasma, Other
- `game.rs` — `GameSprite`, `MapTileSprite`: marker components identifying entity roles
- `visuals.rs` — `LightSensitive`, `ResolutionFactor`, `SpectralClarity`, `UltravioletSensitive`, `InfraredSensitive`:
  rendering attribute components (shader parameters, UV/IR sensitivity)
- `animation.rs` — `CharacterAnimationDirection`, `CharacterAnimationState`, animation state machine types
- `focus_ring.rs` — interaction focus indicator component
- `light.rs` — lighting data components
- Various also with `Reflect` derives for Bevy's type registry

**`board/`** — `SpriteDB` (Resource): a pre-built lookup table mapping tileset tile UIDs to `MapTileComponents` bundles
and a `SpriteCVOKey` index, used for fast map tile spawning and interactive object state updates. `tiledata.rs` provides
`MapTileComponents` bundles.

**`resources/sprite_registry.rs`** — `setup_sprite_registry` system: populates `SpriteDB` at startup by iterating all
registered tile behaviors and building the sprite mesh/material bundles.

**`utils/`** — `quadcc.rs`: quad mesh generation helpers for isometric tiles. `collision.rs`, `light.rs`: board field
utilities.

#### Tier Assessment

This crate functions as a **shared component library** for the entire rendering subsystem and is used by virtually every
plugin in the game. Its placement at T4·4a is correct for the material and shader-coupled types. However, it has become
a **de facto cross-cutting foundation crate** — a role that T4 must not serve, because T0–T3 crates must not import T4.

The core problem: component types like `SpriteLayer`, `SpriteType`, `LightSensitive`, `SpectralClarity`, and the
animation state types are **pure data structs with no rendering pipeline coupling** (no `Material2d`, no `AsBindGroup`,
no shader handles). These are attached by domain plugins (T1) to entities, and read by the rendering pipeline (T4).
Their only Bevy dependency is `Component`, `Reflect`, `Default` — all from `bevy::prelude`, which is available at any
tier.

By placing these components in T4, every domain plugin that spawns or mutates a visual entity (ghost, player, gear item,
fog tile, etc.) is forced to import a T4 crate — creating a pervasive inversion of the dependency direction.

**Reverse consumers (crates that import `unrender-std`) — updated 2026-03-23:**

_T1 domain crates (each is a T1→T4 violation):_

- `unboard-plugin` (T1·1a)
- `unlight-plugin` (T1·1a)
- `unfog-plugin` (T1·1a)
- `unghost-plugin` (T1·1b)
- `unplayer-plugin` (T1·1b)
- `unnavigation-plugin` (T1·1b) — **NEW** (extracted from `unplayer-plugin`)
- `unnpc-plugin` (T1·1b)
- `ungear-plugin` (T1·1c)
- `ungearitems-plugin` (T1·1c)
- `uninventory-plugin` (T1·1c)
- `uninteraction-plugin` (T1·1c)
- `untruck-plugin` (T1·1c)
- `unwalkie-plugin` (T1·1c)

_T2 application crates (each is a T2→T4 violation):_

- `unreplicon-plugin` (T2)
- `unclassic-mode-gameplay-plugin` (T2)

_T3 infrastructure crates (each is a T3→T4 violation):_

- `unmapload-plugin` (T3·3a)
- `untmxmap-plugin` (T3·3a)

_Resolved — no longer import `unrender-std`:_

- `unlocomotion-plugin` (T1·1b) — resolved 2026-03-22
- `unclassic-mode-orchestrator-plugin` (T2) — resolved 2026-03-22

_Legitimate T4 consumers:_

- `unrender-plugin` (T4·4a), `unpicking-plugin` (T4·4a), `ungame-plugin`, `unclassic-mode-render-plugin`,
  `unclassic-mode-ui-plugin`, `unlobby-plugin`, `unui-plugin`

#### Violations

**🔴 T1→T4 (×13): T1 domain plugin crates that depend on `unrender-std`**

Every T1 domain plugin that spawns entities with visual appearance imports this T4 crate. This is the most pervasive
tier boundary violation in the codebase. One violation was resolved (`unlocomotion-plugin`); one new violation was
introduced (`unnavigation-plugin`, extracted from `unplayer-plugin`). Net count unchanged at 13.

**🔴 T2→T4 (×2): T2 application plugins depend on `unrender-std`**

`unreplicon-plugin` and `unclassic-mode-gameplay-plugin` import T4. `unclassic-mode-orchestrator-plugin` was resolved
(2026-03-22).

**🔴 T3→T4 (×2): T3 map pipeline crates depend on `unrender-std`**

`unmapload-plugin` and `untmxmap-plugin` import `unrender-std` to access tile data types and material handles during map
loading. Infrastructure adapters must not import presentation.

#### Recommendation

Extract the remaining non-GPU-coupled components from `unrender-std` into a new T0 or T1 crate (e.g.,
`unrender-types`).
Candidates for extraction (all are pure `Component`/`Reflect`/`Default` structs with no render-pipeline coupling):
`SpriteLayer`, `SpriteType`, `GameSprite`, `MapTileSprite`, and visual-attribute components (`ResolutionFactor`,
`AlphaModulator`, `EctoplasmVisuals`, `Emissive`, `Ethereal`, `ShadowCaster`). GPU-coupled types (`CustomMaterial1`,
`CustomMaterial2`, `UIPanelMaterial`, `SpriteDB`, quad mesh utilities) stay in `unrender-std` (T4). After extraction,
T1/T2/T3 imports would be from the new T0/T1 crate — eliminating all upward violations.

### `unrender-plugin`

**Audit date:** 2026-03-20 **Assigned tier:** T4·4a (Rendering) **Declared role:** Main 2D isometric render pipeline and
shaders

#### Dependencies

Internal: `unrender-std` (T4·4a), `unbehavior` (T3·3a), `untypes-core` (T0), `unspatial-core` (T0), `unboard-core`
(T1·1a), `unmetrics-core` (T0), `untruck-core` (T1·1c). External: `bevy`, `winit` (non-WASM only), `image` (non-WASM
only).

All internal deps are T0, T1, T3, or T4 — correctly downward.

#### Contents

Files: `lib.rs`, `plugin.rs`, `metrics.rs`, `systems/` (animation, board_sync, hydration, lerp).

**`plugin.rs`** exposes two plugins:

`UnhaunterRenderCorePlugin` — reads `CliOptions` to detect headless mode:

- In both modes: sets up board_sync, lerp, hydration systems, registers metrics, initializes `SpriteDB`.
- In headless mode only: stubs out `Assets<CustomMaterial1>`, `Mesh`, `Image`, `TextureAtlasLayout`, `AudioSource` so
  level-loading code can run without a GPU context.

`UnhaunterRenderPlugin` — presentation: animation system, `setup_sprite_registry` startup system, `apply_perspective`
update system (moves tiles to correct isometric screen positions), registers `Material2dPlugin::<CustomMaterial1>` and
`UiMaterialPlugin::<UIPanelMaterial>`, and (non-WASM only) sets the application window icon.

`apply_perspective` system: queries entities with `Position`, optional `LerpPosition`, `Transform`, optional
`SpriteLayer`; converts board coordinates to screen coordinates via `perspective::to_screen_coord`; applies the
`SpriteLayer` Z-offset.

**`metrics.rs`** — registers `DiagnosticPath` constants for frame-time tracking of key render systems.

**`systems/`** — board_sync, lerp, animation, hydration systems for synchronizing domain state to visual representation.

#### Tier Assessment

Clean T4·4a. All imports are from T0, T1, T3, or sibling T4. No violations. The headless stub init in
`UnhaunterRenderCorePlugin` is a pragmatic workaround to allow the level-loading pipeline (which depends on
`Assets<CustomMaterial1>`) to function without a GPU — a consequence of `unrender-std` being imported by T3 map pipeline
crates (see above).

**Note:** The crate exposes two plugins in one, differentiated by the headless flag at runtime. This is a reasonable
pattern given the current architecture but would become unnecessary if the pure-data components were extracted out of
`unrender-std`, breaking the T3→T4 import chain that necessitates the headless stub.

No violations.

### `unpicking-core`

**Audit date:** 2026-03-20 **Assigned tier:** T4·4a (Rendering) **Declared role:** Mouse-to-world picking data

#### Dependencies

No internal game crate dependencies. External: `bevy` only.

#### Contents

Single module: `picking.rs`.

Defines:

- `ALPHA_THRESHOLD: f32` — constant 0.8, used as the alpha cutoff for pixel-perfect hit testing
- `CustomSpritePickingCamera` — marker `Component` for cameras that should participate in custom picking
- `CustomSpritePickingMode` — `enum` (`BoundingBox`, `AlphaThreshold(f32)`) selecting the hit-test algorithm
- `CustomSpritePickingSettings` — `Resource` with picking configuration: `require_markers`, `picking_mode`,
  `tile_size: Vec2`, `check_neighbors`, `use_8_way_neighbors`, `neighbor_distance`

All types are pure data: `Component`, `Resource`, `Default`. No rendering pipeline types.

#### Tier Assessment

Correctly placed at T4·4a as a data companion to `unpicking-plugin`. The types could arguably live at T0 since they
contain no rendering pipeline coupling, but their purpose is exclusively picking configuration — a presentation concern
— so T4 is appropriate. The crate is only imported by `unpicking-plugin` (T4·4a), `ungame-plugin`, and
`unclassic-mode-render-plugin` (T4·4a), all legitimately in the presentation tier.

No violations.

### `unpicking-plugin`

**Audit date:** 2026-03-20 **Assigned tier:** T4·4a (Rendering) **Declared role:** Visual feedback for interaction
picking

#### Dependencies

Internal: `unpicking-core` (T4·4a), `unrender-std` (T4·4a). External: `bevy`, `bevy_picking`.

All imports are T4 or external. No violations on the dependency side.

#### Contents

Files: `lib.rs`, `plugin.rs`, `sprite_picking_backend.rs`, `README.md`.

**`plugin.rs`** — `CustomSpritePickingPlugin`:

- Initializes `CustomSpritePickingSettings` as a resource
- Registers `custom_sprite_picking` system in `PreUpdate` within `PickingSystems::Backend`

**`sprite_picking_backend.rs`** — `custom_sprite_picking` system (~350 lines):

- A full custom Bevy picking backend for entities using `MeshMaterial2d<CustomMaterial1>` (the game's custom sprite
  material), as opposed to Bevy's built-in `Sprite`-based picking backend
- Queries: pointers (`PointerId`, `PointerLocation`), cameras (with render target, ortho projection), primary window,
  sprites (with visibility, pickable, material handle, transform)
- Process: filter and Z-sort sprites → for each pointer, find the matching camera → convert screen to world → test hit
  by mode (`BoundingBox` or `AlphaThreshold`) → emit `PointerHits`
- `pixel_perfect_hit_test` — full pixel-level alpha sampling: extracts sprite-sheet UV coords from
  `CustomMaterial1Data`, samples the `Image` pixel data, checks alpha byte, optionally checks 8-connected neighbors.
  Uses constant-time-safe code path; bounds-checked before indexing.

The hitting logic correctly handles horizontal flipping, y-anchor offset, sprite-sheet columns/rows, padding/margin, and
upscale factor.

#### Tier Assessment

Clean T4·4a. The crate is a pure presentation system — it bridges mouse input to Bevy's picking event infrastructure for
the game's custom sprite material. No domain logic, no upward imports. Well-scoped.

No violations.
