## Tier 3 · Infrastructure & Adapters

External I/O, file formats, and persistence. Anti-Corruption Layers (ACL): external data formats are translated here and
must never leak into T0–T2. May import T0, T1, T2.

### 3a · Map Pipeline (Tiled ACL)

Crates: `untiled`, `untmxmap-core`, `untmxmap-plugin`, `unmapload-core`, `unmapload-plugin`, `unbehavior`

### untiled-core

- **Status:** CURRENT
- Audit date: 2026-03-20
- Declared tier: T3·3a · Map Pipeline
- Pair: standalone (no `-plugin` counterpart — anomalous for a `-core` named crate)
- Internal deps: `unrender-core` (T4·4a)
- Highest tier imported: **T4**
- Tier compliance: **FAIL** — declared T3, imports T4

**Violations:**

1. `unrender-core` (T4·4a) — `tiled.rs` imports `CustomMaterial1` from the rendering layer and stores it inside
   `AtlasData`:

   ```rust
   pub enum AtlasData {
       Sheet((Handle<TextureAtlasLayout>, CustomMaterial1)),
       Tiles(Vec<(Handle<Image>, CustomMaterial1)>),
       Headless,
   }
   ```

   `MapTileSetDb` (a `Resource`) holds `MapTileSet` values that each contain an `AtlasData`. This means the tileset
   database — an infrastructure resource — owns live rendering material handles. The rendering domain (`unrender-std`,
   `unrender-plugin`) is instead supposed to consume domain types and _produce_ rendering handles, not have them stored
   inside the map loading pipeline. The fix: `AtlasData` should carry only neutral image handle data (`Handle<Image>`,
   atlas dimensions, anchor metadata). The `CustomMaterial1` construction belongs in a T4 observer that reacts to a
   tileset being indexed.

**ACL boundary failure — `tiled::PropertyValue` leaks through:**

`MapLayer` in `tiledmap/map.rs` declares:

```rust
pub user_properties: HashMap<String, tiled::PropertyValue>,
```

`tiled::PropertyValue` is a type from the external `tiled` crate. Any crate that imports `untiled-core` and accesses
`MapLayer.user_properties` must also accept a dependency on the `tiled` library. This is the ACL failing its primary
job: the external format is not being translated — it is being forwarded as-is. The correct approach is to define a
`MapProperty` enum in `untiled-core` that mirrors only the variants the game uses, then convert `tiled::PropertyValue` →
`MapProperty` at the ACL boundary. Downstream crates would then only see the domain-facing enum.

**Structural note — missing `-plugin` pair:**

`untiled-core` has no `-plugin` counterpart. In the tier model, a `-core` without a `-plugin` is either a standalone
data library (acceptable) or an incomplete bounded context (a smell). Here, the core is used directly by
`untmxmap-plugin` for its raw map parsing types — the plugin is effectively `untmxmap-plugin`. That is a weak
justification for the split; `untiled-core` types could be private to `untmxmap-plugin` rather than exposed as a
separate crate.

### untmxmap-core + untmxmap-plugin

- **Status:** CURRENT
- Audit date: 2026-03-20
- Declared tier: T3·3a · Map Pipeline
- Pair: `untmxmap-core` / `untmxmap-plugin` (same tier: YES)
- Internal deps (`untmxmap-core`): `untypes-core` (T0)
- Internal deps (`untmxmap-plugin`): `untmxmap-core` (T3·3a), `untiled-core` (T3·3a), `unmapload-core` (T3·3a),
  `unboard-core` (T1·1a), `untypes-core` (T0), `unsettings-core` (T3·3b), `unrender-std` (T4·4a)
- Highest tier imported (`untmxmap-core`): T0
- Highest tier imported (`untmxmap-plugin`): **T4** — `unrender-std` (T4·4a)
- Tier compliance (`untmxmap-core`): **PASS**
- Tier compliance (`untmxmap-plugin`): **FAIL** — declared T3, imports T4

**Violations (`untmxmap-plugin`):**

1. `unrender-std` (T4·4a) — `bevy.rs` imports `CustomMaterial1` from `unrender-std` and constructs rendering material
   objects inside `bevy_load_map` during map tile loading. Every tileset processed during level load has a
   `CustomMaterial1` built and stored in `MapTileSetDb`. This means the map-loading pipeline cannot run headlessly
   without the rendering layer present. There is a `headless` flag that gates the material construction via
   `AtlasData::Headless`, but the import and the coupling remain regardless — a headless server binary still carries the
   T4 dependency at compile time. The fix: move all `CustomMaterial1` construction to a T4 observer that reacts to
   tileset data being available in `MapTileSetDb`, populating a parallel T4-owned structure.

**Notes (`untmxmap-core` — pass-compliant, but design concerns):**

`untmxmap-core` passes tier compliance cleanly. However, its type design shows domain data embedded inside the
infrastructure layer:

**`TmxMissionData` is a domain object in an ACL crate.**

```rust
pub struct TmxMissionData {
    pub mission_reward_base: i64,
    pub required_deposit: i64,
    pub grade_a_score_threshold: i64,
    pub grade_b_score_threshold: i64,
    pub grade_c_score_threshold: i64,
    pub grade_d_score_threshold: i64,
    pub difficulty: Difficulty,
    pub min_player_level: i32,
    ...
}
```

These fields are mission economics and progression tuning — domain data that lives in `.tmx` files by convention but
whose meaning is owned by the game's domain. By placing `TmxMissionData` inside `untmxmap-core`, the ACL becomes the
canonical home for mission scoring, difficulty, and economic parameters. A campaign UI (`uncampaign-plugin`, T4·4c) that
needs the list of missions and their rewards imports `untmxmap-core` instead of a T1/T2 domain type. The dependency
arrow goes in the wrong direction: UI should query a domain resource, not an infrastructure type.

The clean shape: define a `MissionDescriptor` type at T2 (`unmission-core`) containing these domain fields. The
`untmxmap-plugin` ACL reads the raw TMX bytes and produces `MissionDescriptor` values, writing them into a T2 resource.
Campaign UI reads the T2 resource. `untmxmap-core` reverts to raw asset types only (`TmxMap`, `TsxSheet`, `AssetIdx`,
`Maps`, `UpscaleIndex`) — no domain semantics.

**`NaivelyParsedProps` duplicates `TmxMissionData` as raw strings.**

`NaivelyParsedProps` (in `tmxmap.rs`) contains the same set of mission fields as `TmxMissionData`, but as raw parsed
strings inside the `TmxMap` Bevy asset. The conversion chain is: `.tmx bytes` → `NaivelyParsedProps` → `TmxMissionData`
→ campaign UI. This two-step conversion exists solely because the domain fields are held inside the ACL. Pushing
`TmxMissionData` to T2 would simplify `TmxMap` to only the data needed to actually load the map (bytes, class, a minimal
set of opaque string props read by the plugin).

**Grade threshold computation logic is embedded inside the asset loader.**

`TmxMap::calculate_grade_thresholds` runs the golden-ratio cascade that fills in missing grade thresholds during asset
load time. This is game-balance logic — a domain rule about how difficulty grades should relate to each other — sitting
inside a Bevy `AssetLoader`. If the design decision about the golden ratio changes, the asset loader must be edited.
This logic belongs in the mission domain (T2) or in a difficulty configuration resource, not in the loading layer.

**Orphan file: `untmxmap-plugin/src/properties.rs`**

`properties.rs` exists on disk in `untmxmap-plugin/src/` but it is not declared in `lib.rs` (no `mod properties;`
statement). It is never compiled. The file defines `MapProps` using `tiled::Properties` directly — the external library
type that the ACL is supposed to hide. The file may be a leftover from an earlier refactor. It should either be
integrated (with the `tiled::Properties` reference replaced) or deleted.

**`bevy_load_map` and the headless split problem.**

The central function `bevy_load_map` in `bevy.rs` accepts a `headless: bool` parameter and branches on it to skip
material creation. This pattern is a smell: a map-loading function should not need to know whether it is running in a
headless context. The correct split is two separate code paths — a domain-level map loader that processes geometry and
properties (T3·3a, no rendering imports), and a T4 observer that reacts to that loading completing and populates
rendering resources. Right now both paths live in one function gated by a flag, and the T4 import leaks into the T3
binary regardless.

### unmapload-core + unmapload-plugin

- **Status:** CURRENT
- Audit date: 2026-03-20
- Declared tier: T3·3a · Map Pipeline
- Pair: `unmapload-core` / `unmapload-plugin` (same tier: YES)
- Internal deps (`unmapload-core`): `unboard-core` (T1·1a), `untiled-core` (T3·3a)
- Internal deps (`unmapload-plugin`): `unmapload-core` (T3·3a), `untmxmap-core` (T3·3a), `untiled-core` (T3·3a),
  `unbehavior` (T3·3a), `unboard-core` (T1·1a), `unspatial-core` (T0/T1), `undifficulty-core` (T1·1c),
  `uninteraction-core` (T1·1c), `untypes-core` (T0), `unrender-std` (T4·4a)
- Highest tier imported (`unmapload-core`): T3·3a — same tier, no upward dep
- Highest tier imported (`unmapload-plugin`): **T4** — `unrender-std` (T4·4a)
- Tier compliance (`unmapload-core`): **PASS**
- Tier compliance (`unmapload-plugin`): **FAIL** — declared T3, imports T4

**Violations (`unmapload-core` — design violations, tier compliance passes):**

1. **`tiled::PropertyValue` leaks through a public component.** `PendingTiledLayerProperties` is defined as:

   ```rust
   #[derive(Component)]
   pub struct PendingTiledLayerProperties(pub HashMap<String, tiled::PropertyValue>);
   ```

   Any crate that accesses the component's payload must take a direct dependency on the external `tiled` crate. This is
   the ACL's core failure: it is forwarding the external format type rather than translating it to a domain-owned enum.
   The correct fix is to define a `MapProperty` enum inside `unmapload-core` (or `untiled-core`) that covers only the
   property variants the game uses, and convert `tiled::PropertyValue` → `MapProperty` at the moment of component
   construction.

2. **`MapLayer` from `untiled-core` embedded in a public event.** `LevelLoadedEvent.layers` carries
   `Vec<(usize, MapLayer)>` — a type from `untiled-core`. Any crate that reads this event (including T1
   field-initialisation systems listening on it) must also depend on `untiled-core`. The ACL boundary is broken at the
   event API: the map layer payload should be translated into a domain-level structure before being published. The event
   should carry a game-facing type (e.g., `Vec<(usize, GameMapLayer)>` defined in `unmapload-core`), not a raw Tiled
   format type.

3. **`MissionAssets` is misplaced and over-scoped.** `assets.rs` defines `MissionAssets`, an `AssetCollection` that
   bundles all mission audio (heartbeats, ghost roars, door sounds, breaker trips) and all particle/overlay images
   (smoke, salt, particles, hiding overlay). These are mission lifecycle and rendering assets — they have nothing to do
   with reading a `.tmx` file. Their canonical home is `unmission-core` (T2) for mission-lifecycle audio, and a T4 asset
   collection for presentation-only images. Placing them here forces every crate that needs map loading to carry a
   dependency on audio and visual asset handles.

4. **`MapAssets.vignette` is a T4 presentation resource.** `vignette.png` is a rendering overlay handle. Owning a
   presentation resource inside a T3 infrastructure crate is a presentation-to-infrastructure leak. It should be in a T4
   rendering or UI asset collection.

**Violations (`unmapload-plugin`):**

1. **`unrender-std` (T4·4a) — pervasive coupling across four source files.**
   - `level_setup.rs` — `LoadLevelSystemParam` holds `ResMut<Assets<CustomMaterial1>>`, `ResMut<Assets<Mesh>>`, and
     `ResMut<SpriteDB>` (all T4 rendering resources). Every system using this system param transitively depends on the
     rendering layer.
   - `level_finalization.rs` — imports `PreMesh`, `ResolutionFactor`, and `rebuild_collision_data` from `unrender_std`.
     The mesh-placeholder promotion system (`process_pre_meshes`) runs inside the map loading plugin.
   - `sprite_db.rs` — imports `MapTileComponents`, `PreMesh`, `TileSpriteBundle`, `ResolutionFactor`, and `QuadCC` from
     `unrender_std`. The entire populate-sprite-db function is building rendering bundles (materials, meshes,
     visibility) inside the map loading crate.
   - `tile_spawning.rs` — imports `GameSprite` and `MapTileSprite` from `unrender_std`. Spawning code sets
     `Visibility::Hidden`, `Transform`, and `MeshMaterial2d` alongside board-position setup.

   Fix (consistent with `untmxmap-plugin`): the map loading pipeline should produce headless entities with
   board-position and behavior data only. A T4 observer reacts to the entity's presence (or to `LevelLoadedEvent`) and
   adds `Mesh2d`, `MeshMaterial2d`, `Visibility`, and `SpriteDB` entries. The `SpriteDB` itself should move to
   `unrender-std` (or a T4 dedicated crate) so the rendering domain owns it.

2. **State machine ownership overreach in `plugin.rs`.** The plugin calls:

   ```rust
   app.init_state::<AppState>()
      .init_state::<BootState>()
      .init_state::<GameState>()
      .init_state::<SimulationState>()
   ```

   These are game-wide state machines whose lifecycle is owned by T2 orchestration (`unclassic-mode-orchestrator-plugin`
   or a dedicated engine plugin). A T3 map-loading plugin should not be the canonical registrar for `AppState` or
   `GameState`. If the plugin initialises these states it becomes an implicit dependency for any other plugin that needs
   state-gated systems — an invisible coupling far outside map loading's scope.

3. **Direct game-state transitions inside `level_finalization.rs`.** `after_level_ready` calls:

   ```rust
   next_app_state.set(AppState::InGame);
   next_game_state.set(GameState::Running);
   ```

   These are T2 orchestration decisions (when to enter gameplay) expressed inside a T3 map pipeline system. The pattern
   is backwards: `LevelReadyEvent` is already fired (a clean signal), and the T2 orchestrator should consume it and
   drive the state transition. Instead, the T3 plugin bypasses the orchestrator and directly manipulates the T2 state
   machine. If a different game mode (e.g., a tutorial mode) wants different post-load behaviour, it cannot override
   this without modifying the T3 map loader.

4. **`hydration_generic.rs` attaches gameplay components directly.** The hydration system inserts `Interactive`, `Door`,
   `RoomStateDelta`, `Stairs`, `Light`, `HeatEmitter`, `Movable`, `HidingSpot`, and picking flags based on `Behavior`
   property inspection. These are live gameplay components that drive physics, interaction, and lighting — not inert
   data for the map loading pipeline. The attachment logic here makes `unmapload-plugin` aware of every gameplay
   mechanic that tiles can participate in. Any new tile mechanic (e.g., `FreezeEmitter`) requires editing the map
   loading plugin to insert the component. The correct model: `unbehavior`-aware plugins in T1/T2 observe entities with
   specific behavior flags and insert their own components; the map loading layer only attaches `Behavior` and board
   data.

#### The dependency inversion — quantified (pre-split, historical context)

> **This violation was resolved by the split described below.** The analysis is preserved as context for why the split
> was necessary.

`unbehavior` was imported by **21 crates**. The T1 crates that imported it did so not to access the Tiled translation
logic, but to query `Behavior`, `Door`, `HeatEmitter`, `Opaque`, `Collision`, `Interactive`, `RoomStateDelta`, and
peers at runtime. Every one of these crates was forced to carry an indirect dependency on the `tiled` external crate
purely because the domain types and ACL constructors shared a crate boundary:

**T1 crates importing unbehavior:**

- `unlight-core` (T1·1a) — **critical**: a `-core` crate at T1 importing T3; likely queries `Opaque`, `Light`, or
  emission data
- `unboard-plugin` (T1·1a) — collision/walkable flags
- `unlight-plugin` (T1·1a) — light emission, heat coefficient
- `unthermal-plugin` (T1·1a) — `HeatEmitter`, heat output values
- `unfog-plugin` (T1·1a) — opacity, collision for fog propagation
- `unghost-plugin` (T1·1b) — `InteractableByGhost`, `Behavior` for interaction selection
- `unlocomotion-plugin` (T1·1b) — movement flags, ghost/player collision
- `unnpc-plugin` (T1·1b) — `NPC` class, `Interactive`, `NpcHelpDialog`
- `ungearitems-plugin` (T1·1c) — `Behavior` for gear interactions
- `uninventory-plugin` (T1·1c) — pickable/movable object flags
- `uninteraction-plugin` (T1·1c) — `Interactive`, `Door`, `RoomStateDelta`
- `untruck-plugin` (T1·1c) — item/gear object queries
- `unwalkie-plugin` (T1·1c) — room or entity queries

**T2 crates (fine — T2 may import T3):** `uninput-plugin`, `unclassic-mode-gameplay-plugin`,
`unclassic-mode-orchestrator-plugin`

**T4 crates (fine — T4 may import T3):** `unrender-std`, `unrender-plugin`, `unclassic-mode-render-plugin`,
`unclassic-mode-ui-plugin`

The `unlight-core` import is the clearest proof: a T1 `-core` crate cannot import T3 under the binding rules. The
correct tier must be ≤ T1, but the `tiled` dependency prevents the entire crate from living at T1. The solution is the
split described below.

---

#### Why the user is right — and slightly underselling it

The framing "this shields the intricacies of the TMX" is correct for Category B. But Category A — `Class`, `TileState`,
`Properties`, `Behavior`, and all the marker components — is not TMX shielding at all. It is the game's **tile
ontology**: the formal vocabulary that every system uses to answer "what is this object, what does it collide with, does
it emit light, can it be moved, is it a ghost interaction target?" This is T1 domain knowledge by definition.

The `tiled` crate is a one-time construction dependency: it is needed only at map-load time to parse `.tmx` files and
build `Behavior` components. Once an entity has a `Behavior` component attached, no T1 system ever needs to know that
the data originated from a Tiled file. The ACL has done its job. But because the construction code and the domain types
share a crate, the `tiled` dependency is carried everywhere the domain types go.

---

#### Fix applied — 2026-03-22

The split was implemented as described in the analysis above. The outcome:

**`unbehavior-core` (T1·1a — The Stage)** — created. Contains all Category A domain types: `Class`, `TileState`,
`Properties`, `Behavior`, `Light`, `Movement`, `Object`, `Util`, `Display`, all marker components from `components.rs`
(`Ground`, `Collision`, `Opaque`, `UVSurface`, `HeatEmitter`, `Door`, `Stairs`, `Movable`, `HidingSpot`,
`FloorItemCollidable`, `InteractableByGhost`, `RoomStateDelta`, `TmxEntityId`), `Interactive`, `UnhaunterPropertyValue`,
`BehaviorProperties`, `SpriteConfig`, `SpriteCVOKey`, `AutoSerialize`. No `tiled` dependency. All T1 domain crates
now import `unbehavior-core` instead of `unbehavior`.

**`unbehavior` (T3·3a — retained as ACL shell)** — retained and stripped. Now imports `unbehavior-core` + `tiled` only
(4 deps total). Retains all `from_tiled*` constructors: `BehaviorProperties::from_tiled`, `SpriteConfig::from_tiled_auto`,
`from_tiled`, `try_from_tiled`, `UnhaunterPropertyValue::from(&tiled::PropertyValue)`, and `NpcHelpDialog` (which still
touches `tiled::PropertyValue` in its constructor). Only consumed by T3·3a map pipeline crates.

**Remaining anomaly:** `unnpc-plugin` imports both `unbehavior` (T3·3a) and `unbehavior-core` (T1·1a), indicating a
partial migration. The T3 import in `unnpc-plugin` should be removed once NPC hydration no longer needs
Tiled-conversion constructors directly.
