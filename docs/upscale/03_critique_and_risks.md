# Design Critique & Risk Analysis

This document provides a critical examination of the proposed upscaling design, identifying potential issues, risks, and
areas that require further clarification before implementation.

## 1. Summary of the Current Proposal

- **Goal**: Use `xbrzscale` (2x-6x, with support up to 9x) to produce high-resolution assets, reducing pixel-art
  jaggedness for a "liminal/watercolor" aesthetic.
- **Storage**: `assets/upscaled/{Nx}/img/...` mirroring the `assets/img/` structure.
- **Loading**: "Highest Available" strategy, capped by a user setting `MaxUpscaleFactor`.
- **Compensation**: Per-entity `ResolutionFactor(f32)` component; `Transform.scale /= N` at spawn time.

---

## 2. Critical Findings

### 2.1. AssetIdx Structural Limitation

**Problem**: The current `assetidx_updater.rs` hardcodes the folder names to scan:

```rust
fn get_asset_types() -> Vec<(&'static str, Vec<&'static str>)> {
    vec![
        ("fonts", vec!["ttf"]),
        ("img", vec!["png"]),
        ("maps", vec!["tmx", "tsx"]),
        // ...
    ]
}
```

This means `assets/upscaled/3x/img/` will **not** be automatically indexed unless we add every possible upscale folder
to this list (e.g., `("upscaled/2x/img", vec!["png"])`, ...).

**Risk**: Without proper indexing, the game (especially in WASM) will have no way to know which upscaled assets exist.

**Solution Options**:

1. Modify `get_asset_types` to dynamically discover `upscaled/*/img` subfolders.
2. Create a separate "upscale manifest" file generated by the bash script that lists all available factors.
3. Rely on a single manifest file listing the single highest available upscale factor (e.g., `upscaled/manifest.txt`
   containing just "6").

### 2.2. Shader `sprite_width` / `sprite_height` Must Scale

**Confirmed Requirement**: The custom shader in `custom_material1.wgsl` uses `sprite_width` and `sprite_height` in
physical pixel units for margin calculations and pixel-perfect sampling:

```wgsl
let margin = 0.5;
let mx = margin / material.sprite_width;
let texel_per_px = abs(dpdx(mesh.uv.x) * material.sprite_width);
```

If we load a 3x image but leave `sprite_width` at its 1x value, the shader's margin and texel calculations will be
incorrect, potentially causing visual artifacts (wrong anti-aliasing, bleeding from neighboring sprites).

**Action Required**: `CustomMaterial1Data.sprite_width` and `sprite_height` must be multiplied by $N$ when an upscaled
asset is loaded for a tileset. This is handled in `bevy_load_map` (`crates/untmxmap-plugin/src/bevy.rs`).

### 2.3. Hardcoded Sprite Scales and Sizes Scattered Across Codebase

**Finding**: Many sprite spawning calls use hardcoded `with_scale(Vec3::new(0.5, 0.5, 0.5))` or similar:

| Location                                     | Scale Value            |
| :------------------------------------------- | :--------------------- |
| `orchestrator.rs` (Player spawn)             | `0.5`                  |
| `ghost.rs` (SaltyTrace spawn)                | `0.5`                  |
| `ghost.rs` (Smoke particle spawn)            | `0.2`                  |
| `sage.rs` (Smoke particle spawn)             | `0.2`                  |
| `salt.rs` (Salt pile spawn)                  | `0.5`                  |
| `hide.rs` (Hiding overlay spawn)             | `0.2`                  |
| `ungear-plugin/systems.rs` (Gear icon spawn) | `0.25`                 |
| `tile_spawning.rs` (Map tiles)               | `1.0` (or `-1.0` flip) |

**Risk**: If these sprites use upscaled textures, but the scale isn't compensated, they will appear $N \times$ larger
than intended.

**Challenge**: These are inline spawns via `asset_server.load("img/...")`, not going through `AssetCollection`. A
`ResolutionFactor` component is only useful if the spawning code _reads it_ or if a _system_ later adjusts the
transform. Neither is currently in place for these ad-hoc spawns.

### 2.4. `custom_size` Usage

**Finding**: Several sprites use `custom_size: Some(Vec2::new(X, Y))` to define their rendered size in world units,
rather than relying on the image's native resolution + transform scale.

Examples:

- `ghost.rs`: `custom_size: Some(Vec2::new(8.0, 8.0))` for salt particles.
- `waypoint.rs`: `custom_size: Some(Vec2::new(1.0, 1.0))` for indicators.
- `ghost_orb.rs`: `custom_size: Some(Vec2::new(1.0, 1.0))`.
- Various particle effects.

**Impact**: For sprites using `custom_size`, the image resolution is decoupled from the world size. Upscaling the
texture will improve visual quality _without_ requiring any `Transform.scale` change. These are "resolution-agnostic".

**Conclusion**: This is _good_ for these specific assets. No changes needed for them.

### 2.5. Dynamic Scale Modification Systems

**Finding**: Multiple systems modify `Transform.scale` dynamically:

1. **`ghost_scale_glitch_system`** (`ghost.rs`): Lerps scale towards `Vec3::ONE` as the "rest" state.
2. **Camera zoom** (`game_systems.rs`): `transform.scale.x *= 1.02` for NumpadAdd/Subtract.
3. **Tile flip** (`tile_spawning.rs`): `transform.scale.x = -1.0` for horizontal flipping.

**Risk #1**: `ghost_scale_glitch_system` uses `Vec3::ONE` as the "normal" scale. If the ghost sprite uses a 3x texture,
its "normal" scale should be `Vec3::splat(1.0 / 3.0)`. This system will fight against the compensation.

**Risk #2**: Tile flipping sets `scale.x = -1.0`. If a tile has a base scale of `0.33` (for 3x), flipping would need to
set it to `-0.33`, not `-1.0`.

### 2.6. `TextureAtlas` vs. `Sprite` Component

**Finding**: The game uses two sprite rendering approaches:

1. **`Sprite` + `Handle<Image>`**: For simple, single-image sprites (particles, overlays).
2. **`Sprite` + `TextureAtlas` (via `texture_atlas` field)**: For sprite sheets (player, gear, badges).

The `TextureAtlas` references a `TextureAtlasLayout` that defines tile sizes. If an upscaled image is loaded but the
layout still has 1x tile sizes, only the top-left portion of the first frame will be visible.

**Action Required**: When loading via `AssetCollection` (e.g., `PlayerAssets`), the `TextureAtlasLayout` must be
regenerated dynamically with `tile_size * N`. The `#[asset(texture_atlas_layout(...))]` macro is compile-time static, so
a new approach is needed.

### 2.7. Tiled Map Tiles Have No Transform Scale (Currently)

**Finding**: In `tile_spawning.rs`, map tiles are spawned with a `Transform` based purely on position, not a world scale
for the sprite itself:

```rust
let mut transform = Transform::from_xyz(t_x, t_y, pos.visual_priority);
if tile.flip_x {
    transform.scale.x = -1.0;
}
```

The tile's visual size comes from the `CustomMaterial1` and its associated mesh, not from `Transform.scale`. The mesh is
generated based on the tileset's `tile_width` and `tile_height`.

**Implication**: For map tiles, upscaling requires:

1. Loading the upscaled PNG.
2. Multiplying `tile_width`, `tile_height`, and `spacing` by $N$ when building the `TextureAtlasLayout`.
3. Multiplying `sprite_width`, `sprite_height` in `CustomMaterial1Data` by $N$.
4. **The mesh itself might need to remain 1x size**, or some other component must compensate.

This needs careful verification. If the mesh is generated at $3\times$ size, the tiles will appear $3\times$ larger in
the world.

## 3. Open Design Questions

### 3.1. How to Handle Ad-Hoc `asset_server.load()` Calls?

There are ~30+ places where `asset_server.load("img/...")` is called directly for particles, overlays, etc. Options:

1. **Wrapper Function**: Replace all `asset_server.load(path)` calls with `upscaled_load(asset_server, path)` that
   returns the path and the detected resolution factor.
2. **Post-Spawn System**: A system queries newly added `Sprite` components, looks up the loaded image's path, infers the
   resolution factor, and adjusts `Transform.scale`. This is fragile and adds a frame of delay.
3. **Ignore**: If most of these use `custom_size`, the impact might be minimal.

### 3.2. What is the "Base Scale" for Each Asset Type?

Different asset types seem to have different "baseline" transform scales:

| Asset Type | Typical Base Scale | Notes                             |
| :--------- | :----------------- | :-------------------------------- |
| Player     | `0.5`              | Set in `orchestrator.rs`          |
| Ghost      | `1.0` (implicit)   | No explicit scale set             |
| Map Tiles  | `1.0`              | Size from mesh, not transform     |
| Gear Items | `0.25`             | Set in `ungear-plugin/systems.rs` |
| Particles  | `0.2` - `0.5`      | Varies                            |
| Focus Ring | `1.1` or `0.5`     | Varies (player vs. breach)        |

This heterogeneity means a single global `ResolutionFactor` resource won't work. The per-entity component approach is
correct, but it requires each spawn site to be aware of it.

### 3.3. Should `xbrzscale` Apply to Everything?

**Consideration**: `xbrzscale` is designed for pixel art with clean lines. Some assets might not benefit or might even
look worse:

- **Noise/Gradient textures** (e.g., `vignette.png`, `smoke.png`): May get artificial "pixel art" edges.
- **Procedurally generated effects**: If any textures are runtime-generated, they wouldn't have upscaled versions.

**Recommendation**: Test a small sample of different asset types before committing to a full batch run. The script could
have an exclusion list.

## 4. Risk Summary

| Risk                                      | Severity | Mitigation                                           |
| :---------------------------------------- | :------- | :--------------------------------------------------- |
| `assetidx` doesn't index `upscaled/`      | High     | Modify updater or use a manifest file.               |
| Shader `sprite_width` incorrect           | High     | Ensure `bevy_load_map` scales these values.          |
| Hardcoded `Vec3::ONE` in glitch system    | Medium   | Refactor to use `ResolutionFactor` component.        |
| Tile flip breaks with non-1.0 scale       | Medium   | Refactor flip logic to negate existing scale.        |
| Ad-hoc spawns ignore resolution factor    | Medium   | Audit and use wrapper or accept visual discrepancy.  |
| `TextureAtlasLayout` from macro is static | High     | Move to runtime layout generation for sprite sheets. |
| `xbrzscale` artifacts on some textures    | Low      | Maintain exclusion list in the batch script.         |

---

## 5. Recommendations for Next Steps

1. **Prototype the `assetidx` change first**: Without proper discovery, nothing else works.
2. **Prototype map tile upscaling**: This is the most visually impactful and will validate the shader/layout scaling.
3. **Audit all `transform.scale` usages**: Create a comprehensive list of locations and categorize them.
4. **Define a `ResolutionFactor` component API**: Decide on helper functions for spawn-time scale calculation.
5. **Test `xbrzscale` on a diverse set of assets**: Smoke, particles, vignettes, and character sprites.
