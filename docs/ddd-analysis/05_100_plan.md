# The 100% Readiness Roadmap: "The Final Seams"

## Phase 1: The "Visual Trait" Refactor

**Goal:** Remove `GhostSprite` and `PlayerSprite` references from `unlight-plugin`. The renderer should only care about
_how things look_, not _what they are_.

1. **Define Generic Visual Components:** In `unrender-std/components/visuals.rs`, ensure these exist:
   - `Luminescent { intensity: f32, pulse: f32 }`: For things that glow (Breaches).
   - `Ethereal { alpha_oscillation: f32, warp: f32 }`: For things that flicker or distort (Ghosts).
   - `ShadowCaster { shadow_strength: f32 }`: For solid entities (Players).
2. **Refactor `maplight.rs`:** Replace the `if let Some(ghost) = o_gs` and `if o_player.is_some()` blocks with queries
   for these new components.
3. **Update `unclassic-mode-plugin`:** When spawning the ghost or player, attach these visual trait components.
4. **The Win:** You can now create a "Glowing Crystal" or a "Distorted Time Anomaly" simply by adding these traits,
   without the lighting system ever needing to know what a "Ghost" is.

## Phase 2: Scoring & Mission Abstraction

**Goal:** Move the specific "Unhaunter" scoring math out of the core engine and into the Game Mode.

1. **Create a Scoring Trait:** In `unsummary-core`, define a `MissionEvaluator` trait:

   ```rust
   pub trait MissionEvaluator {
       fn calculate_base_score(&self, data: &SummaryData) -> i64;
       fn evaluate_grade(&self, score: i64) -> Grade;
   }
   ```

2. **Move Logic to Mod:** Implement this trait inside `unclassic-mode-plugin`.
3. **Refactor Summary:** Change the `calculate_score` system in `unsummary-plugin` to call the active `MissionEvaluator`
   resource.
4. **The Win:** If you build an "Escape Mode," you can provide a different evaluator that scores based on "Time
   Survived" or "Items Extracted" instead of "Repellent Used."

## Phase 3: Representation Decoupling (Assets)

**Goal:** Remove `GearSpriteID` from the `-core` crates. The core data shouldn't know it's a 2D game.

1. **Introduce Visual Keys:** In `unfoundation-core`, replace `GearSpriteID` (the enum with numbers) with
   `VisualKey(String)`.
2. **Registry Mapping:** In `unrender-plugin`, create a resource `SpriteRegistry(HashMap<VisualKey, usize>)`.
3. **Refactor Gear Spawning:** Gear items now carry a `VisualKey("item.thermometer")`. The renderer looks up that key in
   the `SpriteRegistry` to find the index `45`.
4. **The Win:** If you ever switch to a 3D engine, you simply change the registry to map `"item.thermometer"` to a 3D
   Model Handle instead of a sprite index. The gear data remains exactly the same.

## Phase 4: Mission Logic Migration

**Goal:** Move the "End Mission" and "Bank" logic out of the Truck (UI) and into a generic system.

1. **Create `unmission-plugin`:** Extract the bank update, XP gain, and "End Mission" logic from
   `untruck-plugin/systems/truck_ui_systems.rs`.
2. **Event-Driven Flow:** The Truck UI should only send a `RequestEndMission` event. The new `unmission-plugin` listens
   for this and handles the actual profile persistence.
3. **The Win:** The engine now has a proper "Mission Lifecycle" controller. You could trigger the end of a mission by
   walking through a door or reaching a timer, without needing the Truck UI at all.
