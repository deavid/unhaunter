### unlocomotion-plugin

- **Status:** CURRENT
- Audit date: 2026-03-20
- Declared tier: T1 · 1b · The Actors
- Pair: `unlocomotion-plugin` only — **no `-core` counterpart**
- Internal deps: `unplayer-core` (T1·1b), `unspatial-core` (T0), `untypes-core` (T0), `undifficulty-core` (T1·1c),
  `unfog-core` (T1·1a), `ungear-core` (T1·1c), `uninteraction-core` (T1·1c), `unnpc-core` (T1·1b), `unnavigation-core`
  (T1·1a), `unbehavior` (T3·3a), `unrender-std` (T4·4a), `unreplicon-core` (T2), `unaudiospatial-core` (T4·4b),
  `unui-core` (T4·4c)
- Highest tier imported: **T4** (`unrender-std`, `unaudiospatial-core`, `unui-core`)
- Tier compliance: **FAIL** — declared T1, imports T2, T3, and T4

**Violations:**

1. `unrender-std` (T4·4a) — uses `AnimationTimer`, `CharacterAnimation` (rendering animation components). These are
   presentation types living in a domain plugin.

2. `unaudiospatial-core` (T4·4b) — writes `SoundEvent` for footstep sounds during movement. Audio events are
   presentation-layer output; dispatching them belongs in T4, not T1.

3. `unui-core` (T4·4c) — uses `MouseVisibility` resource to suppress movement when the cursor is hidden. UI state should
   not gate domain movement logic.

4. `unreplicon-core` (T2) — reads `AuthorityRole` to decide whether to emit `ExecuteInteractionEvent` directly or send
   an `InteractionRequestMessage` over the network. Replication routing is a T2 concern embedded inside a T1 system.

5. `unbehavior` (T3·3a) — queries `&Behavior` and `&Interactive` on interactable entities to resolve the nearest
   interactable and to handle van-entry. The same systemic T3 bleed seen across all Stage plugins.

**Notes — what this crate actually does:**

`unlocomotion-plugin` contains **two systems**:

- `apply_movement_intent`: reads `PlayerInput.movement` (a `Vec2`), applies `CollisionHandler.delta` from
  `unnavigation-core`, integrates speed/stamina/miasma penalties, and writes the final delta into `Position`. This is
  the true kinematics step — it owns the movement physics.

- `dispatch_interact_intent`: reads `PlayerInput.interact` (a `bool`), finds the nearest `Interactive` entity within
  range, and dispatches `ExecuteInteractionEvent` or `InteractionRequestMessage`. This is interaction dispatch, not
  locomotion.

The second system does not belong here by name or by responsibility. Interaction dispatch is a Mechanics concern
(T1·1c), not a locomotion concern.

**Notes — is this the `-plugin` for `unnavigation-core`?**

No — but it is closely related and the question reveals the gap. The responsibility boundary is:

| Concern                                                      | Where it should live                           | Where it lives now                     |
| ------------------------------------------------------------ | ---------------------------------------------- | -------------------------------------- |
| A\* pathfinding algorithm                                    | `unnavigation-plugin` (missing)                | `unnavigation-core` (wrong crate type) |
| Waypoint creation (click → path → entities)                  | `unnavigation-plugin` (missing)                | `unplayer-plugin`                      |
| Waypoint following (queue → `PlayerInput.movement`)          | `unnavigation-plugin` (missing)                | `unplayer-plugin`                      |
| Keyboard cancels waypoints                                   | `unnavigation-plugin` (missing)                | `uninput-plugin` (T2)                  |
| Collision response delta                                     | `unnavigation-plugin` or `unlocomotion-plugin` | `unnavigation-core` (as SystemParam)   |
| Kinematics integration (`PlayerInput.movement` → `Position`) | `unlocomotion-plugin` ✅                       | `unlocomotion-plugin`                  |
| Interaction dispatch                                         | `uninteraction-plugin` or similar              | `unlocomotion-plugin` ❌               |

`unlocomotion-plugin` owns the last pure-physics step correctly. But it has been used as a dumping ground for two
additional concerns (interaction dispatch, and indirectly the collision SystemParam from `unnavigation-core`).

**Notes — this is part of the same half-extracted domain as `unnavigation-core`.**

Together, `unnavigation-core` and `unlocomotion-plugin` represent a locomotion planning domain that was never fully
extracted:

- `unnavigation-core` has the data types (waypoints) and the algorithm (A\*) but no plugin.
- `unlocomotion-plugin` has the final physics step (kinematics) but no core, and carries two foreign responsibilities.
- The middle layer (planning → waypoint queue → `PlayerInput`) lives in a third crate (`unplayer-plugin`) that should
  not own it.

The target shape remains: one bounded context (`unlocomotion-core` + `unlocomotion-plugin`, or a `unnavigation-core` +
`unnavigation-plugin` pair) that owns the full pipeline from "entity wants to be at position X" to "entity's `Position`
is updated each frame." Until that refactor happens:

- Do not add more foreign responsibilities to `unlocomotion-plugin`.
- Do not move the collision physics from `unnavigation-core` into `unlocomotion-plugin` without auditing what else comes
  with it.
- The interaction dispatch system in this plugin is a misplacement candidate for the first time this area is touched.

(`target_point`), rage simulation, hunt timers, repellent hit counters, and visual hint fields
(`hunt_warning_intensity`). No tier violation, but it is a candidate for future decomposition (e.g., separating AI
planning state from social/combat state from visual hint state).

**Violations (`unghost-plugin`):**

1. `unrender-std` (T4·4a) — used in `ghost_orb.rs` for `GameSprite`, `SpriteLayer`, `InfraredSensitive` (spawning orb
   particle entities with rendering components) and in `ghost_ai/mod.rs` for `ResolutionFactor`. Ghost orb particle
   spawning is a visual effect and should live in a T4 rendering crate.

2. `unaudiospatial-core` (T4·4b) — used as `AudioEmitter` (a `SystemParam`) in `ghost_ai/mod.rs` for ghost sounds during
   the AI loop. Ghost sound dispatch should go through events, not direct audio emitter access inside a T1 system.

3. `unaudiobg-core` (T4·4b) — imported by the plugin, likely to mute/unmute background music tracks during hunts. Music
   state changes are a T4 presentation decision triggered by domain events, not a T1 domain responsibility.

4. `unsummary-core` (declared T4·4c) — used to accumulate ghost contribution stats (kill count, hunt data) into the
   post-mission report. Note: `unsummary-core` is imported by multiple T1 and T2 crates (`unvitals-plugin`,
   `unplayer-plugin`, `ungearitems-plugin`, `unmission-plugin`, `unclassic-mode-orchestrator-plugin`). Its declared T4
   placement is almost certainly wrong — post-mission report data is domain data, not presentation. This is a systemic
   tier mislabeling that will appear repeatedly until `unsummary-core` is re-audited and re-shelved at T1 or T2.

5. `unreplicon-core` (T2) — used in `ghost_ai/mod.rs` for `SpawnParticleNetEvent` (broadcast particle effects over the
   network). Network message dispatch from a T1 domain system is the same T2-bleed pattern seen in
   `unlocomotion-plugin`.

6. `unbehavior` (T3·3a) — the Ghost Interaction System (`gis/`) queries `&Behavior` and `&Interactive` to select and act
   on interactable entities. Same systemic T3 bleed seen throughout T1.

**Notes — good design patterns worth preserving:**

- The plugin defines **two separate plugin structs**: `UnhaunterGhostCorePlugin` (simulation: registers resources, AI
  systems, evidence decay, sound field pulses — headless-safe) and `UnhaunterGhostPlugin` (presentation: asset loading,
  orb visual effects — client only). This is the correct headless/client split. The pattern should be enforced: the T4
  violations currently in `UnhaunterGhostCorePlugin` must move to `UnhaunterGhostPlugin` or a T4 crate, not the other
  way around.

- Ghost AI correctly initializes `PerlinNoise` from `unnoise-core` (T0) with a headless-optimized variant
  (`new_low_mem`) when running dedicated. This is a clean use of the T0 noise resource.

- Cross-domain sound field interaction (`sound_field_pulse.rs`) emits directly into `unsoundfield-core`'s grid, which is
  correct T1→T1 interaction.

- The ghost plugin reads `unplayer-core` types but does not own or call into player systems — it observes player state,
  it does not alter it. Correct directionality.

**Violations (`unplayer-core`):**

1. `unreplicon-core` (T2) — `PlayerSprite::network_id: NetworkId`. The player's fundamental identity component carries a
   replication-layer type. The need to correlate a player entity with a specific client is legitimate, but coupling the
   T1 `-core` to `NetworkId` forces an upward dep. Fix: define a thin `PlayerNetworkId(u64)` newtype at T1; the T2
   boundary maps `NetworkId` → `PlayerNetworkId` and never leaks inward.

2. `unsettings-core` (T3·3b) — `PlayerInputMapping::controls: ControlKeys`. Key-binding configuration is a user
   preference stored on disk — a T3 concern. The component should hold the resolved action mapping (key → action), not a
   reference to a settings persistence type.

3. `GameConfig.player_id` — "which player the camera should follow" is a rendering / presentation config and does not
   belong in a T1 `-core` resource.

1. `unrender-std` (T4·4a) — `AnimationTimer`, `CharacterAnimation` in `movement.rs` (`drive_character_animation` is

5. `unreplicon-core` (T2) — `LocallyOwned`, `LobbyInfo`, `LocalPlayer`, `AuthorityRole`, `PlayerDiedEvent`,

6. `unbehavior` (T3·3a) — `Behavior`, `Interactive`, `Stairs`, `FloorItemCollidable`, `RoomStateDelta` queried across

7. `unprofile-core` (T3·3b) — `record_death_to_profile` calls `player_profile.persist()` directly from a sanity system.
   Profile persistence is infrastructure; it should be triggered by an event handler at T2/T3, not inlined into a T1
   simulation system.

**Notes — how the god crate grew:**

Every feature touching the player entity landed in `unplayer-plugin` because the player entity was always involved. This
is the classic ECS anti-pattern of organising around entities instead of bounded contexts.

The most telling symptom: `unvitals-plugin` and `uninventory-plugin` already exist as separate crates, but
`unplayer-plugin` still contains vitals simulation systems and inventory management systems. The split was started but
never completed. The strangler fig is stalled at the first cut.

The natural decomposition path — which already has the right crate names in place:

- `unvitals-plugin` receives sanity drain, health regeneration, stamina. `unplayer-plugin` retains only death
  observation (which might move to `unvitals-plugin` too).
- `uninventory-plugin` receives grab, drop, cycle, swap.
- `unnavigation-plugin` (to be created) receives waypoint creation, stair traversal, waypoint following.
- `unlocomotion-plugin` receives kinematics integration (already partially its job).
- T4 rendering crate receives `drive_character_animation`, `apply_player_tint_color`, vignette rendering.
- T2/T3 observer receives `record_death_to_profile`.
- `unplayer-plugin` shrinks to: player spawn/despawn, identity lifecycle, input routing, hiding.

**Special note — workspace membership:**

`unnpc-core` is listed in `[workspace.dependencies]` with the comment "not in workspace members." It is absent from the
`[workspace.members]` array and therefore excluded from `cargo check --workspace`, `cargo clippy`, etc. The reason for
this exclusion is undocumented. It compiles only as a transitive dependency of `unnpc-plugin`. This is silent drift: any
lint warning, unused-item, or hidden API break in `unnpc-core` will go undetected by workspace-wide tooling.

**Notes — `unnpc-core`:**

The crate contains exactly one file (`events.rs`) with exactly one type:

```rust
pub struct NpcHelpEvent { pub entity: Entity }
```

That is the entire bounded context declared by `unnpc-core`. As a pure event definition with zero internal deps it is
tier-compliant, but it raises the question of whether a crate this thin warrants its own workspace entry at all. The
event could live directly in `unnpc-plugin` until the domain grows. The fact that it was split out suggests it was
anticipated that other crates would import the event type directly — but currently nothing imports `unnpc-core` except
`unnpc-plugin` itself.

**Notes — `unnpc-plugin`:**

Despite the thin `-core`, the plugin mixes **four distinct tiers** of responsibility in three files:

| File / function                         | Concern                                                                            | Actual tier                    |
| --------------------------------------- | ---------------------------------------------------------------------------------- | ------------------------------ |
| `hydration.rs` — `hydration_npc_system` | Reads `Behavior.p.is_npc` + `PendingTiledLayerProperties` → inserts NPC components | T3·3a (Tiled ACL)              |
| `npchelp.rs` — `auto_call_npchelp`      | Proximity check + time accumulator → emits `NpcHelpEvent`                          | ✅ T1·1b                       |
| `npchelp.rs` — `npchelp_event`          | Receives the event, sets `GameState::NpcHelp`                                      | T2 (application state machine) |
| `npchelp.rs` — `setup_ui`               | Spawns dialog box UI nodes with `UIPanelMaterial` + `UiAssets` fonts               | T4·4c                          |
| `npchelp.rs` — `cleanup`                | Despawns dialog UI entities                                                        | T4·4c                          |
| `npchelp.rs` — `keyboard`               | Keyboard handling for `GameState::NpcHelp` → returns to Running                    | T2/T4                          |

The only code that genuinely belongs in a T1·1b actor plugin is `auto_call_npchelp`: proximity to the player, a time
trigger, and event emission. Everything else is infrastructure translation (hydration), application orchestration (state
transition), or presentation (UI rendering).

**Additional structural issue — two plugins in one file:**

`plugin.rs` defines both `UnhaunterNPCCorePlugin` and `UnhaunterNPCPlugin`. Per project convention, `plugin.rs` must
contain a single `Plugin` implementation. The "core plugin" only calls `crate::hydration::app_setup(app)` — its
rationale for existing separately is not documented.

**Violations (`unnpc-plugin`):**

1. `unbehavior` (T3·3a) — `hydration.rs` reads `Behavior`, `NpcHelpDialog`, `Interactive`, and `FloorItemCollidable`
   from `unbehavior`. The systemic Tiled ACL bleed. `NpcHelpDialog` itself is defined in `unbehavior`, meaning the NPC
   concept's primary data carrier is a T3 type — the actor domain has no native representation of its own characters.

2. `unmapload-core` (T3·3a) — `hydration.rs` reads `PendingTiledLayerProperties` to extract dialog text from the Tiled
   object variant field. Same map-loading pattern as every Stage plugin.

3. `unrender-std` (T4·4a) — `npchelp.rs`: `UIPanelMaterial` drives the dialog panel's material. Rendering concerns
   inside a T1 actor plugin.

4. `unui-core` (T4·4c) — `npchelp.rs`: `UiAssets` provides font handles for dialog text nodes. UI asset access inside a
   T1 actor plugin.

**Design observation — NPC as a Tiled-native concept:**

The NPC is fundamentally defined through a Tiled map property (`is_npc = true`, `variant = "…dialog text…"`). There is
no native domain model: the `NpcHelpDialog` component that carries the dialog text is defined in `unbehavior`, not in
`unnpc-core`. This means the "actor" exists only because the map says so, and its identity is entirely in T3 territory.

A cleaner design would:

- Define `NpcHelpDialog` (or a renamed equivalent) in `unnpc-core` as a first-class domain component.
- Have `unbehavior` translate Tiled properties into `unnpc-core` types (T3 → T1, correct direction).
- Move `setup_ui`, `cleanup`, `keyboard` to a T4·4c UI plugin.
- Move `npchelp_event` (the state transition) to a T2 observer.
- Move `hydration_npc_system` to `unbehavior` or a T3 hydration plugin.
- `unnpc-plugin` shrinks to only `auto_call_npchelp` + the message wiring.
