**Violations:**

1. `unrender-std` (T4·4a) — **RESOLVED (2026-03-23).** `AnimationTimer` and animation-state types were moved to
   `unlocomotion-core`; all remaining uses of `unrender-std` in `unlocomotion-plugin` were removed. No T4 rendering
   import remains in this plugin for locomotion simulation.

2. `unui-core` (T4·4c) — uses `MouseVisibility` resource to suppress movement when the cursor is hidden. UI state should
   not gate domain movement logic.

3. `unreplicon-core` (T2) — reads `AuthorityRole` to decide whether to emit `ExecuteInteractionEvent` directly or send
   an `InteractionRequestMessage` over the network. Replication routing is a T2 concern embedded inside a T1 system.

4. `unreplicon-core` (T2) and T4 imports (`unui-core`, `unaudiospatial-core`, `unrender-std`) remain the primary tier
   violations. `unbehavior-core` is now a T1 dependency and no longer a tier violation by itself.

**Notes — what this crate actually does:**

`unlocomotion-plugin` contains **two systems**:

- `apply_movement_intent`: reads `PlayerInput.movement` (a `Vec2`), applies `CollisionHandler.delta` from
  `unnavigation-core`, integrates speed/stamina/miasma penalties, and writes the final delta into `Position`. This is
  the true kinematics step — it owns the movement physics.

- `dispatch_interact_intent`: reads `PlayerInput.interact` (a `bool`), finds the nearest `Interactive` entity within
  range, and dispatches `ExecuteInteractionEvent` or `InteractionRequestMessage`. This is interaction dispatch, not
  locomotion.

The second system does not belong here by name or by responsibility. Interaction dispatch is a Mechanics concern
(T1·1c), not a locomotion concern.

**Notes — is this the `-plugin` for `unnavigation-core`?**

No — but it is closely related and the question reveals the gap. The responsibility boundary is:

| Concern                                                      | Where it should live                           | Where it lives now                     |
| ------------------------------------------------------------ | ---------------------------------------------- | -------------------------------------- |
| A\* pathfinding algorithm                                    | `unnavigation-plugin` (missing)                | `unnavigation-core` (wrong crate type) |
| Waypoint creation (click → path → entities)                  | `unnavigation-plugin` (missing)                | `unplayer-plugin`                      |
| Waypoint following (queue → `PlayerInput.movement`)          | `unnavigation-plugin` (missing)                | `unplayer-plugin`                      |
| Keyboard cancels waypoints                                   | `unnavigation-plugin` (missing)                | `uninput-plugin` (T2)                  |
| Collision response delta                                     | `unnavigation-plugin` or `unlocomotion-plugin` | `unnavigation-core` (as SystemParam)   |
| Kinematics integration (`PlayerInput.movement` → `Position`) | `unlocomotion-plugin` ✅                       | `unlocomotion-plugin`                  |
| Interaction dispatch                                         | `uninteraction-plugin` or similar              | `unlocomotion-plugin` ❌               |

`unlocomotion-plugin` owns the last pure-physics step correctly. But it has been used as a dumping ground for two
additional concerns (interaction dispatch, and indirectly the collision SystemParam from `unnavigation-core`).

**Notes — this is part of the same half-extracted domain as `unnavigation-core`.**

Together, `unnavigation-core`, `unnavigation-plugin`, and `unlocomotion-*` represent the locomotion planning domain,
but responsibility is still partially split:

- `unnavigation-core` has the data types (waypoints) and algorithm utilities.
- `unlocomotion-plugin` has the final physics step (kinematics) and still carries foreign responsibilities.
- The middle layer (planning → waypoint queue → `PlayerInput`) lives in a third crate (`unplayer-plugin`) that should
  not own it.

The target shape remains: one bounded context (`unlocomotion-core` + `unlocomotion-plugin`, or a `unnavigation-core` +
`unnavigation-plugin` pair) that owns the full pipeline from "entity wants to be at position X" to "entity's `Position`
is updated each frame." Until that refactor happens:

- Do not add more foreign responsibilities to `unlocomotion-plugin`.
- Do not move the collision physics from `unnavigation-core` into `unlocomotion-plugin` without auditing what else comes
  with it.
- The interaction dispatch system in this plugin is a misplacement candidate for the first time this area is touched.

**Notes — good design patterns worth preserving:**

- The plugin defines **two separate plugin structs**: `UnhaunterGhostCorePlugin` (simulation: registers resources, AI

  way around.

- Ghost AI correctly initializes `PerlinNoise` from `unnoise-core` (T0) with a headless-optimized variant
  (`new_low_mem`) when running dedicated. This is a clean use of the T0 noise resource.

- Cross-domain sound field interaction (`sound_field_pulse.rs`) emits directly into `unsoundfield-core`'s grid, which is
  correct T1→T1 interaction.

- The ghost plugin reads `unplayer-core` types but does not own or call into player systems — it observes player state,
  it does not alter it. Correct directionality.

**Special note — workspace membership:**

`unnpc-core` is listed in `[workspace.dependencies]` with the comment "not in workspace members." It is absent from the
`[workspace.members]` array and therefore excluded from `cargo check --workspace`, `cargo clippy`, etc. The reason for
this exclusion is undocumented. It compiles only as a transitive dependency of `unnpc-plugin`. This is silent drift: any
lint warning, unused-item, or hidden API break in `unnpc-core` will go undetected by workspace-wide tooling.

**Notes — `unnpc-core`:**

The crate contains exactly one file (`events.rs`) with exactly one type:

```rust
pub struct NpcHelpEvent { pub entity: Entity }
```

That is the entire bounded context declared by `unnpc-core`. As a pure event definition with zero internal deps it is
tier-compliant, but it raises the question of whether a crate this thin warrants its own workspace entry at all. The
event could live directly in `unnpc-plugin` until the domain grows. The fact that it was split out suggests it was
anticipated that other crates would import the event type directly — but currently nothing imports `unnpc-core` except
`unnpc-plugin` itself.

**Notes — `unnpc-plugin`:**

Despite the thin `-core`, the plugin mixes **four distinct tiers** of responsibility in three files:

| File / function                         | Concern                                                                            | Actual tier                    |
| --------------------------------------- | ---------------------------------------------------------------------------------- | ------------------------------ |
| `hydration.rs` — `hydration_npc_system` | Reads `Behavior.p.is_npc` + `PendingTiledLayerProperties` → inserts NPC components | T3·3a (Tiled ACL)              |
| `npchelp.rs` — `auto_call_npchelp`      | Proximity check + time accumulator → emits `NpcHelpEvent`                          | ✅ T1·1b                       |
| `npchelp.rs` — `npchelp_event`          | Receives the event, sets `GameState::NpcHelp`                                      | T2 (application state machine) |
| `npchelp.rs` — `setup_ui`               | Spawns dialog box UI nodes with `UIPanelMaterial` + `UiAssets` fonts               | T4·4c                          |
| `npchelp.rs` — `cleanup`                | Despawns dialog UI entities                                                        | T4·4c                          |
| `npchelp.rs` — `keyboard`               | Keyboard handling for `GameState::NpcHelp` → returns to Running                    | T2/T4                          |

The only code that genuinely belongs in a T1·1b actor plugin is `auto_call_npchelp`: proximity to the player, a time
trigger, and event emission. Everything else is infrastructure translation (hydration), application orchestration (state
transition), or presentation (UI rendering).

**Additional structural issue — two plugins in one file:**

`plugin.rs` defines both `UnhaunterNPCCorePlugin` and `UnhaunterNPCPlugin`. Per project convention, `plugin.rs` must
contain a single `Plugin` implementation. The "core plugin" only calls `crate::hydration::app_setup(app)` — its
rationale for existing separately is not documented.

**Violations (`unnpc-plugin`):**

1. `unbehavior` (T3·3a) — **partial migration (2026-03-23)**: `unnpc-plugin` now imports both `unbehavior` (T3·3a) and
   `unbehavior-core` (T1·1a), indicating the `unbehavior` split was initiated in this crate but not completed.
   `hydration.rs` still reads `NpcHelpDialog`, `Interactive`, and `FloorItemCollidable` from `unbehavior`. `NpcHelpDialog`
   is defined in `unbehavior`, meaning the NPC concept's primary data carrier is still a T3 type — the actor domain has
   no native representation of its own characters. The `unbehavior` (T3) import should be removed once `NpcHelpDialog`
   is moved to `unnpc-core` and the Tiled ACL constructors in `hydration.rs` are relocated.

2. `unmapload-core` (T3·3a) — `hydration.rs` reads `PendingTiledLayerProperties` to extract dialog text from the Tiled
   object variant field. Same map-loading pattern as every Stage plugin.

3. `unrender-std` (T4·4a) — `npchelp.rs`: `UIPanelMaterial` drives the dialog panel's material. Rendering concerns
   inside a T1 actor plugin.

4. `unui-core` (T4·4c) — `npchelp.rs`: `UiAssets` provides font handles for dialog text nodes. UI asset access inside a
   T1 actor plugin.

**Design observation — NPC as a Tiled-native concept:**

The NPC is fundamentally defined through a Tiled map property (`is_npc = true`, `variant = "…dialog text…"`). There is
no native domain model: the `NpcHelpDialog` component that carries the dialog text is defined in `unbehavior`, not in
`unnpc-core`. This means the "actor" exists only because the map says so, and its identity is entirely in T3 territory.

A cleaner design would:

- Define `NpcHelpDialog` (or a renamed equivalent) in `unnpc-core` as a first-class domain component.
- Have `unbehavior` translate Tiled properties into `unnpc-core` types (T3 → T1, correct direction).
- Move `setup_ui`, `cleanup`, `keyboard` to a T4·4c UI plugin.
- Move `npchelp_event` (the state transition) to a T2 observer.
- Move `hydration_npc_system` to `unbehavior` or a T3 hydration plugin.
- `unnpc-plugin` shrinks to only `auto_call_npchelp` + the message wiring.

**Context:**

This plugin was extracted from `unplayer-plugin` to consolidate navigation planning into its own bounded context, as
recommended in the `unnavigation-core` audit (see `02_t1a.md`). It is placed at T1·1b (Actors) rather than T1·1a
because navigation logic interacts directly with player and NPC actor components. The `-core`/`-plugin` split is
therefore cross-subgroup by design.

**What the plugin owns:**

Pathfinding logic, waypoint queue management, click-to-move target computation, and stair traversal helpers extracted
from `unplayer-plugin`. The waypoint following loop (queue → `PlayerInput.movement`) and stair snap logic that
previously lived in `unplayer-plugin` should conceptually belong here; verify the extraction is complete.

**Violations:**

1. `unrender-std` (T4·4a) — waypoint entities are marked with `GameSprite` (a rendering component) so they appear in
   the world view. The rendering-layer marker should be attached by a T4 observer, not by the pathfinding logic.

2. `unui-core` (T4·4c) — reads `MouseVisibility` to suppress waypoint creation when cursor is hidden. UI state should
   not gate domain logic; this belongs in the input adapter layer (T2/`uninput-plugin`).

**Positive notes:**

- The extraction itself is structurally correct: navigation now has a bounded context owner. Other actor plugins can
  express movement intent via `MoveToTarget` without importing pathfinding utilities.
- No T3 imports. No `unbehavior` (T3·3a) pollution.
