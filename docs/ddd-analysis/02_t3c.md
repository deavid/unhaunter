### `unhub-client`

**Audit date:** 2026-03-20 **Assigned tier:** T3·3c (External Network Clients) **Declared role:** HTTP client for the
hub server

#### Dependencies

No internal game crate dependencies (neither `un*-core` nor `un*-plugin`). Pure external crates only: `serde`, `uuid`,
`rand`, `sha2`, `postcard`, `hmac`, `anyhow`.

This crate has **zero Bevy dependency** and **zero internal game deps** — it is headless-safe and could in principle run
anywhere including on the dedicated server or ProcMan process.

#### Contents

**`protocol.rs`** — Network wire format types for all three communication channels:

- `ProcManMessage` — bidirectional Hub↔ProcMan WebSocket protocol (hello, heartbeat, room lifecycle events, control
  commands)
- `RoomState`, `RoomMetadata`, `RoomSummary` — shared room data types
- `ChallengeRequest`, `ChallengeResponse`, `CreateRoomRequest`, `JoinRoomRequest` — Player↔Hub REST API request bodies
- `CreateRoomResponse`, `JoinRoomResponse`, `HubError`, `HealthResponse` — Player↔Hub REST API response bodies
- `ProcManToDedicated`, `DedicatedToProcMan` — ProcMan↔Dedicated server control protocol (assign/wipe/shutdown room,
  state reporting)

All types are plain data structs/enums with `serde` derives. No game logic.

**`tickets.rs`** — HMAC-SHA256 connection ticket encoding/decoding:

- `ConnectionTicket` — room code, installation_id, player_uuid, expiry timestamp
- `encode_ticket(ticket, hmac_secret)` — serializes to fixed 256-byte Renet `user_data` buffer with HMAC signature
- `decode_ticket(user_data, hmac_secret)` — verifies HMAC and deserializes; uses constant-time comparison (safe against
  timing attacks)

**`utils.rs`** — Generation utilities:

- `generate_room_code()` — 5-char code from safe vocal alphabet (avoids ambiguous chars)
- `generate_room_secret()` — 16-char alphanumeric string for basic access control
- `generate_codename(letter, attempt)` — adjective+noun display name generator for player nicknames
- `solve_pow(nonce, difficulty)` — SHA256 proof-of-work solver for anti-spam rate limiting

`lib.rs` re-exports the utility functions. `GAME_VERSION` constant from `env!("CARGO_PKG_VERSION")`.

#### Tier Assessment

The crate is a clean ACL for the Hub external network protocol. It defines no domain types and has no knowledge of game
rules or Bevy ECS. The contained types are shaped by the external service contract (Hub REST API, WebSocket protocol),
not by domain concepts — confirming the T3 placement.

**Reverse consumers (from workspace Cargo.toml):**

- `unhub-plugin` (T3·3c) — hub HTTP client at game runtime
- `unreplicon-plugin` (T2) — uses `ConnectionTicket`, `encode_ticket`, `decode_ticket`, `ProcManToDedicated`,
  `DedicatedToProcMan` for Renet authentication and ProcMan IPC
- `unprocman` (tool) — ProcMan process manager
- `unhub` server tool — hub server binary

#### Violations / Concerns

**⚠️ T2→T3 upward dependency: `unreplicon-plugin` imports `unhub-client`.**

`unreplicon-plugin` is T2 (Application Layer). It imports three things from this T3 crate:

- `protocol::{DedicatedToProcMan, ProcManToDedicated}` — ProcMan IPC protocol (used in `systems/procman.rs`)
- `tickets::{ConnectionTicket, encode_ticket}` — ticket creation for outgoing Renet connections (used in
  `systems/connection.rs`)
- `tickets::decode_ticket` — ticket validation for incoming Renet connections (used in `systems/auth.rs`)

Dependency direction rules require T2 to import only from T0, T1, and T2. T3 is above T2 in the tier hierarchy. This is
an upward dependency, which is a binding rule violation.

The root cause: the connection ticket and ProcMan message types were placed in `unhub-client` because they relate to hub
infrastructure. However, `unreplicon-plugin` also needs them for its authentication handshake. Neither location is
clearly wrong in isolation, but the combined result breaks the tier boundary.

**Recommendation:** Extract the types that T2 needs — `ConnectionTicket`, `encode_ticket`, `decode_ticket`, and the
ProcMan↔Dedicated protocol types — into a new T2 or T1 crate (e.g., `unnet-types` or extend `unreplicon-core`), so that
`unreplicon-plugin` can import them from its own tier. `unhub-client` could then re-export or depend on those types from
below.

**Update 2026-03-22 — T2→T3 violation RESOLVED (stale Cargo dep remains):**

As of 2026-03-22, all three source files that imported `unhub-client` in `unreplicon-plugin` (`systems/procman.rs`,
`systems/connection.rs`, `systems/auth.rs`) were moved to the new `unreplicon-transport` crate (T3·3c).
`unreplicon-transport` and `unhub-client` are peers at the same tier — the indirect usage is no longer a T2→T3
violation. However, `unhub-client` **remains listed in `unreplicon-plugin/Cargo.toml`** despite no source file under
`unreplicon-plugin/src/` importing it. The entry is dead. Removing it from `unreplicon-plugin/Cargo.toml` is a one-line
cleanup.

### `unreplicon-transport`

- **Status:** CURRENT
- Audit date: 2026-03-22
- Declared tier: T3·3c · External Network Clients
- Pair: standalone plugin (no `-core`); acts as a sub-plugin consumed by `unreplicon-plugin`
- Internal deps: `unreplicon-core` (T2), `unprofile-core` (T3·3b), `unhub-client` (T3·3c)
- Highest tier imported: T2 (T3 importing T2 is compliant — downward dependency)
- Tier compliance: **PASS**

**Purpose:**

`unreplicon-transport` is the Netcode/Renet/authentication/ProcMan ACL. It was extracted from `unreplicon-plugin` on
2026-03-22. It contains three modules mirroring the old `unreplicon-plugin` infrastructure:

| Module          | Content                                              | Role                         |
| --------------- | ---------------------------------------------------- | ---------------------------- |
| `procman.rs`    | Stdin/stdout IPC with the ProcMan process manager    | T3·3c infrastructure adapter |
| `connection.rs` | UDP transport setup for server and client            | T3·3c infrastructure adapter |
| `auth.rs`       | JWT ticket validation for incoming Renet connections | T3·3c infrastructure adapter |

Resources defined: `ProcManChannel` (bidirectional crossbeam channel to procman), `RoomAuth` (auth state received from
ProcMan — room code and HMAC secret).

**System map:**

| System / hook                                                        | Content                                                                                                | Verdict     |
| -------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------ | ----------- |
| `setup_procman_system` (Startup)                                     | Reads `CliOptions.procman_channel`; spawns stdin/stdout threads; inserts `ProcManChannel`              | ✅ T3·3c    |
| `update_procman_system` (Update)                                     | Drains `ProcManChannel.rx`; applies `AssignRoom`/`RenameRoom`/`WipeRoom`/`Shutdown` commands           | ✅ T3·3c    |
| `startup_transport_system` (Update, gated)                           | Creates `RenetServer`/`NetcodeServerTransport` (host) or `RenetClient`/`NetcodeClientTransport` (join) | ✅ T3·3c    |
| `monitor_renet_client_status` (Update)                               | Logs connection state changes                                                                          | ✅ T3·3c    |
| `monitor_renet_server_clients` (Update)                              | Logs transport-level client count changes                                                              | ✅ T3·3c    |
| `handle_disconnect_request` (Update)                                 | On `DisconnectRequest`: removes `RenetClient`/transport, despawns `Replicated` entities, swaps roles   | ⚠️ see note |
| `validate_new_connection_observer` (Observer `Add<ConnectedClient>`) | JWT HMAC validation; populates `ClientUuidMap`; disconnects invalid clients                            | ✅ T3·3c    |

**Note — `handle_disconnect_request` scope:**

`handle_disconnect_request` in `connection.rs` performs three actions:

1. Removes `RenetClient` and `NetcodeClientTransport` — transport teardown. ✅ T3·3c
2. Despawns all entities with `Replicated` — ECS entity cleanup. ⚠️
3. Removes `LobbyPresenceRole` and inserts `AuthorityRole` — application role mutation. ⚠️

Steps 2 and 3 cross into the application layer. Despawning replicated entities and mutating role resources involves
knowledge of session lifecycle and ECS conventions that belong in `unreplicon-plugin` (T2) or a dedicated session
teardown system. The placement is pragmatic: teardown on disconnect is a single atomic path and splitting it across
tiers would add complexity for limited gain. **Flag for review** if the disconnect path becomes more complex or is
reused in other teardown scenarios.

**`unreplicon-plugin` coupling — residual T2→T3 violation:**

`unreplicon-transport` is added as a sub-plugin inside `unreplicon-plugin::systems::app_setup`:

```rust
app.add_plugins((.., unreplicon_transport::plugin::UnrepliconTransportPlugin));
```

This makes `unreplicon-plugin` (T2) depend on `unreplicon-transport` (T3·3c) — an upward T2→T3 dependency. Transport
setup is infrastructure; the correct place to add `UnrepliconTransportPlugin` is the top-level app assembler
(`unhaunter/src/app.rs`) alongside other T3 plugins, which would break this coupling. Accepting for now; no functional
harm but the tier boundary is bent.

**Domain narrative:**

The extraction of `unreplicon-transport` from `unreplicon-plugin` (2026-03-22) was the correct architectural move. UDP
socket creation, Netcode protocol management, JWT authentication, and stdin/stdout IPC are all external-system adapters
that have no business in T2. The new crate correctly places all infrastructure adapters at T3·3c and passes tier
compliance cleanly. The boundary concerns noted above (`handle_disconnect_request` scope and the plugin coupling) are
known and accepted for this iteration.

### `unhub-plugin`

- **Audit date:** 2026-03-24 (re-audit; previous audit 2026-03-20)
- **Declared tier:** T3·3c (External Network Clients) — **see reclassification finding below**
- **Declared role:** Hub matchmaking feature: HTTP client bridge + Hub screen UI

#### Dependencies

Internal: `unhub-client` (T3·3c), `untypes-core` (T0), `untags-core` (T0), `unreplicon-core` (T2), `unmenu-core`
(T4·4c), `unui-core` (T4·4c), `unprofile-core` (T3·3b).

External: `bevy`, `reqwest`, `tokio`, `crossbeam-channel`, `uuid`, `bevy-persistent`, `rand`.

#### Contents

Files: `plugin.rs`, `hub_client.rs`, `ui.rs`. All hub internal modules are `pub(crate)`; only `plugin` is `pub`,
which correctly limits the external surface to `UnhaunterHubPlugin`.

**`plugin.rs`** — `UnhaunterHubPlugin`:

- Reads `CliOptions` at `build()` time to skip all registration on dedicated server.
- Registers startup: `hub_client::setup_hub_client`, `hub_client::initialize_nickname`.
- Registers update: `hub_client::update_hub_status`.
- Registers Hub screen on `AppState::Hub`: `ui::setup_hub_ui` (OnEnter), `ui::hub_menu_event`,
  `ui::update_code_input`, `ui::handle_hub_responses` (Update), `ui::despawn_hub_ui` (OnExit).

Note: registers all systems inline in `build()` rather than delegating to `systems::app_setup(app)`. Minor structural
deviation from the project pattern.

**`hub_client.rs`** — Async HTTP client bridge:

- `HubClient` (Resource) — `crossbeam_channel` tx/rx pair bridging Bevy ECS to an OS thread running a `tokio` runtime.
- `HubRequest` / `HubResponse` — in-process message types (not wire types; wire types live in `unhub-client`).
- `HubStatus` (Resource) — tracks pending state and the last response received.
- `setup_hub_client` — spawns dedicated OS thread; handles `CreateRoom` (PoW challenge → solve → create) and `JoinRoom`
  HTTP sequences via `reqwest`. Inserts `HubClient` and `HubStatus`.
- `update_hub_status` — drains the channel rx from Bevy Update, moves responses into `HubStatus`.
- `initialize_nickname` — mutates `Persistent<PlayerProfileData>` to assign a random nickname letter if none is set.

**`ui.rs`** — Hub screen UI:

- `RoomCodeInput` (Resource) — tracks the room code string being typed by the player.
- `HubMenuID`, `HubMenuMarker`, `HubCodeDisplay` — Bevy components for the Hub screen entities.
- `setup_hub_ui` — spawns `Camera2d` + `MCamera`, full menu layout via `unmenu_core::templates`, room code text node.
- `hub_menu_event` — reads `MenuItemClicked` / `MenuEscapeEvent`, drives create/join room requests, transitions state.
- `update_code_input` — reads `KeyboardInput`, builds the room code string, updates the display text.
- `handle_hub_responses` — processes `HubResponse`, writes `CliOptions::net_mode` and `RoomIdentification`, transitions
  to `AppState::Lobby`.
- `despawn_hub_ui` — despawns all `MenuUI` and `MCamera` entities on exit.

#### Domain Audit (Priority Order)

##### 1. Domain Completeness

There is **no `unhub-core` counterpart**. `HubClient`, `HubStatus`, `HubRequest`, and `HubResponse` all live as
`pub(crate)` inside the plugin. Because nothing outside the plugin depends on these types (all modules are
`pub(crate)`), the missing `-core` is not currently blocking. However, it is a structural constraint: if the UI were
ever extracted or another crate needed `HubStatus`, a `-core` crate would be required. Flag as a known limitation, not
an immediate violation.

The plugin registers no custom events (`app.add_message::<T>()`) — the hub communicates its results by writing directly
to `CliOptions` and `RoomIdentification` rather than by emitting domain events. This contributes to the TDA violation
described below.

##### 2. Tell, Don't Ask (Signal Direction)

**`initialize_nickname` — TDA violation.**

This system reads `Persistent<PlayerProfileData>`, checks whether `nickname_letter` is `None`, and if so picks a random
letter and persists it. The knowledge of _what constitutes an uninitialized nickname_ and _how to initialize one_ belongs
to the profile domain (`unprofile-plugin`), not to the hub. The hub does not own the profile; it is reaching into the
profile and making a decision that is the profile domain's responsibility.

The hub's legitimate concern is: "I need a nickname for this player before I can display it." The correct TDA pattern is
for `unprofile-plugin` to guarantee that a nickname letter is always initialized (e.g., on_startup or on first profile
load), and for the hub to simply read the already-initialized nickname. System belongs in `unprofile-plugin`.

**`handle_hub_responses` — design smell on `CliOptions.net_mode` mutation.**

When a room is created or joined, `handle_hub_responses` sets `cli.net_mode = CliNetMode::Join { address, ticket }`.
`CliOptions` starts as a startup configuration resource derived from command-line arguments, but here it is mutated at
runtime as a communication mechanism between systems. The Hub is "push" in direction (it produces a result and other
systems react), but it mutates a shared config resource rather than emitting a domain event. A `HubRoomReady` event
carrying the address, ticket, code, and secret would be the cleaner TDA-compliant design, with the networking/lobby
setup reacting to it. Not a hard violation in the current scope but flag for future clean-up.

**All other systems — TDA compliant.** `setup_hub_client` is infrastructure setup. `update_hub_status` is a channel
drain. `hub_menu_event` receives generic menu signals and emits hub requests on the channel. `update_code_input` handles
raw keyboard input. `despawn_hub_ui` is state cleanup.

##### 3. Information Hiding

**Vocal alphabet duplicated in `update_code_input`.**

`ui.rs` contains a hardcoded match arm list of valid room-code characters:
`KeyCode::KeyC → 'C'`, `KeyCode::KeyD → 'D'`, … `KeyCode::Digit9 → '9'`. This is the safe vocal alphabet — the same
character set that `unhub_client::generate_room_code()` draws from (filtering `0/O/1/I/5/S/2` ambiguities). The
authoritative definition of which characters are valid in a room code lives in `unhub-client`. The UI is silently
duplicating that knowledge. If the room code alphabet ever changes in `unhub-client`, the UI filter will silently drift.

The fix: expose a `const ROOM_CODE_CHARS: &str` or similar from `unhub-client` and drive the keyboard filter from it.

**`initialize_nickname` encodes profile-domain threshold logic.**

As noted under TDA: the "pick letter if none" decision, including the range `'A'..='Z'`, belongs to `unprofile-plugin`.

##### 4. System Membership

**`initialize_nickname` writes nothing in the hub domain.** Its sole effect is mutating
`Persistent<PlayerProfileData>` — a resource owned by the profile domain. A system that writes exclusively to another
domain's resources does not belong in this plugin. It is misplaced.
**Move `initialize_nickname` to `unprofile-plugin`.**

All other systems write to hub-domain resources (`HubClient`, `HubStatus`, `RoomCodeInput`) or drive hub-scoped UI
entities. System membership is otherwise satisfied.

##### 5. Marker-Gated Write Rule

`hub_menu_event` queries `Query<(&HubMenuID, &MenuItemInteractive)>`. `MenuItemInteractive` is a capability descriptor
from `unmenu-core`, not an entity-class marker (entity-class markers identify _what kind of entity_ something is, e.g.,
`GhostMarker`). The system reads `MenuItemInteractive.identifier` and does not write to it. **No violation.**

`setup_hub_ui` spawns with `MCamera` from `untags-core`. `MCamera` is an infrastructure marker shared across all
menu-type screens (main menu, lobby, hub, campaign). It is not a foreign entity-class marker in the domain sense — it is
a rendering/ECS infrastructure tag. **No violation.**

##### 6. Vertical Slice Supremacy (VSA) — supersedes old split recommendation

**The previous audit's recommendation to split `ui.rs` into a new `unhub-ui-plugin` is WRONG under VSA.**

The hub is a feature vertical slice: Hub matchmaking service, including everything the player sees and does on the Hub
screen. UI, Rendering, and Networking are _output layers_, not domains. The hub domain's output layer is its own Hub
screen. The hub domain should own that screen.

Compare with the established pattern: `unpause-plugin` (T4) owns the entire Pause screen — it is not split into
`unpause-core` + `unpause-ui-plugin`. `unmainmenu-plugin` (T4) owns the Main Menu screen. `unlobby-plugin` (T4) owns
the Lobby screen. The hub feature follows the same pattern.

Splitting the hub UI into a separate crate would fragment the vertical slice — two crates sharing the same feature with
no domain boundary between them. This is the Horizontal-Cut Trap. **Do not split.**

**The correct fix for the tier violation is to reclassify `unhub-plugin` from T3·3c to T4·4c.** The hub is a
full-screen interactive feature; it is T4 material. As T4, imports of `unmenu-core` and `unui-core` become compliant
downward dependencies. The HTTP channel bridge code inside `hub_client.rs` calls into `unhub-client` (T3), which is a
legal downward dependency from T4.

Only one crate currently depends on `unhub-plugin`: the top-level app assembler (`unhaunter/src/app.rs`), which is not
tier-constrained. The reclassification requires no code changes — only moving the crate entry in `Cargo.toml` from the
`3c` group to the `4c` group.

##### 7. Defensive Logging (Silent Failures)

**`hub_menu_event` — silent drop on unrecognized click identifier.**

```rust
if let Some((menu_id, _)) = menu_items.iter().find(|(_, interactive)| interactive.identifier == ev.pos) {
    match menu_id { ... }
}
// no else branch
```

A `MenuItemClicked` event scoped to `AppState::Hub` with no matching `HubMenuID` entity silently does nothing. This is
unexpected in normal play — every click in hub state should match a hub menu item. **Add `warn!` in the else branch.**

**`update_code_input` — silent skip on missing `Text` component.**

```rust
for child in children.iter() {
    if let Ok(mut text) = q_text.get_mut(child.to_owned()) { ... }
    // no else branch
}
```

`setup_hub_ui` always inserts a `Text` component on the code display child. If `.get_mut` fails, the display is
silently not updated. Since this should never happen in normal operation, **add `warn!` in the else branch.**

**`hub_client.rs` worker thread exit — silent on channel close.**

The worker loop `while let Ok(req) = rx_from_bevy.recv()` exits without any log when the Bevy sender is dropped. This
happens on shutdown; a `debug!("Hub worker: channel closed, exiting")` would confirm clean teardown and reduce ambiguity
during debugging.

#### Recommendation

1. **Reclassify `unhub-plugin` to T4·4c** in `Cargo.toml` (move the entry from the `3c` group to `4c`). No code
   changes required. This resolves the T3→T4 import violations and correctly reflects that the crate contains a
   full-screen interactive feature.

2. **Move `initialize_nickname` to `unprofile-plugin`**. Remove `initialize_nickname` from `hub_client.rs` and its
   registration from `plugin.rs`. Add the equivalent startup system in `unprofile-plugin` so the profile domain
   guarantees nickname initialization independently of whether the hub is active. UPDATE: Code deleted - was never wanted.

3. **Expose the room-code character set from `unhub-client`** as a public constant or slice, and drive
   `update_code_input`'s key filter from it to eliminate the duplicated knowledge.

4. **Add missing `warn!` logs** in `hub_menu_event` (unrecognized click) and `update_code_input` (missing Text),
   and a `debug!` on hub worker thread exit.

5. (Future) **Replace `CliOptions.net_mode` mutation with a `HubRoomReady` event** emitted by `handle_hub_responses`,
   consumed by the networking/lobby layer. This removes the runtime mutation of a startup-config resource.
