# B24 - Stairs visibility bleeds backwards via omnidirectional light

## Symptoms

- When a player looks at stairs to view another floor, if the destination floor is very bright, the visibility logic
  switches from a directional cone to an omnidirectional 360º spread.
- This causes the visibility to bleed backwards, occluding the player and making the view confusing.

## Investigation

- The issue lies in the 3D isometric visibility rendering (`unlight` or presentation layers), not the 2D fog-of-war
  (`unfog`).
- Review the recent addition that makes visibility conical based on darkness. The algorithm needs to handle extreme
  brightness differently when calculating cross-floor propagation.
- Ensure the visibility propagation strictly remains conical, projecting _away_ from the player when traveling up/down
  stairs, ignoring the ambient brightness of the destination floor.

## Findings

### Facts (Code Reality)

- **Z-Factor Discrepancy**: `visibility.rs` uses `Z_FACTOR = 2.0` for distance calculations (line 37), while
  `Position::distance2` (the codebase standard) uses `6.0`.
- **Trust Threshold**: The algorithm defines a `threshold` (usually 1.5 to 3.5 tiles) where distance-based
  directionality is ignored (`f = 1.0` if `npds < threshold`).
- **Omnidirectional Zone**: Both the "moving away" check and the conical `cone_factor` are disabled when
  `npds < threshold`.
- **Stair Jump Proximity**: With `Z_FACTOR = 2.0`, tiles on the destination floor (Z+1 or Z-1) start at a distance of
  2.0. This is often below the `threshold`, putting the other floor into the "trust zone" where directionality is not
  enforced.
- **Flood Fill Logic**: The fill uses `f = ((npds - pds) / npref).clamp(0.0, 1.0)` to ensure expansion only happens away
  from the player. This is bypassed inside the `threshold` zone.

### Theories (Observed Behavior Mechanism)

- **Threshold Blind Spot**: Because `Z_FACTOR` is low, the visibility flood reaches the other floor and finds itself
  still inside the `threshold` radius (the "blind spot").
- **Backwards Leak**: Inside this blind spot, the algorithm ignores whether it is moving "away" from the player. It can
  therefore leak "backwards" on the destination floor toward the player's XY position.
- **Omnidirectional Blobbing**: Since the cone logic is also disabled inside the `threshold`, this leak is 360º,
  creating a circular blob of visibility on the other floor instead of a cone.
- **XY Projection Symmetry**: Because the cone calculation projects everything to XY, any tile on the other floor that
  falls "behind" the player in 2D is naturally penalized—unless the `penalty_floor` is high OR the tile is inside the
  `threshold`.

### Conclusion

The "backwards bleed" is caused by the `threshold` (trust zone) being applied across floors. Because the floor above is
considered "close" in 3D distance, the algorithm skips the "moving away" check and the conical restriction.

Restricting the `threshold` to the **same floor only** would ensure that visibility propagation across stairs is always
directional and conical, projecting strictly away from the player as intended. Additionally, aligning `Z_FACTOR` with
the codebase standard (6.0) would improve distance accuracy for cross-floor visibility decay.
