# Crate Audit — T2 · Application Layer

> Part of the Unhaunter DDD audit. Index: [02_crate_audit.md](02_crate_audit.md)

---

## Tier 2 · Application Layer

Game flow, sessions, mode orchestration. Coordinates the domain; does not express it. May import T0, T1. Must never
import T3 or T4.

---

### unmission-core

- **Status:** CURRENT
- Audit date: 2026-03-20
- Declared tier: T2 · Application Layer
- Pair: standalone (no `-plugin` counterpart at this name — lifecycle systems live in `unmission-plugin`)
- Internal deps: `unfoundation-core` (T0)
- Highest tier imported: T0
- Tier compliance: **PASS**

**Notes:**

`unmission-core` is notably thin. It contains:

| Module / type                | Content                                                  | Verdict                       |
| ---------------------------- | -------------------------------------------------------- | ----------------------------- |
| `MissionEvent(End)`          | Fires when the mission should conclude                   | ✅ T2 — coordination event    |
| `MissionEndRequested`        | Marker resource set when end has been initiated          | ✅ T2 — flow control resource |
| `MissionConcludingCinematic` | Marker component or resource for the end-cinematic phase | ✅ T2 — flow control marker   |

Everything in this crate is correct, and the dep profile is exemplary.

**Content misplacement (outside this crate but logically belongs here):**

| Type                     | Where it lives                    | Why it should be here                                                                               |
| ------------------------ | --------------------------------- | --------------------------------------------------------------------------------------------------- |
| `SummaryData`            | `unsummary-core` (declared T4·4c) | Mission outcome data — recorded at T2 (evaluation), consumed by T4 (results screen). Belongs at T2. |
| `MissionEvaluator`       | `unsummary-core` (declared T4·4c) | Evaluation logic is T2 application orchestration; it determines the outcome of the mission.         |
| `ActiveMissionEvaluator` | `unsummary-core` (declared T4·4c) | Points to the evaluator registered for the current mission. This is session-scope state: pure T2.   |

`unsummary-core` is a recurring systemic issue: it is declared T4·4c (a UI/presentation crate) but its contents are
mission-outcome domain data evaluated at T2 time. The types noted above would sharpen `unmission-core` into the
canonical home for "what does it mean for a mission to end?" Once `SummaryData` and `MissionEvaluator` live here, every
crate that cares about mission outcomes imports T2, not a mislabeled T4 crate.

### unmission-plugin

- **Status:** CURRENT
- Audit date: 2026-03-20
- Declared tier: T2 · Application Layer
- Pair: `unmission-core` / `unmission-plugin`
- Internal deps: `unmission-core` (T2), `unsummary-core` (declared T4·4c), `unprofile-core` (T3·3b), `unboard-core`
  (T1·1a), `untypes-core` (T0), `unmetrics-core` (T0), `unfoundation-core` (T0), `unreplicon-core` (T2)
- Highest tier imported: **T4 (declared)** — `unsummary-core` (declared T4·4c, but see systemic mislabeling note)
- Tier compliance: **FAIL** — declared T2, imports T3 and T4

**Violations:**

1. `unprofile-core` (T3·3b) — `handle_mission_events` writes `PlayerProfileData` directly when a mission ends:
   incrementing mission counters, recording best scores, and calling `.persist()`. Profile persistence is a T3
   infrastructure concern. The correct pattern is: emit a domain event (`MissionEvent::End`) and let a T3 observer (in
   `unprofile-plugin`) react to it with persistence writes. The domain plugin should not know how persistence works.

2. `unsummary-core` (declared T4·4c) — `evaluate_mission_end` reads `SummaryData` and calls `MissionEvaluator::evaluate`
   to compute the final grade and score. As noted in the `unmission-core` entry, this is T2 application orchestration
   that happens to live in a crate mislabeled as T4. The functional violation disappears if `unsummary-core` is
   reclassified at T2 (or its types are migrated into `unmission-core`).

**Domain narrative:**

The plugin correctly covers two distinct responsibilities: evaluation (`evaluate_mission_end`) and event dispatch
(`handle_mission_events`). These are correctly T2 concerns. The problem is execution:

- `evaluate_mission_end` runs cleanly — it reads a summary resource and calls an evaluator method. The only issue is the
  mislabeled `unsummary-core` import.
- `handle_mission_events` mixes T2 coordination (save `MissionEndRequested`, trigger the cinematic, clear board) with T3
  persistence (write and persist `PlayerProfileData`). Extracting the profile write to a T3 observer would leave the
  handler clean.

The `unreplicon-core` (T2) import is correct: `handle_mission_events` reads `NetworkId` and sends a network message to
broadcast the mission end to all clients. T2 importing T2 is compliant.

### unclassic-mode-gameplay-plugin

- **Status:** CURRENT
- Audit date: 2026-03-20
- Declared tier: T2 · Application Layer
- Pair: standalone plugin (no `-core`)
- Internal deps: `unmission-core` (T2), `untypes-core` (T0), `unboard-core` (T1·1a), `unlight-core` (T1·1a),
  `unthermal-core` (T1·1a), `unsoundfield-core` (T1·1a), `unplayer-core` (T1·1b), `unghost-core` (T1·1b), `ungear-core`
  (T1·1c), `ungearitems-core` (T1·1c), `uninteraction-core` (T1·1c), `undifficulty-core` (T1·1c), `untruck-core`
  (T1·1c), `unspatial-core` (T0), `unnavigation-core` (T1·1a), `unreplicon-core` (T2), `unbehavior` (T3·3a),
  `untmxmap-core` (T3·3a), `unrender-std` (T4·4a)
- Highest tier imported: **T4** — `unrender-std`
- Tier compliance: **FAIL** — declared T2, imports T3 and T4

**Notable structural issue — missing `[lints] workspace = true`:**

The crate's `Cargo.toml` does not include the workspace-level lint configuration. All other post-refactor crates inherit
clippy and rustfmt settings from `[workspace.lints]`. This crate silently skips all those lints. The fix is a one-line
addition to `Cargo.toml`.

**Violations:**

1. `unrender-std` (T4·4a) — `boot.rs` inserts `GameSprite`, `SpriteLayer`, `TiledCustomTileData`,
   `crate::maps::EntityBlueprint` onto map-loaded entities. Sprite insertion at boot time is T4 initialization logic.
   `unrender-std::consts` is also imported for `Z0_*` layer z-coordinate constants. Those constants live in the wrong
   crate (they are spatial constants, semantically T0, but placed in a T4 rendering crate for historical reasons).

2. `unbehavior` (T3·3a) — `boot.rs` reads `Behavior` to classify entities during boot (determining collision,
   interactive state, etc.). `environmental_mechanics.rs` reads `Behavior` for door charge propagation. `roomchanged.rs`
   reads `Behavior` to determine van door variants. The systemic T3 bleed is present here as in all T1/T2 plugins that
   deal with game entities.

3. `untmxmap-core` (T3·3a) — `boot.rs` reads `TilesetTile` and `EntitiesLoaded` (the Tiled map-load completion marker)
   to drive the boot sequence after map data is ready. `untmxmap-core` is the Tiled ACL integration; reading its types
   directly in a T2 plugin means T2 is directly coupled to the Tiled map format. The intended direction is: T3·3a
   translates Tiled events into domain events (e.g., `LevelReadyEvent`, `BoardSetupEvent`); T2 listens to those domain
   events.

**Domain correct systems (within the plugin):**

| System / file                                        | Responsibility                                         | Domain correctness   |
| ---------------------------------------------------- | ------------------------------------------------------ | -------------------- |
| `simulation_state_transitions.rs`                    | `GameState::Normal` ↔ `GameState::Hunting` transitions | ✅ T2                |
| `roomchanged.rs` (van opening on `RoomChangedEvent`) | Van open/close triggers on `RoomChangedEvent`          | ✅ T2                |
| `evidence_perception.rs`                             | Sensor evidence observation logic                      | ⚠️ T1 (see below)    |
| `object_charge.rs`                                   | EMF / object charge propagation mechanics              | ⚠️ T1 (see below)    |
| `environmental_mechanics.rs`                         | Temperature / fog / sound field mutations              | ⚠️ T1 (see below)    |
| `boot.rs`                                            | Map-entity boot sequence                               | ❌ T3/T4 (see above) |

The three "⚠️ T1" rows are noteworthy: `evidence_perception.rs` and `object_charge.rs` are genuinely T1 domain mechanics
(how physical evidence manifests, how EMF propagates through objects) placed here by convenience at the time the
classic-mode crates were carved out. They do not depend on any T3/T4 types and could be migrated straight into the
appropriate T1 crates (`ungearitems-plugin` for evidence perception, `unboard-plugin` or a new domain crate for EMF
charge). Only `simulation_state_transitions.rs` (hunt state machine) and the van-opening response in `roomchanged.rs`
are authentically mode-specific T2 orchestration.

**Design note — `boot.rs` and T3 map-loading:**

The `boot.rs` system is the central T3 violation: it drives the entire entity initialization sequence from Tiled map
data. This pattern appears in every `-gameplay-plugin` and `-orchestrator-plugin`. The architectural fix is to have the
T3·3a crate (`unmapload-plugin`) fire a richer `LevelReadyEvent` carrying all necessary entity blueprints in domain
terms, so T2 plugins can react to a domain event without knowing about Tiled data structures.

### unclassic-mode-orchestrator-plugin

- **Status:** CURRENT
- Audit date: 2026-03-20
- Declared tier: T2 · Application Layer
- Pair: standalone plugin (no `-core`)
- Internal deps: `unmission-core` (T2), `untypes-core` (T0), `unboard-core` (T1·1a), `unlight-core` (T1·1a),
  `unthermal-core` (T1·1a), `unplayer-core` (T1·1b), `unghost-core` (T1·1b), `unnavigation-core` (T1·1a),
  `unspatial-core` (T0), `undifficulty-core` (T1·1c), `unreplicon-core` (T2), `ungear-core` (T1·1c), `unbehavior`
  (T3·3a), `unmapload-core` (T3·3a), `unrender-std` (T4·4a), `unsummary-core` (declared T4·4c)
- Highest tier imported: **T4** — `unrender-std`, `unsummary-core` (declared T4·4c)
- Tier compliance: **FAIL** — declared T2, imports T3 and T4

**Violations:**

1. `unrender-std` (T4·4a) — `ghost_setup.rs` inserts `LightSensitive`, `GameSprite`, `SpriteLayer`, `Sprite`,
   `TextureAtlas`, `MapColor` onto ghost entities at spawn time. Ghost sprite initialization is T4 rendering setup. The
   domain orchestrator should spawn a ghost entity with domain components only; a T4 observer reacts to the `Ghost`
   component being inserted and attaches the presentation layer. This is the Bevy observer pattern for separating spawn
   from rendering.

2. `unmapload-core` (T3·3a) — `orchestration.rs` listens to `MapEntitiesReadyEvent` and `LevelReadyEvent` to drive the
   mission setup sequence. These are the two Tiled map-loading completion events defined in T3·3a. Consuming these
   events directly in T2 creates the coupling that the event design was supposed to avoid.

   **Systemic note — `LevelReadyEvent` is the highest-leverage fix in the workspace:**

   `LevelReadyEvent` is defined in `unmapload-core` (T3·3a). It is consumed by at minimum:
   `unclassic-mode-orchestrator- plugin`, `unclassic-mode-gameplay-plugin`, `untruck-plugin`, `unwalkie-plugin`,
   `unnavigation-core` (at T1!), `unlight-plugin`, `unfog-plugin`, `unsoundfield-plugin`. Most of these are T1 or T2
   crates. Every one of them must import T3·3a solely for this event.

   Moving `LevelReadyEvent` into `unmission-core` (T2) — and having `unmapload-plugin` (T3·3a) emit it there after
   completing its translation work — would break most of the T3 upward-dependency violations in a single change. This is
   the most impactful single refactor available.

3. `unbehavior` (T3·3a) — `orchestration.rs` reads `Movable` to configure ghost movement at spawn time. `Movable` is the
   Tiled-derived locomotion marker from the map pipeline. Same systemic bleed.

4. `unsummary-core` (declared T4·4c) — `orchestration.rs` inserts `ActiveMissionEvaluator` (carrying a
   `ClassicEvaluator` wrapped in an `Arc<Mutex<dyn MissionEvaluator>>`) onto the mission entity at mission start.
   Setting the active evaluator is squarely T2 application orchestration — the plugin determines _which evaluation
   strategy the mission will use_. That `unsummary-core` carries these types while declared T4 is the same systemic
   mislabeling.

**Architecture highlight — `ClassicEvaluator` and `ActiveMissionEvaluator`:**

The `ClassicEvaluator` pattern deserves explicit notice: the orchestrator instantiates a mode-specific evaluation
strategy at mission start and registers it as the `ActiveMissionEvaluator`. The mission plugin (`unmission-plugin`)
later calls `evaluate()` on whatever evaluator is registered — it never knows which game mode is running. This is a
clean Strategy pattern implementation inside ECS: the active mode (orchestrator) injects its evaluation strategy, and
the evaluation system is mode-agnostic.

This pattern is correct and should be preserved. The only structural fix needed is moving `MissionEvaluator`,
`ActiveMissionEvaluator`, and `ClassicEvaluator` from `unsummary-core` (T4) into `unmission-core` (T2) so the types live
at the correct tier.

**Domain narrative:**

The orchestrator correctly owns what is mode-specific about the classic game mode: spawning the ghost, spawning the nav
mesh, the mission lifecycle sequencing (entered → map loaded → entities hydrated → ghost spawned → play). The violations
are rendering setup (`unrender-std`) and map-loading event coupling (`unmapload-core`). Both are fixable by the general
strategies: move sprite insertion to a T4 observer, move `LevelReadyEvent` to T2.

### uninput-plugin

- **Status:** CURRENT
- Audit date: 2026-03-20
- Declared tier: T2 · Application Layer
- Pair: standalone plugin (no `-core`)
- Internal deps: `unplayer-core` (T1·1b), `unboard-core` (T1·1a), `unspatial-core` (T0), `unreplicon-core` (T2),
  `unbehavior` (T3·3a), `unsettings-core` (T3·3b), `unui-core` (T4·4c)
- Highest tier imported: **T4** — `unui-core`
- Tier compliance: **FAIL** — declared T2, imports T3 and T4

**Notes — no `-core` is justified:**

Unlike `uninventory-plugin` or `unvitals-plugin`, the absence of a `-core` counterpart is correct here. Input handling
is a pure adapter: external input events enter, domain events exit. There are no canonical data types owned by this
bounded context that other domains need to import. The input plugin is a leaf node in the dependency graph.

**Violations:**

1. `unbehavior` (T3·3a) — `hover_system` queries `Interactive.hovered` to drive cursor highlight state. The hover state
   is stored as a field on a T3 entity type (`Interactive`). The fix requires either moving `Interactive` to a T1
   interaction-domain type, or routing hover state through an `HoveredEntity` resource at T0/T1.

2. `unsettings-core` (T3·3b) — `player_input_system` reads `MovementStyle` (a settings preference) to determine input
   mapping (WASD vs click-to-move). User preferences are T3 persistence; input systems should not query settings
   directly. The correct pattern is a T0/T1 resource updated by a T3 observer when settings change.

3. `unui-core` (T4·4c) — `mouse_visibility_system` reads and writes `MouseVisibility` (a T4 UI resource) to control
   whether the OS cursor is shown. This is a T4 rendering/UI concern, not an input concern. Fix: emit a domain event
   from input; a T4 system observes it and updates cursor visibility.

**Domain correct systems:**

| System                        | Responsibility                                                                   | Domain correctness                  |
| ----------------------------- | -------------------------------------------------------------------------------- | ----------------------------------- |
| `player_input_system`         | Keyboard/mouse → `PlayerInput` resource (movement, gear use, interaction)        | ✅ T2 input adapter                 |
| `sync_player_input_to_server` | Send `PlayerInput` snapshot to server each frame                                 | ✅ T2 networking concern            |
| `hover_system`                | Raycast → nearest `Interactive` entity → set hover state                         | ⚠️ T3 for `Interactive` (see above) |
| `update_camera_follow_dir`    | Right-click held → camera rotation delta → `GameConfig.target_camera_follow_dir` | ✅ T2 camera control                |
| `mouse_visibility_system`     | Hide/show cursor based on active UI                                              | ❌ T4 presentation                  |

Three of five systems are correctly placed. The hover system is at the T3 boundary due to `Interactive`; the mouse
visibility system is outright T4.

**Design note — hover belongs in `uninteraction-plugin`:**

The hover system finds the nearest interactive entity and marks it as hovered. This is the dispatch step of the
interaction domain (finding the candidate before the player confirms interaction). It was noted in the
`uninteraction- plugin` audit that `dispatch_interact_intent` is incorrectly placed in `unlocomotion-plugin`. The hover
system in `uninput-plugin` is a similar extraction gap: hover state management belongs in `uninteraction-plugin`,
triggered by input proximity data passed as an event, not by the input system directly querying `Interactive`.

### unfps-core + unfps-plugin

- **Status:** CURRENT
- Audit date: 2026-03-20
- Declared tier: T2 · Application Layer (current placement)
- Pair: `unfps-core` / `unfps-plugin` (same tier: YES)
- Internal deps (`unfps-core`): none (no `un*` deps)
- Internal deps (`unfps-plugin`): `unfps-core` only
- Highest tier imported (`unfps-core`): T0 (no `un*` deps — external crates only)
- Highest tier imported (`unfps-plugin`): T0 (only its own `-core`)
- Tier compliance (current T2 placement): PASS — neither crate imports anything above T0

**This crate pair is in the wrong layer.**

Tier compliance is not the issue. The issue is that `unfps-core` and `unfps-plugin` have **zero `un*` dependencies**.
They implement a portable, game-agnostic Bevy plugin that limits frame rate via `std::thread::sleep`. The crate names
carry the project prefix `un`, but the code has no connection to any Unhaunter domain concept. It could be extracted to
a standalone crate and published to crates.io without any changes to its source — it would just need a rename.

**Why T2 placement is wrong:**

The tier model is about domain knowledge. Being in T2 implies the crate is aware of the application layer: it
coordinates game flow, knows about sessions, orchestrates mechanics. `unfps-plugin` knows about none of these. It sleeps
a thread. T2 crates depend on T1 domain types or T2 session resources; `unfps-plugin` depends on neither.

**Recommended placement: Portable Libraries (above T0 / below the hexagon):**

Per the Portable Libraries appendix, crates that are game-agnostic Bevy plugins belong above T0, outside the hexagonal
architecture diagram entirely. They have no `un*` deps, no T-number, no `-core/-plugin` split (where that split is
unjustified), and no `un` prefix on extraction.

The `-core` / `-plugin` split for `unfps` is also unjustified: `unfps-core` defines one resource (`TargetFps`) and one
system function. The plugin imports the core and calls the system. There is no reason for another crate to import
`unfps-core` independently of the plugin. The correct shape is a single `fps_limiter_plugin` crate (or similar name)
containing both the resource and the plugin implementation.

**Action:**

1. Collapse `unfps-core` and `unfps-plugin` into a single crate.
2. Move it to the `# ── Portable Libraries ──` section in `Cargo.toml` (above T0 entries).
3. Optionally rename it (removing the `un` prefix) to signal it is not part of the domain hierarchy.
4. No code changes required — just `Cargo.toml` restructuring and a crate merge.

### unreplicon-core + unreplicon-plugin

- **Status:** CURRENT
- Audit date: 2026-03-20
- Declared tier: T2 · Application Layer
- Pair: `unreplicon-core` / `unreplicon-plugin` (same tier: YES)
- Internal deps (`unreplicon-core`): `uninteraction-core` (T1·1c), `ungear-core` (T1·1c), `ungearitems-core` (T1·1c),
  `unghost-core` (T1·1b)
- Internal deps (`unreplicon-plugin`): `unreplicon-core` (T2), `untypes-core` (T0), `unfoundation-core` (T0),
  `unspatial-core` (T0), `untags-core` (T0), `unmission-core` (T2), `unnavigation-core` (T1·1a), `unboard-core` (T1·1a),
  `undifficulty-core` (T1·1c), `unplayer-core` (T1·1b), `unghost-core` (T1·1b), `ungear-core` (T1·1c),
  `ungearitems-core` (T1·1c), `uninteraction-core` (T1·1c), `untruck-core` (T1·1c), `unprofile-core` (T3·3b),
  `unmapload-core` (T3·3a), `unbehavior` (T3·3a), `unhub-client` (T3·3c), `unrender-std` (T4·4a), `unsummary-core`
  (declared T4·4c)
- Highest tier imported (`unreplicon-core`): T1
- Highest tier imported (`unreplicon-plugin`): **T4** — `unrender-std` (T4·4a), `unsummary-core` (declared T4·4c)
- Tier compliance (`unreplicon-core`): **PASS** — all deps are T1 or below; T2 importing T1 is compliant
- Tier compliance (`unreplicon-plugin`): **FAIL** — declared T2, imports T3 (`unprofile-core`, `unmapload-core`,
  `unbehavior`, `unhub-client`) and T4 (`unrender-std`, `unsummary-core`)

**Violations (`unreplicon-plugin`):**

1. `unrender-std` (T4·4a) — `ghost.rs` registers `SpectralClarity` (a visual rendering component) as a replicated
   component via `app.replicate::<SpectralClarity>()`. `debug.rs` queries `LightEmitter` from `unrender-std` for debug
   logging. Both are T4 presentation imports in a T2 networking plugin. Replication registration for T4 types should
   live in the T4 plugin that owns those types.

2. `unsummary-core` (declared T4·4c) — `ghost.rs` spawns a `SummaryData` component on the `MissionGoalEntity` and
   bridges it to a resource both ways (`sync_summary_data_to_mission_goal`, `sync_mission_goal_to_summary_data`). As
   noted in the `unmission-core` audit, `SummaryData` is T2 application data mislabeled as T4. The functional violation
   disappears once `SummaryData` is reclassified or migrated to T2.

3. `unprofile-core` (T3·3b) — `bridge.rs` reads `RuntimeInstallationId` to initialise `LocalPlayer`. Player identity
   bootstrapping depends on the persistence layer reading a UUID from disk. The correct pattern is: T3 emits an event or
   writes a T0/T2 resource after reading; T2 reacts to that resource without importing T3 types directly.

4. `unmapload-core` (T3·3a) — `lobby.rs` writes `LoadLevelEvent` (defined in T3·3a) when the server starts a mission
   (`handle_request_start_mission`) and when a join client auto-joins (`process_auto_join`). This couples the T2
   application layer directly to the Tiled map-loading event format. Moving `LoadLevelEvent` to `unmission-core` (T2) —
   as recommended in the `unclassic-mode-orchestrator-plugin` audit — would eliminate this violation.

5. `unbehavior` (T3·3a) — `players.rs` inserts `unbehavior::components::Movable` on every player entity at spawn
   (`setup_mission_players`, `spawn_late_joining_players`). `Movable` is a Tiled-derived locomotion marker that belongs
   to the map pipeline ACL. Player entities spawned by networking code should carry a T1 domain locomotion marker
   instead. The correct fix: define `Movable` (or its semantic equivalent) in a T1 crate such as `unlocomotion-plugin`
   or `unnavigation-core`, and let the map pipeline translate its own `Movable` into that domain type.

6. `unhub-client` (T3·3c) — `auth.rs` calls `unhub_client::tickets::decode_ticket` to validate JWT tickets of
   newly-connected clients. Ticket validation is an infrastructure adapter concern (it speaks a specific authentication
   protocol defined by the hub server). The entire `auth.rs` module belongs in a T3 plugin, not a T2 one.

**Structural issues (`unreplicon-core` — pass-compliant but architecturally wrong):**

`unreplicon-core` passes tier compliance because T2 importing T1 is allowed. However, it is a textbook **God Crate**:
every domain's network message types have been centralised here, creating a single point of coupling for all networked
communication in the game. This is the opposite of bounded-context design.

**1. `GearSkeletonState` — hardcoded gear catalogue in the network layer.**

```rust
pub enum GearSkeletonState {
    Flashlight(FlashlightStatus),
    UVTorch(bool),
    RedTorch(bool),
    RepellentFlask { qty: i32, liquid_content: Option<GhostType> },
    Salt(u8),
    Sage { is_active: bool, consumed: bool },
    Quartz(u8),
    Toggleable(bool),
}
```

Every concrete gear type is an arm of this enum. Adding a new gear item requires editing `unreplicon-core`. This creates
a backward dependency from the network layer back into domain specifics — the network layer is supposed to be a
transport, not a domain registry. The import of `ungearitems_core::components::flashlight::FlashlightStatus` directly
into `messages.rs` makes this concrete: gear item state knowledge lives inside the networking crate.

The correct shape: each gear item's network state is expressed using the item's own serialisable component type,
registered from its owning crate's plugin. `unreplicon-core` carries no gear knowledge at all.

**2. `ExportStateMessage` — player domain state encoded in a flat struct.**

```rust
pub struct ExportStateMessage {
    pub x: f32, pub y: f32, pub z: f32,
    pub direction_dx: f32, pub direction_dy: f32, pub direction_dz: f32,
    pub stamina: f32, pub health: f32, pub sanity: f32,
    pub is_running: bool, pub is_hiding: bool, pub in_truck: bool, ...
}
```

This message is a hand-rolled serialisation of `PlayerVitals`, `Stamina`, `Position`, `Direction`, and several boolean
states. Its existence means `unreplicon-core` owns the canonical shape of the player's networked state — not
`unplayer-core`. Adding a player stat requires editing this struct in the networking crate, not the player domain crate.

**3. The centralised replication registration anti-pattern.**

`players.rs::app_setup` calls `app.replicate::<T>()` for every replicated component across every domain: `Position`,
`Direction`, `PlayerSprite`, `PlayerVitals`, `Flashlight`, `UVTorch`, `RedTorch`, `RepellentFlask`, `SaltData`,
`SaltPile`, `SageBundleData`, `QuartzStoneData`, `Behavior`, `GhostGuess`, `SummaryData`, and more. This means
`unreplicon-plugin` must know the complete set of replicated types across all bounded contexts. In a correct design,
each domain plugin registers its own replicated components in its own `app_setup`. `unreplicon-plugin` would only
register the types it owns (`NetworkId`, `Owner`, `LocallyOwned`, `LobbyInfo`, `ServerGamePhase`, `SelectedMission`).

**4. `NetworkId` belongs at T0.**

`NetworkId` is a 64-bit entity identifier with no game-specific dependencies. It is used by T1 crates (e.g.
`unmission-plugin` reads `NetworkId` when broadcasting the mission end). Placing it in T2 forces any crate that needs a
stable network entity handle to take a T2 dependency, even if it has no other networking concerns. `NetworkId` should
live in `untags-core` or `unfoundation-core` (T0).

**5. `auth.rs`, `connection.rs`, and `procman.rs` are T3 infrastructure inside a T2 plugin.**

- `auth.rs`: JWT ticket validation using HMAC-SHA256 — a specific authentication protocol tied to the hub server. This
  is an adapter translating external auth tokens into domain identity. It belongs at T3.
- `connection.rs`: UDP socket creation, Netcode transport setup, `RenetServer`/`RenetClient` management. Network
  transport is infrastructure I/O. It belongs at T3.
- `procman.rs`: Stdin/stdout channel to a process manager, handling `AssignRoom`/`WipeRoom`/`Shutdown` messages. Pure
  external I/O adapter. It belongs at T3.

All three modules are masquerading as T2 application logic but are in fact T3 adapters for external systems (the hub
server's auth protocol, the UDP transport layer, and the process manager). The T2 plugin is doing T3 work because there
is no separate T3 networking crate — everything was consolidated here.

**Domain narrative:**

The comment in `Cargo.toml` says it all: `# Networking / replication (God Crate — being drained)`. The user's intuition
is correct. The architecture was built by pulling every network concern into one place for expediency. The result is:

- `unreplicon-core`: a message bus containing every message type in the game, with deep domain knowledge embedded in its
  types (`GearSkeletonState`, `ExportStateMessage`, `FlashlightStatus` imports).
- `unreplicon-plugin`: a monolith that sets up transport, validates auth, manages the lobby, spawns players, spawns
  gear, manages ghost replication, handles the mission lifecycle, bridges the process manager, and registers debug
  systems — for every domain simultaneously.

**Recommended decomposition path:**

The "being drained" note signals intent; here is the target shape:

| What                                              | Where it should go                                       |
| ------------------------------------------------- | -------------------------------------------------------- |
| `NetworkId`                                       | `untags-core` or `unfoundation-core` (T0)                |
| `Owner`, `LocallyOwned`, `OwnerId`                | `unreplicon-core` stays (T2 networking primitives)       |
| `LobbyInfo`, `ServerGamePhase`, `SelectedMission` | `unreplicon-core` stays (T2 session/phase types)         |
| `ExportStateMessage` + player lobby spawning      | `unplayer-core`/`unplayer-plugin` (T1·1b)                |
| `ExportGearStateMessage`, `GearSkeletonState`     | `ungear-core`/`ungear-plugin` or `ungearitems-*` (T1·1c) |
| Interaction messages                              | `uninteraction-core`/`uninteraction-plugin` (T1·1c)      |
| Ghost/journal messages                            | `unghost-core`/`unghost-plugin` (T1·1b)                  |
| `app.replicate::<T>()` for each domain's types    | The `-plugin` for the crate that owns `T`                |
| `auth.rs` (JWT ticket validation)                 | New T3 crate or into `unhub-plugin` (T3·3c)              |
| `connection.rs` (UDP transport setup)             | New T3 networking crate (T3·3c)                          |
| `procman.rs` (process manager adapter)            | `unhub-plugin` or dedicated T3 procman crate (T3·3c)     |
| `bridge.rs` (LocalPlayer init from profile)       | `unprofile-plugin` (T3·3b) observing T0 resource         |

The Strangler Fig approach applies here too: drain types out of `unreplicon-core` one bounded context at a time, moving
each domain's messages to its own crate and registering replication there. The God Crate shrinks until only the true T2
networking primitives remain.
